# 여행 챗봇·코스 추천 — 다른 서비스는 어떻게 만들었나

> MZ2AZ-200(AI 코스 추천 엔진) · MZ2AZ-201(여행 도우미 챗봇) 조사 문서.
> 2026-09-03 작성. 담당: 김태환.
>
> 설계 결정과 알고리즘은 [`ai-course-planner.md`](ai-course-planner.md) 에 있다.
> 이 문서는 **바깥 세상이 어떻게 하고 있는가**와 **그래서 우리가 무엇을 했는가**다.

---

## 0. 세 줄 요약

1. **순수 LLM 으로 일정을 짜는 대형 서비스는 사실상 없다.** 전부 도구 호출·RAG 로
   자사 데이터에 묶는 방향이고, 그 묶음이 약했던 Expedia 는 AI 컨시어지를 **폐기**했다.
2. **국내 1위 사업자(트리플)가 이미 우리와 같은 구조를 쓴다** — 자체 알고리즘이 일정을
   계산하고 LLM 은 설명만 한다. 우리 「LLM 샌드위치」는 특이한 선택이 아니라 검증된 선택이다.
3. **K-드라마 촬영지 전용 AI 서비스는 아직 없다. 그러나 정부가 만들기 시작했다.**
   문체부 2026 R&D 가 우리와 거의 같은 범위를 3년 과제로 착수했다.

## 1. 해외 — 무엇이 깨졌는지가 더 중요하다

### 1-1. Expedia 「Romie」 폐기 — 업계에서 가장 명확한 실패 자백

2024 년 대대적으로 띄운 올인원 AI 컨시어지를 **퇴역**시켰다. 임원의 진단이 우리에게
그대로 교훈이다.

> *"travelers left when the bot's answers floated free of Expedia's real inventory,
> rates, and reservations"* — 답이 **실제 재고에서 떠 버리자** 사용자가 몇 번의 대화
> 만에 떠났다. *"You can't put a tower on a foundation of sand."*

복구에 약 1 년이 걸렸는데, **그 대부분이 모델 개선이 아니라 평가 체계 재구축과
「응답이 라이브 데이터에서 나오게 하는」 데이터 인프라 작업**이었다.

**우리에게 뜻하는 것** — 모델을 좋은 것으로 바꾸는 일은 이 문제를 못 고친다.
`_refuse` 와 `shown` 목록, 도구 결과 밖을 말하지 않는 규칙이 이 실패에 대한 우리의 답이다.

### 1-2. Booking.com — 환각을 막을수록 대화가 지루해진다

자사 블로그가 인정한 트레이드오프다. 환각을 줄이려 제약과 예시를 계속 더했더니
**정확해진 대신 반복적이고 지루해졌다.** 자사 조사에서 응답자 **91% 가 AI 에 우려**를
갖고 있고 출력을 완전히 신뢰하는 사람은 **35%** 뿐이었다.

제품 방향도 바꿨다 — 독립 챗봇 탭이 아니라 **예약 여정 단계에 녹아든 컴패니언**으로.
8/11 회의에서 나온 「챗봇은 탭이 아니라 떠 있는 시트」 결론과 같은 방향이다.

### 1-3. Airbnb — 「아직 이르다」고 공개 선언하고 계획 기능을 미뤘다

CEO 는 AI 여행 계획이 아직 준비되지 않았다며 현재 AI 를 **"인터넷의 90년대 중후반"**
수준이라고 했다. 대신 **고객지원부터** 했고, 그 선택은 수치로 정당화됐다 —
평균 해결 시간 **약 3시간 → 6초**, 이후 지원의 **45% 자동화**.

### 1-4. 표로 — 아키텍처와 능동성

| 서비스 | 일정 생성 | 대화로 수정 | 능동적 제안 |
| --- | --- | --- | --- |
| Expedia | LLM (최적화기 공개 안 됨) | 공개 안 됨 | **있음** — 날씨·결항을 감시하다 대안 제시 |
| Booking.com | LLM. **최적화기 언급 전혀 없음** | 대화형(방식 미공개) | 예고 단계 |
| Trip.com TripGenie | LLM 즉시 생성 | **부분 수정 + 다인 협업 편집** | **있음** — 항공 상태·체크인 알림 |
| Mindtrip | LLM+에이전트 추론 | **부분 갱신** — 채팅 수정 시 지도 핀·가격 카드 즉시 갱신 | **있음** — 가격 하락 선제 알림 |
| Kayak | 일정 빌더 없음 | — | 공개 안 됨 |
| Airbnb | **없음** (의도적으로 미룸) | — | — |
| GetYourGuide | **없음** — 계획은 외부 AI 에 맡김 | — | — |

**두 가지가 눈에 띈다.**

- **「일정 최적화기를 쓴다」고 밝힌 상용 서비스가 하나도 없다.** 순서·동선을 알고리즘으로
  푼다는 언급이 어느 1차 출처에도 없다. 우리 `planner.py` 가 오히려 차별점이 되는 자리다.
- **능동성은 전부 「여행 중 사고 대응」이다** — 날씨, 결항, 가격. **위치 기반으로 현장에서
  먼저 말을 거는 서비스는 조사 범위에서 확인되지 않았다.** MZ2AZ-201 이 요구한
  「현재 위치를 근거로 먼저 정보를 준다」는 **아직 아무도 안 한 자리**다.

### 1-5. 시장이 말하는 한계

- GetYourGuide 조사: 여행 계획 세션의 **1/3 이 AI 로 시작**하지만, 액티비티 예약에
  AI 를 쓴 사람은 **17%**. 회사 스스로 *"AI 의 강점은 오늘날 영감이지 거래가 아니다"*.
- Kayak: 과제는 모델 성능이 아니라 **「검색창 대신 대화형에 맡기도록 사용자를 설득하는 것」**.

## 2. 국내 — 우리와 같은 구조를 이미 1위가 쓴다

| 서비스 | 아키텍처 | 일정 생성 | 답하는 데이터 |
| --- | --- | --- | --- |
| **트리플**(놀유니버스) | **LLM 샌드위치** | **자체 알고리즘**이 계산, GPT 는 요약·설명만 | 자사 DB 한정 (POI 310만, 사용자 일정 700만) |
| **마이리얼트립** | LLM 직접 (ChatGPT 래퍼, 48시간 MVP) | **LLM 이 통째로** | **자사 DB 아님** — GPT 일반 지식, 상품은 뒤에 링크 |
| 놀유니버스 AI 에이전트 | 에이전틱 + **MCP 도구 8종** | 도구 조합 | 자사 통합 플랫폼 |
| 여기어때 AI 검색 | 생성형 의미 검색 | 없음 (숙소 한정) | 자사 DB + 리뷰 1,000만 |
| 네이버·카카오 | 추천 알고리즘 + LLM 요약 | 없음 | 자사 장소·리뷰 |

**핵심 두 가지.**

1. **트리플이 우리와 같다.** 국내 최대 규모 사업자가 「알고리즘이 일정을 만들고 LLM 은
   설명만 한다」를 택했다. 우리 설계를 방어할 때 인용할 국내 사례다.
2. **성과 지표를 공개한 곳은 사실상 여기어때뿐이다** — 무결과 검색의 42% 해소, 그중
   **32.3% 가 실제 예약 전환**. 나머지는 전부 「공개 안 됨」이고, 이는 국내 여행 AI 의
   실효성이 아직 대외 검증되지 않았다는 뜻이다.

### 2-1. 경쟁 — K-드라마 촬영지

| 대상 | 정체 | 위협도 |
| --- | --- | --- |
| **문체부 2026 R&D** — 「방송·영상 로케이션 기반 관광지 AI 에이전트」 | 주관 이즈피엠피, **3년 과제**. 촬영지 자동 인식 AI + 개인화 추천 + **환각 최소화 관광 에이전트** + 경로 안내 + AR + 예약 연계. **API 20종을 지역 IT 기업에 무상 배포** | **최상** — 범위가 거의 완전히 겹친다 |
| **KDramaMap** | 개인 운영 웹사이트, 누적 300만+ 방문. **AI 없음** | 중 — 다만 데이터가 압도적 (촬영지 기록 20,839건 / 고유 15,724곳 / 드라마 487편) |
| 서울시 SOUL SPOT | 촬영지 30개소 물리 현판 + QR, AI 음성합성만 | 낮음 |
| 관광공사 × 스튜디오드래곤 「한류 올레길」 | IP 300편 촬영지 코스화. **오프라인 중심** | 중 (데이터·IP 제휴 측면) |

**결론 — 상용 공백은 열려 있으나 시계는 이미 돌아간다.** AI 를 쓴 K-드라마 성지순례
서비스는 현재 없다. 그러나 정부 과제가 같은 범위를 3년 계획으로 착수했고, 결과물이
API 로 무상 배포된다. 우리가 가진 시간은 그때까지다.

## 3. 기술 — 「대화로 고치기」는 어떻게 만드는가

MZ2AZ-201 의 미구현 요구사항 두 개를 어떻게 만들지가 이 절이다.

### 3-1. 부분 수정이 옳다 (그리고 수치가 있다)

| 항목 | 부분 수정(patch) vs 전체 재생성 |
| --- | --- |
| 품질 | **5% 이내 차이** |
| 토큰 | **31% 절감** |
| 지연 | **31~42% 단축** |

(JSON Whisperer, arXiv 2510.04717)

품질이 같고 싸고 빠르면 고를 것이 없다. 게다가 여행 일정에서는 **품질 외의 이유가 더
크다** — 통째로 다시 짜면 사용자가 손대지 않은 1·3일차까지 조용히 바뀐다.
「2일차에서 하나만 빼 줘」라고 말한 사람에게 그것은 시키지 않은 일이다.

**함정 두 개도 확인됐다.**
- **배열 인덱스로 주소를 지정하면 깨진다.** 삭제 후 인덱스 시프트를 모델이 못 따라간다.
- 코딩 에이전트들(OpenHands·SWE-agent·Codex CLI)이 전부 **정확 문자열 매칭**으로
  수렴한 것도 같은 이유다.

→ **우리 결정: 「몇 번째」가 아니라 「일차 + 장소 이름」으로 주소를 지정한다.**

### 3-2. 상태는 대화 이력이 아니라 별도 객체에 둔다

프레임워크들이 공통으로 정리한 원칙이다 — *"agent state 는 대화 이력과 달리 추론 시
모델에 전달되지 않으며, 도구와 애플리케이션 로직이 접근·수정한다"* (Strands Agents).

우리는 이미 `Session` 이 그 역할을 한다. **다만 일정만 빠져 있었다** — `plan_course` 가
결과를 모델에게만 주고 버렸다. 그러면 「2일차에서 개뿔 빼 줘」를 처리하려고 모델이
일정을 기억에서 되짚어야 하고, **그 되짚기가 곧 환각이 들어오는 자리**다.

→ **우리 결정: `Session.plan` 을 만든다.** 오늘 구현했다.

### 3-3. 제약을 넘었을 때 — 자동으로 고치면 안 된다

가장 중요한 발견이다. 「검사 → 자동 재조정」 루프를 오래 돌리면 **결과가 나빠진다.**

> 실제 유효성은 **2 라운드에서 정점**을 찍고 6 라운드에는 **87% → 12% 로 붕괴**했다.
> 그동안 검증기가 보고하는 통과율은 계속 올라간다 — 검증기가 자기 오류에 속는다.
> (VRR-Stop, arXiv 2607.17641)

그리고 **위반을 알리는 방식**이 성공률을 가른다.

| 피드백 방식 | 수정 성공률 |
| --- | --- |
| 원본 에러만 | 28% |
| **위치 + 관측값 + 「허용 가능한 대안값」 + 실패 유형** | **72%** |

(arXiv 2607.14167) 결정적 요소는 **「허용 가능한 대안값」**이었다. 위치와 관측값만 주고
대안을 빼면 개선이 거의 없었다.

→ **우리 결정 둘:**
- **자동으로 자르지 않는다.** 사용자가 넣으라고 한 곳을 코드가 말없이 빼면 화면의
  일정과 사용자가 기억하는 일정이 갈린다. 사실을 알리고 **사용자에게 묻는다.**
- **다만 사실만 알리고 끝내지도 않는다.** 「무엇을 빼면 몇 분이 빠지는지」를 함께 준다.

### 3-4. 능동적 제안 — 언제 말을 걸고 언제 참는가

MZ2AZ-201 의 「현재 위치를 근거로 먼저 정보를 준다」에 해당한다. 필드 연구의 수치가
설계를 바로 정해 준다.

| 트리거 | 참여율 |
| --- | --- |
| **작업 경계 직후** (하나를 끝낸 순간) | **52~73%** |
| 사용자가 무언가를 거절한 직후 | 31% — **거부율 62%**, *"광고처럼 느껴진다"* |
| **유휴(idle) 감지** | **최악** — *"가만히 있을 때 오히려 머릿속으로 생각 중이었다"* |

(arXiv 2601.10253 · CHI 2025 Codellaborator)

그리고 중단의 비용은 크다 — 중단된 작업 복귀에 평균 **약 23분**, **5초짜리 중단도
복잡한 작업의 오류율을 3배**로 만든다. 푸시를 끈 사용자의 **약 절반이 결국 이탈**한다.

→ **우리 결정 셋 (앱 쪽 설계 제안. 구현은 iOS 소관이다):**
1. **트리거는 「작업 경계」로 정의한다** — 스탬프를 찍은 순간, 다음 성지에 도착한 순간,
   경로를 벗어난 순간. **「멈춰 있음」은 트리거로 쓰지 않는다.**
2. **지오펜스는 enter 가 아니라 dwell 로 건다** — 스치듯 지나가는 진입은 무시하고
   일정 시간 머문 뒤에만 발화한다. 안드로이드 API 가 `INITIAL_TRIGGER_DWELL` 로
   이 용도를 문서에 명시해 두었다.
3. **하루 발화 예산을 시스템 상태로 강제하고, 무시가 쌓이면 임계값을 올린다.**
   끄기 버튼 앞에 「덜 받기」 한 단계를 반드시 둔다.

### 3-5. 평가 — 무엇을 결정적으로 재고 무엇을 모델에게 맡기나

업계 합의가 일관된다.

- **결정적으로** — 포맷, 스키마 준수, **도구 선택 정확도**, 상태 술어, 관측 가능한 결과
- **LLM 판정으로** — 어조·유용성 같은 **자연어로 서술 가능한 주관적 차원만**
- **순서** — 결정적 검증을 **먼저** 통과시키고 그 다음에만 판정을 붙인다

한 가지 경고를 새겨 둔다. 벤치마크 자체를 감사한 연구에서 **공식 라벨의 18.5% 가
틀렸다**(BFCL v4 는 20.0%). 그리고 **LLM 에게 테스트 어서션을 쓰게 하면 「의도된 동작」이
아니라 「현재의 (버그 있을 수도 있는) 구현」이 기대값으로 굳는다.**
→ 우리 `tests/` 와 `evals/cases.json` 의 기대값은 사람이 확정한다.

`pass^k` 개념도 가져올 만하다 — 같은 요청을 k 번 돌려 **전부 성공한 비율**. GPT-4o 는
retail 태스크에서 pass^1 약 60% 인데 **pass^8 은 25% 미만**이다. pass@1 은 일관성
붕괴를 숨긴다. 우리 「결정성」 지표(같은 입력 10회 → 같은 출력 100%)가 이미 같은 종류다.

## 4. 그래서 우리는 어디에 서 있나

| | 업계 흔한 방식 | trip-guide |
| --- | --- | --- |
| 일정 계산 | LLM 이 한다 (최적화기 쓴다고 밝힌 곳 없음) | **알고리즘.** 실현 가능률 100% |
| 데이터 결박 | 약하면 Romie 처럼 죽는다 | 도구가 준 것 밖은 답하지 않는다(`_refuse`) |
| 일정 수정 | 부분 수정을 UI 로 증명한 곳은 Mindtrip·Trip.com 정도 | **부분 수정.** 손대지 않은 일차는 안 바뀐다 |
| 제약 위반 | 자동 재조정이 흔하다 (오래 돌리면 붕괴) | **자동으로 안 자른다.** 대안을 주고 묻는다 |
| 위치 기반 능동 제안 | **확인된 사례 없음** | 설계 완료, 구현은 앱 쪽 (§3-4) |
| 평가 | 공개한 곳 거의 없음 | 지표 5 종, 모델 없이 돈다 |

## 5. 오늘 구현한 것 (2026-09-03)

MZ2AZ-201 의 **「대화로 코스를 고칠 수 있게 한다」**가 구현되지 않은 상태였다.
`plan_course` 가 만든 일정을 아무도 들고 있지 않았기 때문이다.

| 한 일 | 자리 |
| --- | --- |
| 일정을 세션이 들고 있게 했다 | `src/session.py` — `Session.plan` |
| 다음 턴 맥락에 일정 요약을 싣는다 | `src/session.py` — `context_block()` |
| 한 일차만 고치는 결정적 함수 | `src/planner.py` — `revise_day()` |
| 일차 간 이동 (한 번의 호출) | `src/planner.py` — `move_stop()` |
| 넘쳤을 때 「뺄 후보 + 아끼는 분」 | `src/planner.py` — `Revision.drop_candidates` |
| 도구 둘 | `schemas/tools.json` — `revise_plan` · `move_stop` |
| 모델에게 쓰는 법을 알린다 | `prompts/system.txt` |
| **위치로 먼저 말 걸기** | `src/proactive.py` — `Guide.observe()` |
| 먼저 건네는 말 (도구 없이) | `src/agent.py` — `speak_first()` |
| 말 거는 규칙 (설정) | `config/guide.json` |
| 걸어 보며 시연 | `src/cli.py` — `/at 37.58,126.99 +120` |
| 시험 | `tests/` — 53 개 → **102 개** |
| 평가 사례 | `evals/cases.json` — 도구 선택 5 → **8** |

**여기에도 LLM 이 없다.** 모델은 「어느 일차에서 무엇을 빼고 넣을지」만 정하고,
순서와 시간표는 `planner.py` 가 다시 푼다. 샌드위치 구조가 수정에도 그대로 적용된다.

실제 데이터(`services/scene-api/seed/v6.csv`, 「도깨비」 57 곳)로 확인한 결과 —

```
사용자: 「2일차에서 한미서점 빼 줘」

  2일차 (수정 전)  5곳 · 총 이동 2,442m · 09:00~14:01
  2일차 (수정 후)  4곳 · 총 이동 1,097m · 09:00~12:01
  1일차            바뀌지 않음
```

빠진 뒤 남은 곳들의 동선이 **다시 최적화되어 이동거리가 55% 줄었다.** 그리고
「2일차에서 에펠탑 빼 줘」에는 결과 대신 이유만 돌아가고 일정은 변하지 않는다.

### 5-1. 먼저 말 걸기 — 판단은 코드가, 말은 모델이

「위치 기반 능동 제공」도 같은 샌드위치로 만들었다. **`proactive.py` 에도 LLM 이 없다.**

```
[앱 · iOS]   GPS 로 위치를 받는다. 지오펜스를 걸고 알림을 띄운다
     ↓ observe(위치, 시각)
[proactive]  말할까 말까를 정한다 — 반경·머무름·예산·중복. 모델 없음
     ↓ Brief (문장이 아니라 재료)
[agent]      speak_first() 가 한두 문장으로 푼다. **도구는 주지 않는다**
```

규칙은 조사 §3-4 를 그대로 옮겼다 —

| 규칙 | 코드 |
| --- | --- |
| 트리거는 작업 경계 (도착) | `kind == "도착"` 이 「지나침」보다 언제나 우선 |
| **유휴는 트리거가 아니다** | 「멈춰 있음」 을 재는 코드가 아예 없다 |
| enter 가 아니라 **dwell** | 계획 정지점 150m·60초 · 계획 밖 80m·90초 |
| 예산은 목표가 아니라 **상태** | 하루 8 회, 발화 간 최소 5 분 |
| 무시가 쌓이면 물러난다 | 한 번 밀어낼 때마다 반경 ×0.6 · 머무름 ×2, 세 번이면 그 종류 중단 |
| **말할 재료가 없으면 참는다** | 작품도 장면도 없으면 발화하지 않는다 |

그리고 참을 때마다 **왜 참았는지**(`last_reason`)를 남긴다. 조용한 기능은 조용히
고장 나고, 고장 났다는 사실조차 조용하기 때문이다.

실제 데이터로 걸어 본 결과 (「눈물의 여왕」 2일 일정) —

```
[   10초] 1번 성지 도착        조용 — 가깝게 오래 머문 곳이 없다   ← 스치듯 지나가면 말 안 한다
[   80초]   1분 서 있음        🔔 도착 · 옹달샘 합정감자탕 → 다음 서강대교
[  280초] 2번 성지 도착        조용 — 마지막으로 말한 지 200초    ← 연달아 말하지 않는다
[  380초]   머무는 중          🔔 도착 · 서강대교 → 다음 여의도IFC
```

시연이 결함 하나를 잡았다. 처음에는 예산·간격 검사를 머무름 계산보다 **먼저** 두었는데,
그러면 쿨다운 동안 성지 앞에 5 분을 서 있던 사람이 쿨다운이 끝난 뒤 **또 60 초를 서 있어야**
했다. 사용자는 이미 그 자리에 있었고 우리가 입을 다물고 있었을 뿐이다 — 순서를 뒤집었다.
