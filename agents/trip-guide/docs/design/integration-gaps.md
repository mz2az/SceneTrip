## 0. 한 줄 요약

에이전트가 **읽는 것은 전부 실재하는 API** 다. 문제는 **내보내는 쪽**이다 —
`effects`·`ui`·먼저 말 걸기가 기대하는 창구가 **계약에 하나도 없다.**

## 2. 없는 것을 전제하는 것 — **합의 필요** ❌

### 2-1. `effects[]` 를 받을 창구가 없다 → **정권호**

에이전트가 「이렇게 저장해 달라」를 내보내는데 **받는 엔드포인트가 계약에 없다.**

| 에이전트가 내보내는 것 | 백엔드가 불러야 할 API | 그 API 는? |
| --- | --- | --- |
| `cart.add` | `POST /cart/items` | ✅ 있음 |
| `cart.remove` | `DELETE /cart/items/{placeId}` | ✅ 있음 |
| `plan.draft` · `plan.revise` · `plan.move` | **저장하지 않는다** — 앱에 그대로 넘긴다 | — |

**쓰기 API 는 전부 있다. 없는 것은 「챗봇 창구」다** — 앱의 말을 받아 에이전트에
넘기고 `effects` 를 적용해 줄 자리(`POST /v1/chat` 같은 것).

### 2-1-1. `X-Device-Id` 를 에이전트는 모른다 — **그래서 `effects` 가 옳다**

쓰기 API 14 개가 전부 `X-Device-Id` 헤더를 요구한다(계약 §parameters). 백엔드는 그것으로
계정을 찾는다(`users.resolve`).

```
📱 프론트    X-Device-Id 를 가지고 있다
⚙️ 백엔드    그것으로 계정을 찾는다
🤖 에이전트  모른다. **알 필요도 없다**
```

에이전트가 `POST /cart/items` 를 직접 부르려면 사용자 신원을 넘겨받아야 하는데, 그것은
에이전트가 가질 이유가 없는 정보다. 권한이 새는 구조가 된다.

읽기 API(`/places`·`/contents`·`/search`)는 이 헤더가 필요 없어서, 지금 에이전트가
헤더 없이 부르는 것이 맞다.

→ **`effects` 로 말만 하고 저장은 백엔드가 한다**는 설계가 이 제약과 정확히 맞물린다.

### 2-1-2. **편집 중인 코스는 DB 가 아니라 앱이 정본이다** → **정권호 + 정승길**

계약이 못 박고 있다 — *"편집 화면의 「완료」가 부르는 하나뿐인 요청이다. …편집하는
동안 서버로는 아무것도 나가지 않는다"* (`PUT /courses/{id}` 설명).

그래서 **백엔드가 DB 에서 코스를 읽어 에이전트에 넘기면 틀린 것을 넘기게 된다.**

```
📱 앱 메모리   1일차 5곳 · 2일차 4곳   ← 사용자가 방금 손으로 고친 것
🗄️ DB         1일차 5곳 · 2일차 5곳   ← 어제 저장한 것
```

DB 것을 넘기면 챗봇이 **이미 없는 것을 빼려 하거나 옛 일정을 고쳐서** 돌려준다.

→ **편집 중인 코스는 앱이 요청에 실어 보내야 한다.**

```json
POST /v1/chat
{ "text": "2일차에서 한미서점 빼줘",
  "context": { "courseId": 7, "editing": true,
               "plan": { "…앱이 들고 있는 편집 사본 전체…" } } }
```

백엔드는 그것을 **그대로 통과**시키고 DB 를 읽지 않는다.

#### 정본이 어디인가

| | 정본 | 왜 |
| --- | --- | --- |
| 장바구니 | 🗄️ DB | 담을 때마다 즉시 저장되므로 |
| **코스 (편집 중)** | 📱 **앱** | 저장 전이므로 |
| 코스 (편집 아님) | 🗄️ DB | 마지막 저장본이 최신 |

**「편집 중이면 앱이 정본, 아니면 DB 가 정본」** — 이 규칙을 계약에 적어야 한다.

### 2-1-3. 저장 시점 — **정함 (2026-09-04): 코스는 초안만 건넨다**

같은 이유로, 챗봇이 짠 일정을 백엔드가 **바로 `PUT` 하면 앱의 편집 규칙과 어긋난다.**
사용자가 「취소」를 눌러도 이미 저장돼 있게 된다.

| | 바로 저장 | 초안으로 띄우기 |
| --- | --- | --- |
| 앱을 껐다 켜면 | 남음 | 사라짐 |
| 「취소」 | 안 됨 | 공짜 |
| 기존 편집 규칙과 | 어긋남 | **일치** |
| 부작용 | 「그냥 물어본」 코스가 쌓임 | 완료를 안 누르면 날아감 |

**「초안으로 띄우기」로 정하고 이름을 `plan.save` → `plan.draft` 로 바꿨다.**
계약이 이미 "편집 중엔 서버로 아무것도 나가지 않는다"고 못 박고 있어, 챗봇만 예외로
두면 「취소」가 동작하지 않는 화면이 생긴다.

→ **백엔드는 `plan.*` 을 저장하지 않는다. 그대로 앱에 넘긴다.**

### 2-2. `ui[]` 를 읽는 앱 코드가 없다 → **정승길**

`RouteGuide.swift` 의 응답 해석은 네 필드뿐이다 — `reply` · `used` · `places` · `took_s`.
`ui` 와 `effects` 는 응답에 실려 가도 **읽히지 않고 버려진다.**

```swift
// 필요한 것 (약 20 줄)
for d in answer.ui {
    switch d["op"] as? String {
    case "course.focus":   코스화면.펼치기(day:); 바뀐줄강조()
    case "course.open":    코스탭으로()
    case "sheet.collapse": 챗봇시트.내리기()
    case "map.focus":      지도.맞추기(placeIds:)
    case "route.draw":     선그리기(placeIds:)
    case "place.card":     장소카드(placeId:)
    default: break         // 모르는 지시는 무시 — 에이전트가 늘려도 앱이 안 깨지게
    }
}
```

### 2-3. 먼저 말 걸기 — **지금 범위에서 뺐다 (2026-09-04)**

한 번 만들었다가 걷어냈다. 판단(반경·머무름·예산)만으로는 동작하지 않고, GPS 수신·알림·
예산 상태 보관이 전부 다른 모듈에 있어야 하기 때문이다. 조사와 설계 근거는
[chatbot-and-planner-survey.md](chatbot-and-planner-survey.md) §3-4 에 남겨 두었다 —
다시 만들 때 그대로 쓸 수 있다.

### 2-4. 앱↔에이전트 임시 규약이 계약 밖이다 → **셋 다**

지금 앱을 붙여 보려고 `web/server.py` 에 `POST /api/chat` 을 만들어 두었다. 이것은
**승길님 프로토타입 서버의 규약을 흉내 낸 것**이고 `contracts/` 에 없다.

```
📱 앱 ──8899──→ 🤖 에이전트     ← 백엔드를 건너뛴다. 임시다.
```

프로토타입 서버가 사라지면 이 규약도 함께 사라진다. **정식 구조로 옮길 때 버릴 코드다.**

### 2-5. 에이전트를 배포할 자리가 없다 → **팀 결정**

`MODULE.bazel` 에서 `rules_python` 이 주석 처리돼 있어 `BUILD.bazel` 도 컨테이너
이미지도 만들 수 없다. 지금은 노트북에서 `python3 -m web.server` 로만 돈다.
초안은 [build-draft.md](build-draft.md).

## 3. 타입·필드 불일치

### 3-1. `placeId` — **고침 (2026-09-04)**

계약은 `integer`(int64)인데 에이전트가 **문자열**로 내보내고 있었고, id 가 없으면
**이름으로 대신**하고 있었다. 이름을 id 로 알고 쓰기를 시도하면 조용히 엉뚱한 행에 걸린다.

```
전:  placeId: "155"      · id 없으면 "한미서점"
후:  placeId: 155        · id 없으면 null (백엔드가 시끄럽게 거절하도록)
```

### 3-2. 점수 신호 둘이 죽어 있다 → **정권호에게 확인 필요**

코스 엔진의 점수는 네 항의 합인데, **scene-api 경로에서는 둘이 0 이다.**

| 신호 | CSV 창구 | scene-api 창구 |
| --- | --- | --- |
| 대표성(rank) | ✅ | ✅ |
| 커버리지 | ✅ | ✅ |
| **언급량(mentions)** | ✅ | ❌ 계약에 필드가 없음 |
| **선별등급(tier)** | ✅ | ❌ 계약에 필드가 없음 |

`PlaceSummary` 에 그런 필드가 없어 `0` 으로 채우고 있다. **없는 값을 지어내지 않고
그 항을 죽이는 쪽**을 골랐지만, 결과적으로 **추천 품질이 CSV 로 돌릴 때보다 낮다.**

→ 권호님께: `PlaceSummary` 에 언급량·선별등급을 실어 줄 수 있는지. 데이터에는 있다
(`v6.csv` 의 `famous_rank`·`audience_acc` 계열).

### 3-3. 영업시간이 없다 → POI 파이프라인

일정이 「가 봤자 닫혀 있는 곳」을 넣을 수 있다. Google 이 목적함수에 쓰는 세 번째 항이
우리에겐 없다. 데이터가 실리면 그때 더한다.

## 4. 누구에게 무엇을 말해야 하나

### 정권호 (백엔드)

1. **챗봇 창구를 열어 달라** — 앱의 말을 받아 에이전트에 넘기고 `effects` 를 적용하는 자리
2. **`effects` 를 DB 에 반영** — 쓰기 API 는 이미 다 있으니 연결만
3. **`PlaceSummary` 에 언급량·선별등급**을 실을 수 있는지 (§3-2)
5. 계약을 `contracts/schemas/` 에 확정 — 지금 초안은 `agents/trip-guide/schemas/effects.json`

### 정승길 (프론트)

1. **`ui[]` 를 읽어 화면을 바꾸는 코드** (§2-2, 약 20 줄)
2. **주소 하드코딩 제거** — `RouteGuide.baseUrl = "127.0.0.1:8899"` → 백엔드
4. **모르는 `op` 은 무시** — 에이전트가 지시를 늘려도 앱이 안 깨지게
5. `region_pool` 반경 **25km 는 iOS `RoutePlanner` 실측값**을 그대로 쓴다. 한쪽을 바꾸면 앱과 챗봇이 서로 다른 코스를 낸다 — 바꾸면 알려 주세요

### 팀 결정

- `rules_python` 을 켤지 (§2-5). 켜야 에이전트를 배포할 수 있다

## 4-1. 창구가 둘이다 — 마법사는 모델을 안 거친다

앱에는 **AI 일정짜기 마법사**(`RouteWizardView.swift`)가 따로 있다. 챗봇과 별개 입구이고,
질문 넷을 폼으로 받는다 — 기간 · 작품 · 빡빡/널널 · (미리 받아 둔 현위치).
제 `plan_course` 의 인자와 그대로 겹친다.

**폼은 이해할 것이 없다.** 구조화된 값을 문장으로 만들어 모델에게 주고 모델이 다시
값으로 되돌리는 것은 3~5 초와 토큰을 쓰고 아무것도 얻지 못한다. 그래서 창구를 둘로 나눴다.

| 창구 | 입력 | 모델 | 실측 |
| --- | --- | --- | --- |
| `POST /api/chat` | 자연어 | 씀 (①이해 ③설명) | 3~5 초 |
| **`POST /plan`** | 구조화된 값 | **안 씀** | **0.023 초** |

두 창구가 **같은 엔진, 같은 응답 모양**(`plan` · `effects` · `ui`)을 쓴다. 받는 쪽이 두 벌을
만들 이유가 없다. 시험이 두 경로의 일정이 같음을 확인한다.

`POST /plan` 은 **API 키 없이도 동작한다.** 모델을 안 부르기 때문이다. 키가 없으면 대화만
막히고 이 창구는 산다.

```json
POST /plan
{"titles":["도깨비"], "days":2, "pace":"packed", "start":[37.58,126.99]}
→ {"plan":{…}, "effects":[{"op":"plan.draft","plan":{…}}],
   "ui":[{"op":"course.open","day":1}], "took_s":0.023}
```

**회의 확정과도 맞는다** — *"AI로 초안을 만들고 바로 저장시키는 게 아니고, 거기서
수정할 수 있게 해 줘야"* (`RouteWizardView.swift` 머리말). 그래서 `plan.draft` 다.

### 마법사가 묻는데 엔진이 안 받는 것

**`떠나는 날`** — 앱은 선택 항목으로 묻는다. 엔진은 받지 않는다. 영업시간 데이터가
없어 지금은 쓸 데가 없지만, 앱이 이미 묻고 있으므로 받아서 결과에 실어 주는 것이 맞다.

## 5. 정리

```
읽기   ✅ 있는 API 만 쓴다 (5/20)
쓰기   ⚠️ API 는 있는데 부르는 쪽이 없다
지시   ❌ effects·ui 를 받는 쪽이 양쪽 다 없다
배포   ❌ Bazel 타깃을 만들 수 없다
```

**에이전트 쪽에서 더 할 수 있는 일은 거의 없다.** 남은 것은 전부 합의와 다른 모듈의 작업이다.
