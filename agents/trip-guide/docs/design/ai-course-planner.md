# AI 코스 추천 엔진 설계 — 왜 LLM 에게 일정을 짜게 하지 않는가

> MZ2AZ-200(AI 코스 추천 엔진) · MZ2AZ-201(여행 도우미 챗봇) 설계 문서.
> 2026-09-02 작성. 조사 → 결정 → 구조 순으로 적는다.

## 1. 조사 — 실제 서비스는 어떻게 하는가

### 1-1. 순수 LLM 에게 일정을 맡기면 실패한다

여행 일정은 **제약 만족 문제**다. 하루 시간이 정해져 있고, 장소 사이 이동에 시간이
들고, 같은 곳을 두 번 가면 안 되고, 날짜끼리 겹치면 안 된다. LLM 은 이 계산을 못 한다.

| 출처 | 측정 | 결과 |
| --- | --- | --- |
| MIT 통제 실험 | 순수 LLM 이 만든 일정의 **실현 가능 비율** | **약 4%** |
| 같은 실험, 복잡한 일정 | GPT-4 단독 | **0.6%** |
| Hao et al. (2024) | LLM + 알고리즘 결합 | **97%** |
| Google Research | Gemini + 2 단계 최적화 | 벤치마크 **90%+** |

숫자의 크기가 결론을 대신한다. **일정 계산을 LLM 에게 시키면 스무 번에 열아홉 번
틀린다.** 2026 년 업계는 "pure LLM" 에서 **신경-기호 혼합(neuro-symbolic)** 으로
옮겨 갔다 — LLM 은 말을 다루고, 계산은 알고리즘이 한다.

### 1-2. Google 의 구조 — 우리가 베낀 것

Google Research 의 [Optimizing LLM-based trip planning](https://research.google/blog/optimizing-llm-based-trip-planning/)
은 이렇게 나눈다.

```
Gemini 가 초안을 낸다  →  최적화기가 "초안과 비슷하면서 실현 가능한" 일정을 찾는다
                          1 단계: 하루 안의 배치를 동적계획법으로 최적화
                          2 단계: 날짜끼리 장소를 교환하는 지역 탐색
```

최적화 목적함수는 셋의 합이다 — **초안과의 유사도 + 이동 시간 + 영업시간**.
LLM 의 취향은 살리되 물리 법칙은 알고리즘이 지킨다.

### 1-3. 학계의 이름 — TTDP / 팀 오리엔티어링

이 문제는 관광 분야에서 **TTDP(Tourist Trip Design Problem)** 로 불리고, 보통
**시간창을 가진 팀 오리엔티어링 문제(TOPTW)** 로 모형화한다. 표준 해법은
"지리 기준으로 POI 를 클러스터링한 뒤 반복 지역 탐색(ILS)" 이다. 하루 = 한 팀원,
장소 점수 = 이익, 시간 = 예산으로 두면 그대로 우리 문제다.

### 1-4. 상용 챗봇이 깨지는 세 자리

여행 챗봇 비교 기사들이 공통으로 짚는 실패 지점은 셋이다.

| 깨지는 곳 | 증상 | 우리의 대응 |
| --- | --- | --- |
| **살아 있는 데이터** | 가격·영업 상태를 지어낸다 | 도구가 준 데이터 밖은 답하지 않는다. 못 하면 결과를 아예 안 준다(`_refuse`) |
| **상태 유지** | 긴 대화에서 제약을 잊는다 | `Session.context_block()` 이 매 턴 「지금 상태」를 다시 넣는다 |
| **실행** | 계획만 하고 아무것도 못 한다 | `update_cart` · `plan_course` 가 실제 장바구니와 일정을 바꾼다 |

MZ2AZ-201 이 요구한 *"일반 GPT 쓰는 건 다를 게 없다"* 에 대한 답이 여기 있다.
**차별점은 모델이 아니라 모델을 묶어 두는 구조다.**

## 2. 결정 — LLM 샌드위치 3 단계

```
  ①  이해        ②  계획              ③  설명
  ─────────      ──────────────      ─────────
  자연어         결정적 알고리즘      일정 → 사람의 말
  → 제약 JSON    (LLM 없음)          숫자는 알고리즘 것만 그대로
  [LLM]          [코드]              [LLM]
```

**가운데는 절대 LLM 이 아니다.** 거리·순서·시간은 전부 코드가 푼다.
바깥 두 겹만 LLM 이다 — 말을 알아듣는 일과 말로 풀어 주는 일.

### 왜 이렇게 나누나

- **틀릴 수 없는 것은 틀리지 않게 한다.** 거리 계산에 LLM 을 끼우면 §1-1 의 4% 가 된다.
- **평가할 수 있다.** 가운데가 결정적이라 같은 입력에 같은 일정이 나온다 —
  모델 없이 테스트가 돌고, 회귀를 잡을 수 있다.
- **모델을 갈아 끼워도 일정은 안 바뀐다.** DeepSeek 을 다른 모델로 바꿔도 §2 는 그대로다.

### 챗봇에서는 ①이 공짜다

챗봇 경로에서는 **도구 호출(tool calling)이 곧 ① 이해 단계**다. 모델이
`plan_course(titles=["도깨비"], days=2, pace="normal")` 를 부르는 순간 자연어가
이미 구조화된 제약으로 바뀌어 있다. 스키마 검증(`validate_args`)이 그 결과를 한 번 더
거른다. 그래서 챗봇에는 별도의 이해 프롬프트가 필요 없다 — 기존 에이전트 루프가
그대로 샌드위치가 된다.

CLI 의 `--plan "도깨비 촬영지로 2박 3일"` 한 줄 모드에서만 ①을 명시적으로 부른다
(`prompts/plan_intent.txt`). 발표 데모용 경로다.

## 3. 알고리즘 — 4 단계

### 3-1. 후보 모으기와 점수

**작품을 기준으로 던진다.** MZ2AZ-200 의 지적 그대로다 — 같은 장소가 여러 작품에
나오는데 우리 데이터는 「이 장소가 어느 작품 때문에 담겼는지」를 장소 쪽에 저장하지
않는다. 그래서 `by_title(작품)` 으로 모은다.

점수는 회의에서 나온 세 축(**카운트 · 리뷰수 · 거리**)을 그대로 쓴다.

| 항목 | 신호 | 비고 |
| --- | --- | --- |
| 대표성 | 창구가 준 **순서**(작품 안 등수) | scene-api 는 인기순으로 준다. CSV 는 `rank_in_title` |
| 언급량 | `mentions` | **작품을 가로질러 비교할 수 있는 유일한 값**(places.py 주석). scene-api 는 안 주므로 0 |
| 등급 | `tier`·`selected` | 김태환 선별. scene-api 는 안 주므로 0 |
| 겹침 | 요청한 작품 중 **몇 개를 커버**하는가 | 두 작품에 다 나오는 장소는 한 번 가서 둘을 본다 |
| 근접 | 출발점에서의 거리 | 점수에서 빼지 않고 §3-2·3-3 에서 동선으로 푼다 |

창구에 따라 없는 신호가 있다. **없으면 0 으로 두고 있는 신호로만 판단한다** —
가중치를 몰래 재분배하지 않는다. 어떤 신호가 살아 있었는지는 결과의 `근거` 에 적는다.

### 3-1.5. 지역으로 먼저 거르기 (25km)

**날짜에 나누기 전에 「한 여행지」 로 좁힌다.** 이 단계를 빠뜨렸다가 실측에서 걸렸다
(2026-09-02, 저장소 기준 데이터 155곳) — 「도깨비 + 이태원 클라쓰 1박 2일」 이
**2일차에 제주도 카페 한 곳**을 넣었다. 점수만 보고 상위 10곳을 뽑았더니 제주 한 곳이
끼었고, k-means 는 그것을 성실히 별도의 날로 갈라 주었다. **알고리즘은 맞게 돌았는데
결과가 여행이 아니었다.**

촬영지를 25km 반경으로 묶고 **가장 많이 몰린 덩어리**부터 담는다. 많이 몰린 곳이 그
작품의 중심지이고 여행자가 가는 곳도 거기다. 모자라면 가장 가까운 옆 덩어리를 붙인다.
출발점이 한국 안이면 그쪽 덩어리를 먼저 잡는다 — 부산에 있는 사람에게 서울 코스를
내밀 이유가 없다.

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 도깨비+이태원 클라쓰 1박 2일 | 1일차 44.6km · **2일차 제주 1곳** | 1일차 15.1km 5곳 · 2일차 13.0km 5곳 |

같은 문제를 승길님이 iOS 쪽에서 먼저 풀었다(`RoutePlanner.regionPool` — 눈물의 여왕
3일 590km → 69km). **반경 25km 도 그쪽 실측값을 그대로 쓴다** — 두 구현이 다른 값을
쓰면 앱과 챗봇이 서로 다른 코스를 내놓는다.

### 3-2. 날짜 배분 — 지리 클러스터링

k-means(k = 일수). 초기 중심은 **k-means++ 를 결정적으로** 돌린다(난수 씨앗 고정).
같은 입력에 같은 배분이 나와야 평가가 된다.

거리는 하버사인. 한국 규모에서는 평면 근사로도 되지만 이미 `haversine_m` 이 있다.

### 3-3. 하루 안 순서 — 최근접 + 2-opt

최근접 이웃으로 사슬을 만들고 **2-opt** 로 다듬는다. 하루 3~7 곳이라 2-opt 는
수십 번 비교면 끝나고, 교차하는 동선(눈에 바로 띄는 못난 경로)을 없앤다.

기존 `order_by_walk` 는 최근접만 한다. 이 엔진은 그것을 2-opt 로 확장한 판을 쓴다.

### 3-4. 시간표와 잘라내기

- 시작 09:00, 하루 예산은 `pace` 가 정한다(느긋 360분 · 보통 480 · 빡빡 600).
- 체류 시간은 `kind` 별 기본값(`config/planner.json`).
- 이동 시간은 **직선거리 ÷ 속도** — 도보 4km/h, 3km 넘으면 대중교통 18km/h 로 본다.
- 12:00 · 18:00 을 지나는 자리에 식사 표시를 넣는다. 식당을 고르지는 않는다 —
  맛집 데이터가 없고, 없는 것을 아는 척하지 않는 것이 이 저장소의 규칙이다.

**자를 때 — 「아낀 시간 ÷ 잃는 점수」 가 가장 큰 곳부터.** 점수만 보고 자르면 안 된다는
것을 실측으로 배웠다(2026-09-02): 「도깨비 당일치기」 에서 서울중앙고(1위)와 인천
한미서점(2위)을 남기고 2.5km 옆의 개뿔(3위)을 뺐다. 셋의 점수는 비슷한데 **한미서점
하나가 43km 왕복으로 예산을 다 먹는다** — 그 사실이 점수 규칙에는 보이지 않는다.
오리엔티어링에서 쓰는 이익 대비 비용 규칙으로 바꾸니 43km → 2.5km 가 됐다.

**채울 때 — 「점수 ÷ 늘어나는 시간」 이 가장 큰 곳부터.** 자르기만 하고 채우지 않으면
하루가 텅 빈다(같은 실측에서 360분 예산에 2곳 2시간만 썼다). 뺀 자리를 후보 목록의
다음 곳으로 메운다. 자를 때 쓴 기준을 뒤집은 것이라 두 방향이 서로 싸우지 않는다.

### 3-5. 날짜 간 교환 (Google 2 단계 대응)

배분이 끝난 뒤, 서로 다른 두 날의 장소를 맞바꿔 보고 **총점(장소 점수 합 − 이동
비용)이 오르면** 채택한다. 개선이 없을 때까지, 최대 `max_swap_rounds` 번.

이 한 단계가 "클러스터링만 한 일정" 과 "말이 되는 일정" 을 가른다 — 경계에 걸친
장소가 엉뚱한 날에 붙는 문제를 푼다.

## 4. 정직하게 적어 두는 한계

- **직선거리다.** 실제 도보·대중교통 시간이 아니다. 결과에 그렇게 적어 보낸다.
- **영업시간을 모른다.** 우리 데이터에 없다. Google 이 쓰는 세 번째 항이 우리에겐 없다.
  POI 파이프라인(MZ2AZ-275 계보)이 영업시간을 실으면 그때 목적함수에 더한다.
- **리뷰 수가 없다.** `mentions`(언급량)로 대신한다. scene-api 경로에서는 그마저 0 이라
  창구가 준 순서만 남는다.

## 5. 측정 — 무엇을 평가로 볼 것인가

§1-1 의 숫자와 같은 종류를 우리도 잰다. `evals/` 가 모델 없이 돌린다.

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| **실현 가능률** | 하루 예산 초과·중복 방문·좌표 없는 정지점이 하나도 없는 일정의 비율 | 100% (알고리즘이라 당연해야 한다) |
| 결정성 | 같은 입력 10 회 → 같은 출력 | 100% |
| 동선 효율 | 2-opt 적용 전후 총 이동거리 | 개선되어야 한다 |
| 커버리지 | 요청한 작품이 하루 이상 등장하는 비율 | 높을수록 좋다 |
| 도구 선택 | 대본 모델(`ScriptedClient`)로 「일정 짜 줘」→`plan_course` 를 부르는가 | 100% |

**실현 가능률이 100% 여야 한다는 것이 이 설계의 요점이다.** 순수 LLM 이 4% 인 자리에서
우리는 구조적으로 100% 가 나온다 — 자랑이 아니라 알고리즘을 쓰면 당연한 결과이고,
그 당연함을 얻으려고 LLM 을 가운데서 뺀 것이다.
