# AI 일정 생성 — 모델이 성지를 고른다

> 작성 2026-10-02 · 담당 김태환 · 관련: [ai-course-planner.md](ai-course-planner.md)(결정적 엔진)

## 2026-10-15 — 챗봇·CLI 도 모델이 짠다 (MZ2AZ-453)

사용자 결정: **모든 일정 생성은 LLM 으로.** 마법사(`POST /plan`), 챗봇의 `plan_course`, CLI 의
`--plan` 이 모두 `llm_planner.plan_with_model` 을 부른다. 엔진은 모델 응답이 깨졌거나 모델을 부를
수 없을 때만 짠다(마법사가 이미 쓰던 규칙 그대로). 일정 **고치기**(`revise_plan`·`move_stop`)는
그대로 엔진이다 — 사용자가 말한 곳을 빼고 넣는 일이라 새로 짜는 것이 아니다.

계기: 챗봇에 「도깨비랑 폭싹 속았수다로 2박 3일」 을 물었더니 사흘 모두 제주였다. 엔진의
`region_pool` 이 촬영지가 가장 많이 몰린 한 지역(제주, 폭싹 속았수다)만 남겨 도깨비가 통째로
빠졌다. 같은 요청을 모델에게 주면 두 작품이 모두 들어갔다(로컬 scene-api, gpt-oss-120b):

| 요청 | 엔진 | 모델 (2 회) |
| --- | --- | --- |
| 도깨비 + 폭싹 속았수다, 3일 느긋하게 | 3일 모두 제주 — 도깨비 0 | 2/2 두 작품 모두 |
| 사랑의 불시착 + 더 글로리, 2일 | 두 작품 모두 | 2/2 두 작품 모두 |
| 도깨비 + 이상한 변호사 우영우, 3일 | 두 작품 모두 | 2/2 두 작품 모두 |

엔진도 고쳤다(모델이 못 했을 때 같은 일이 나지 않게) — 지역으로 좁힌 뒤 한 곳도 남지 않은
작품은 그 작품의 중심 지역을 몫(`keep ÷ 작품 수`)만큼 붙인다. 붙은 지역은 `cluster_by_day` 가
다른 날로 가른다.

알아 둘 점: 모델 경로는 출발지를 서울로 고정한다 — 챗봇에서 「현위치에서 시작」 이라고 해도
모델이 짠 일정에는 반영되지 않는다(아래 「알려진 한계」 와 같다).

하루에 너무 많이 넣는 일도 그대로 둔다(사용자 결정) — CLI 「폭싹 속았수다 하루 빡빡하게」 에서 모델이
10곳·약 350km 를 넣어 마치는 시각 어림이 38:21 이었다. 예전 엔진은 하루 480분을 넘으면 뺐다.
10/02 의 「모델 판단을 코드가 고치지 않는다」 를 유지한 것이다 — 고치려면 지시문이 아니라 코드가
뒤쪽을 자르는 방법이 남아 있다.

## 무엇이 바뀌었나 (2026-10-02, 마법사)

앱의 「AI 로 일정 짜기」 마법사(`POST /plan`)가 **모델을 먼저 부른다.** 작품의 성지 목록을
주면 모델이 날짜별로 갈 성지를 고르고, 모델이 답을 못 주면 기존 결정적 엔진(`planner.py`)이
일정을 만든다. 응답 모양(`plan_to_api`)은 그대로라 scene-api·앱 계약은 바뀌지 않는다.

| | 전 | 후 |
| --- | --- | --- |
| 성지 고르기 | 엔진: 점수 → 25km 반경 필터 → k-means | 모델 (`src/llm_planner.py`). 성지마다 위치·인기도만 주고 규칙은 주지 않는다 |
| 성지 인기도 | 없음 (DB 값은 작품 점수의 복사) | 수집 CSV 의 성지점수 (`config/place_scores.json`) |
| 출발지 | 앱이 보낸 현위치 | 서울 고정 |
| 모델 호출 | 0 회, 0.02 초 | 1 회, 실측 0.6~2 초 |
| 실패 시 | — | 엔진으로 돌아간다 |

## 왜

멘토링 지적(2026-09-29): 「일정 생성 AI 의 기능이 너무 빈약하다」. 엔진을 들여다보니 원인은
알고리즘보다 재료였다.

1. **성지별 인기도가 없다.** `place.popularity_score` 는 시드 적재가 작품 점수를 복사한 값이라
   (`services/scene-api/seed/candidates.sql` §7) 한 작품의 성지가 전부 같다. 수집 CSV 에는 성지별
   점수가 있지만 `notes` 칸 안에 있어 적재에서 버려진다.
2. **25km 반경 필터가 대표 성지를 버린다.** 도깨비의 주문진(서울에서 167km)은 「가장 많이 몰린
   덩어리」 가 아니라서 거의 항상 빠졌고, 「꼭 갈 곳」 으로 지정해도 빠졌다.

## 모델에게 주는 것

프롬프트는 `prompts/plan_llm.txt`, 설정은 `config/llm_planner.json`.

- 좋아하는 작품, 일수, 컨셉, 꼭 갈 곳, 출발지(서울)
- 성지별 id·이름·**위치**·위경도·인기도. 위치는 주소 앞 두 마디이고 시·도 이름을 짧은 꼴로
  맞춘다(「강원 강릉시」 · 「서울 종로구」). 수집 CSV 주소가 「서울」·「서울특별시」 로 섞여 있다
- 성지는 인기도 높은 순으로 나열한다

**규칙 문장도, 지역 묶음도 주지 않는다**(2026-10-02 결정). 「하루는 한 지역 안에서」,
「인기도는 같은 작품 안에서만 비교」 같은 지시를 넣지 않는다. 일정을 어떻게 나눌지는 모델이 정한다.

**컨셉은 숫자 없이 성격으로 준다.** 「하루 6~7곳」 처럼 숫자를 주면 모델이 그 수를 채우려고
다른 지역 성지를 끌어왔다.

주지 않는 것: 출발 시각·이동 시간·체류 시간. 화면의 시각은 엔진의 시간표 함수가 어림으로 채운다.

## 성지 인기도는 어디서 오나

**scene-api 응답이 정본이다**(scene-api 1.16.0, MZ2AZ-339). 장소 목록의 `contents[].popularity` 가
장소×작품 산정 점수다(`place_content.popularity_score`, 수집 CSV 의 정식 칸에서 적재). `src/sceneapi.py` 가
그 값을 `Scene.popularity` 로 받고, `popularity()` 가 0 보다 크면 그것을 쓴다.

값이 없을 때만 `config/place_scores.json` 으로 돌아간다 — PRD 의 scene-api 가 1.16.0 이 되기 전까지의 다리다.
이 표는 **예전 CSV 에서 뽑아 지금 DB 와 다르다**(2026-10-14 로컬: 배다리헌책방거리 파일 15.4 · DB 1.5, 도깨비방파제
39.1 · 20.0). 수집 CSV `notes` 의 성지점수를 `scripts/extract_place_scores.py` 가 (작품, 장소 이름, 좌표, 점수) 로
뽑은 표다. scene-api 에서 받은 성지에 (작품, 이름) 으로 붙이고, 이름이 다르면 **같은 작품의 300m 안
좌표**로 붙인다 — 같은 장소가 작품마다 다른 이름으로 수집됐고(「고창 학원농장」 · 「고창 학원농장
메밀밭」) DB 는 이름을 하나만 남긴다. 로컬 DB 96 곳 전부 점수를 찾는다.

## 엔진으로 돌아가는 경우

모델의 판단은 고치지 않는다. 아래일 때만 엔진이 대신 일정을 만든다(`LlmPlanError`).

- 키가 없거나 모델 호출이 실패·시간 초과
- 응답이 JSON 이 아니거나 `days` 가 없음
- **후보에 없는 성지 id 가 하나라도 있음** — 그 응답은 통째로 버린다
- 성지를 하나도 고르지 않음

`config/llm_planner.json` 의 `enabled` 를 `false` 로 두면 모델을 아예 부르지 않는다.

### Bedrock 으로 바꾼 뒤 (2026-10-10, MZ2AZ-395)

같은 사례 21 개, AWS Bedrock `openai.gpt-oss-120b-1:0` (us-west-2, 추론 강도 low). 한 번 돌린 값이다.

| | DeepSeek flash (10-02) | Bedrock gpt-oss-120b (10-10) |
| --- | --- | --- |
| 쓸 수 있는 응답 | 21/21 | 21/21 |
| 하루 안 두 성지가 50km 넘는 날 | 14 | 15 |
| 작품 1위 성지 포함 | 18 | 18 |
| 꼭 갈 곳 포함 | 21 | 20 |
| 컨셉보다 많이 넣은 사례 | 9 | 3 |
| 평균 이동 | 375km | 419km |
| 응답 시간 | 중앙 1.3 초, 최대 1.7 초 | 중앙 1.8 초, 최대 3.3 초 |

- `response_format: json_object` 를 주면 여는 중괄호를 두 번 써서 21 건이 모두 깨졌다. 그래서
  `config/model.json` 의 `json_response_format` 을 껐다 (끈 뒤 21/21).
- 도구 호출은 한 번 불러 확인했다(1.1 초, 인자 정확). 챗봇 턴 전체의 p95 는 아직 재지 않았다.

규칙과 지역 묶음을 뺀 지금 안이 채택안이다. 대신 **하루에 먼 곳을 섞는 날이 3 → 14 로 늘었다**
(예: 서울 성지와 인천·수원을 한 날에).

로컬 클러스터에서 앱 경로(`POST /v1/guide/plan` → scene-api → 에이전트 → scene-api 조회)로도
확인했다. 200, 0.6~2.0 초. scene-api 이미지는 9 월 중순 빌드이고, 에이전트는 노트북에서 띄워
클러스터의 scene-api 가 부르게 했다(로컬 클러스터에는 에이전트 매니페스트가 없다).

### 알려진 한계

- **하루에 먼 곳을 섞는다.** 위의 「퍼진 날」 14 일.
- **컨셉보다 많이 넣는다.** 「빡빡하게」 에 하루 10~11 곳, 「널널하게」 에 하루 7 곳인 날이 있다.
- **날짜 순서가 서울 출발에 맞지 않을 때가 있다.** 그래서 평균 이동이 엔진보다 길다.
- 모델 응답은 같은 입력에도 달라질 수 있다(temperature 는 `config/model.json` 값).
- 실측은 한 모델·사례당 1 회다.
