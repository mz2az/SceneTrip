# 10. 사례 A — 지도 영역 POI 조회: 흩어진 저장 순서 때문에 30 개를 주려고 3,700 개를 두 번 읽는다

- 날짜: 2026-10-19 (진행 중 — 원인·선택지 실측까지 끝, 해결 적용·검증은 아직)
- 대상: `GET /v1/pois?bbox=…&lat=…&lng=…&sort=distance&limit=30` — 경로 탭 지도의 주변 편의시설 핀(iOS `RouteGuide.swift:185`,
  Android `RouteEditorView.kt:591`)
- 환경: DEV DB(RDS db.t4g.medium, PostgreSQL 17.9, PostGIS 3.5.6), 편의시설 910,394 개. 측정은 부하 없는 상태에서 DB 안 시간(`EXPLAIN ANALYZE`).
- 코드: 쿼리는 `services/scene-api/src/main/java/com/mz2az/scenetrip/sceneapi/poi/PoiStore.java` 의 `LIST_SQL`·`COUNT_SQL` 그대로.

## 0. 이 사례는 무엇인가 (처음 읽는 사람용)

부하 시험의 한계(stress) 시험 두 번(실험 [02](2026-10-18-02-한계-DB연결풀.md) v1, [07](2026-10-18-07-v2한계-상태점검.md) v2)에서 scene-api 1 대는
초당 약 560~600 요청에서 막혔다. 원인은 **DB 연결 풀(HikariCP) 10 개가 꽉 찬 것**이고, 그때 DB CPU 도 94% 였다. 연결 하나를 한 번 빌려 쓰는 시간이
평소 1.4ms → 막혔을 때 5.4ms 로 늘어(DB 가 바빠 쿼리가 느려짐) 상한이 더 내려갔다(실험 02 보충).

```
처리 상한 ≈ 연결 10 개 ÷ (요청 하나가 연결을 쥐는 시간)
```

연결을 늘리는 것(사례 B)은 DB CPU 가 이미 94% 라 효과가 작을 것으로 본다. 그래서 먼저 **연결을 쥐는 시간을 줄인다** — DB 시간을 가장 많이 쓰는
요청을 가볍게 한다. 막히기 전 구간의 DB 시간 비중 1 위가 이 요청이다(실험 02 22.1%, 실험 07 16.3%, 요청 하나 DB 시간 약 12ms).

**성과 지표는 「응답이 몇 ms 빨라졌나」 가 아니다.** 부하 없을 때 이 요청은 수십 ms 라 사용자가 느끼지 못한다. 지표는 **같은 서버·같은 연결 10 개로
받을 수 있는 최대 요청 수**, 같은 부하에서의 **DB CPU**, 연결 한 번 쓴 시간이다.

## 1. 실행 계획 — 무엇에 시간을 쓰나

명동~시청 영역(경도 126.97~126.99, 위도 37.555~37.570 — 시나리오와 같은 0.02°×0.015°, 영업 중 편의시설 **3,700 개**), 원본 테이블:

```
Limit 30
 └ Sort (거리순, top-N heapsort)             ← ③ 3,700 개 전부 거리 계산·정렬해서 30 개
    └ Hash Left Join (촬영지 연결)
       └ Bitmap Heap Scan on poi  rows=3700  ← ② 저장 칸(8KB 페이지)에서 행 꺼내기
            Heap Blocks: exact=3370               3,700 행에 페이지 3,370 개
          └ Bitmap Index Scan (poi_geom_geometry_idx)  ← ① 위치 색인: 약 1ms
```

| 단계 | 시간(6 회 안정값) | 뜻 |
| --- | --- | --- |
| ① 색인으로 영역 안 찾기 | 약 1ms | 색인은 잘 탄다 |
| ② 페이지에서 꺼내기 | 약 5~6ms | 페이지 3,370 개(약 27MB)를 훑는다 |
| ③ 정렬·연결 붙이기 | 약 4~5ms | 3,700 개를 정렬해 30 개만 쓴다 |
| 목록 쿼리 | 약 13ms | |
| **개수 쿼리**(`total`) | 약 6ms | ②를 처음부터 한 번 더 |

**왜 페이지가 많나 — 저장 순서가 흩어져 있다.** 페이지 하나에 편의시설 약 18 개(복사본 기준)가 들어가니 3,700 개는 이상적이면 약 200 페이지인데
3,370 페이지를 읽었다 — 페이지 하나에서 평균 1 개 남짓만 쓴다. 같은 동네 편의시설이 여러 페이지에 흩어져 있다.

**왜 흩어졌나(추정)**: DEV 의 `poi` 통계가 insert 910,394 · update 909,843(2026-10-16). 적재가 넣은 뒤 모든 행을 한 번씩 고쳐 썼다. PostgreSQL 은
고친 행을 제자리에 덮지 않고 새 버전을 빈 곳에 쓴다(MVCC) — 그래서 행이 고친 순서대로 흩어지고, 테이블 파일도 397MB 로 복사본(207MB)의 두 배다
(빈 공간이 절반).

## 2. 정정 — 시나리오가 실제 앱과 다른 요청을 보냈다

시나리오 v1·v2 는 `GET /pois?bbox=…&limit=30` — **기준점 없이** 보내 서버 기본값인 **이름순**으로 정렬됐다. 실제 두 앱은 화면 중심(`lat`·`lng`)과
`sort=distance` 를 같이 보낸다(계약: 「가운데부터 채우지 않으면 자료에 먼저 적힌 동네가 상한을 다 먹는다」). 같은 영역에서 재면 두 모양 모두
3,700 개를 꺼내 정렬하는 같은 계획이고 시간도 비슷했다(이름순 약 11ms, 거리순 약 13~14ms). 그래서 실험 02·07 의 결론은 그대로다. **검증 시험은
시나리오를 앱과 같은 모양으로 고쳐서 돌린다.**

## 3. 선택지와 판단

### 처음 떠올린 넷
| | 무엇 | 줄이는 일 | 계약 변경 |
| --- | --- | --- | --- |
| ① 동네끼리 모아 저장(클러스터링) | 지도에서 가까운 행끼리 같은 페이지에 들어가게 테이블을 다시 쓴다(`CLUSTER` 또는 지오해시 순) | ②(목록·개수 둘 다) | 없음 |
| ② 가까운 것부터 30 개 | PostGIS 위치 색인의 근접 검색(KNN, `<->`)으로 가까운 순으로 꺼내다 30 개에서 멈춘다 | ③과 대부분의 ② (목록만) | 없음 |
| ③ 개수 빼기 | `total` 을 계약에서 뺀다 | 개수 쿼리 | **있음** |
| ③' 한 번에 세기 | 목록 쿼리에 `count(*) OVER ()` 를 붙여 개수를 같이 센다 | 개수 쿼리, 연결 빌리기 2 → 1 | 없음 |

### 판단 기록
1. **「total 은 앱이 『더 확대하세요』 에 쓴다」 → 사실이 아니었다.** 계약 설명에 그렇게 적혀 있었으나 두 앱 코드는 `items` 만 읽는다(위 두 줄).
   처음엔 계약 문장을 확인 없이 믿었다.
2. **③(개수 빼기)은 하지 않는다.** 지금은 쓰는 곳이 없지만 편의시설 이름 검색(`q`, MZ2AZ-283)이 예정돼 있고 검색 목록은 전체 개수가 필요할 수
   있다(페이지 번호·「결과 ○건」). 계약에서 뺐다가 다시 넣는 비용이 크다. 또 생성된 앱 클라이언트가 `total` 을 필수로 읽어 서버만 빼면 응답 해석이
   깨질 수 있다.
3. **③'(한 번에 세기)와 ②(가까운 것부터 30 개)는 함께 못 쓴다.** 개수를 세려면 3,700 개를 다 봐야 해서 30 개에서 멈출 수 없다. 그래서 둘 중
   하나 — **A안 = ① + ③'**, **B안 = ① + ② + 개수 쿼리 따로** — 를 실측으로 고르기로 했다.
4. **①은 두 안 모두에 들어간다** — 개수 쿼리도 ②단계(페이지 꺼내기)라 같이 줄어든다.

## 4. 실측 — 원본을 건드리지 않고 복사 테이블로

### 방법
- DEV DB 에 시험 스키마 `lab_mz2az502` 를 만들고(마이그레이션 역할 `app_migrate` — 앱 역할 `app_runtime` 은 만들 권한이 없다) `poi` 를 복사했다.
  색인은 원본과 같은 위치 색인 둘(geography GiST, geometry 식 GiST)과 기본 키. 번역·촬영지 연결 표는 원본을 그대로 붙인다.

  | 테이블 | 만든 법 | 크기 |
  | --- | --- | --- |
  | `orig` | 원본 `public.poi` | 397MB |
  | `plain` | `ORDER BY id` 로 복사 — **빈 공간만 없애고 순서는 동네와 무관** (대조군) | 207MB |
  | `geohash` | `ORDER BY ST_GeoHash(geom::geometry, 10)` 로 복사 | 207MB |
  | `cluster` | 복사 뒤 `CLUSTER … USING (geom::geometry) GiST` | 207MB |

- 쿼리는 앱과 같은 모양(거리순, 화면 중심 = 영역 가운데, `ko`), 준비된 문장(`PREPARE`)으로. 영역은 명동 1 곳 + 서울 안 무작위 40 곳(경도
  126.85~127.15, 위도 37.45~37.65, 0.02°×0.015°, 시드 502 — 시나리오와 같은 크기). 한 번 데워 둔 뒤 다시 잰 값(운영도 캐시가 데워져 있다).
- 「지금 방식」 은 코드대로 **목록이 30 개 미만이면 개수 쿼리를 건너뛴다**(41 곳 중 37 곳이 30 개를 채웠다).
- 시간 = 계획 + 실행(DB 안). 버퍼 = 읽은 8KB 페이지 수(색인 포함).

### 읽은 것
1. **모아 저장하면 읽는 페이지가 30 분의 1 로 준다** — 명동 6,869 → 약 220. 대조군 `plain`(빈 공간만 없앰)은 개수 쿼리가 여전히 2,942 페이지 →
   줄어든 것은 **순서** 덕이다. 지오해시 순과 `CLUSTER` 는 거의 같다.
2. **A안이 진다** — 페이지는 적게 읽지만(191) 명동 11.1ms. 3,700 개 모두의 거리를 계산하고 정렬하는 일(CPU)이 남기 때문이다. B안은 가까운 30 개만
   거리를 계산한다.
3. **B안이 이긴다** — 명동 20.5ms → **3.2ms(약 6 배)**, 41 곳 p95 13.4 → 5.1ms. 쿼리는 둘(연결을 두 번 빌린다)이지만 둘 다 짧아 연결을 쥐는 시간
   합이 A안보다 작다.
4. **덤 — 플래너가 계획을 바꿨다.** 원본에서는 가까운 순 꺼내기(KNN)를 안 고르고 전부 정렬했는데, 복사본에서는 같은 SQL 로 스스로 KNN 을 골랐다.
   테이블이 작아지고 통계가 바뀐 결과로 보인다(SQL 을 고치지 않고도 ②가 따라온다). 원본을 정리한 뒤에도 같은 계획을 고르는지는 적용 때 확인한다.

### 왜 복사본에서는 DB 가 스스로 「가까운 순 꺼내기」 를 골랐나 (보충 2026-10-19)
SQL 은 「무엇을」 만 말하고(영역 안·영업 중·거리순·30 개) 「어떻게」 는 플래너가 예상 비용으로 고른다. 같은 SQL 의 두 계획을 강제로 바꿔 가며 예상 비용과
실제 시간을 쟀다(명동, `enable_bitmapscan`·`enable_sort`·`enable_indexscan` 으로 한쪽을 막고 `EXPLAIN`):

| 테이블 | 전부 꺼내 정렬 — 예상 / 실제 | 가까운 순 꺼내기 — 예상 / 실제 | 플래너 선택 |
| --- | --- | --- | --- |
| 원본 | **5,020** / 14ms | 7,934 / **102ms** | 전부 정렬 (맞는 선택) |
| cluster | 5,724 / — | **3,841** / 1.3ms | 가까운 순 (맞는 선택) |

**원본에서는 가까운 순 꺼내기가 실제로 느렸다.** 위치 색인만으로 가장 가까운 30 개를 꺼내는 쿼리(`ORDER BY geom <-> 점 LIMIT 30`)를 따로 재면:

| | geography 색인 크기 | geometry 색인 크기 | 가까운 30 개 꺼내기 | 읽은 페이지 |
| --- | --- | --- | --- | --- |
| 원본 | **124MB** | **73MB** | 14.5ms | 296 |
| plain (빈 공간 없앤 복사, 색인 새로 만듦) | 69MB | 36MB | 4.3ms | 126 |
| cluster (동네순 복사, 색인 새로 만듦) | 72MB | 36MB | **0.6ms** | 32 |

- 원본의 위치 색인은 새로 만든 것보다 **약 2 배 크다**. 넣기 91 만 번 뒤 고쳐 쓰기 91 만 번(HOT 아닌 갱신은 색인 항목도 새로 넣는다)으로 부풀고, 하나씩
  끼워 넣으며 자란 색인은 처음부터 한 번에 만든 색인보다 영역끼리 덜 묶인다(추정 — PostgreSQL GiST 의 일반 성질).
- 그래서 원본에서는 가까운 순 꺼내기의 예상 비용이 높았고 실제로도 느렸다 — 플래너는 양쪽 모두에서 맞게 골랐다. **복사본으로 바뀐 것은 플래너의 판단이
  아니라 테이블과 색인의 상태**다(테이블 50,864 → 26,491 페이지, 색인 절반, 동네순 저장).
- 정리하면 효과는 두 겹이다: ① 테이블·색인을 새로 써서 부푼 것을 없앤다(`plain` — 명동 20.5 → 9.9ms, 가까운 순 꺼내기가 쓸 만해짐) ② 동네순으로
  저장한다(`cluster` — 9.9 → 3.2ms, 개수 쿼리의 페이지도 2,942 → 158).

### 결정
**B안 — 동네끼리 모아 저장 + (지금 SQL 그대로) 가까운 순 꺼내기 + 개수 쿼리 따로.** 계약 변경 없음, SQL 변경 없음(①만으로 ②가 따라왔다).
③'(한 번에 세기)는 쓰지 않는다 — ②를 막아 오히려 느려진다.

## 5. 적용 시 고려

| 걱정 | 내용 | 대응 |
| --- | --- | --- |
| 정리 중 잠금 | `CLUSTER` 는 끝날 때까지 테이블을 **읽기도 막는다**. DEV 복사본(207MB)에서 `CLUSTER` 만 **약 16 초** — 그동안 지도 핀·편의시설 상세가 멈춘다 | PRD 는 잠그지 않는 방법: 정렬한 새 테이블을 만들어 바꿔 끼우기, 또는 `pg_repack`(RDS 지원) |

| 플래너가 KNN 을 계속 고르나 | 통계에 따라 다시 전부 정렬로 돌아갈 수 있다 | 적용 뒤 같은 `EXPLAIN` 으로 확인. 통합 테스트의 `explainList`(순차 스캔 없음 확인)에 더할지 검토 |

## 6. 덤으로 찾은 위험 (지금은 안 터짐)
`PoiStore` 의 조건은 「값 IS NULL OR 조건」 꼴이다(조건을 안 준 요청을 한 SQL 로 표현). 같은 준비된 문장을 재사용하는 **일반 계획**
(`plan_cache_mode = force_generic_plan`)으로 실행하면 색인을 못 쓰고 91 만 개를 전부 훑어 **815ms**(명동). 지금은 DB 가 매번 값에 맞춘 계획을 세워
(실제 trace 25ms) 일어나지 않지만, 통계·버전이 바뀌면 일반 계획을 고를 수 있다. 사례 A 범위 밖 — 기록만 한다.

## 9.4 원인 — 가설과 증거
1. **느린 요청은 어디인가** → 1 초 넘은 목록 쿼리의 요청 주소(`url.query`)를 모으니 관악산·대모산·구룡산·북한산 자락·현충원 — **편의시설이 30 개도
   안 되는 화면**이었다.
2. **그 화면에서 DB 는 무엇을 했나** → 같은 영역·같은 언어로 `EXPLAIN ANALYZE`
   ([data/case-a/after-cluster-sparse-en-explain.txt](data/case-a/after-cluster-sparse-en-explain.txt)):
   `Index Scan using poi_geom_idx`(거리 목록표 — 화면 중심에서 가까운 순으로 꺼낸다) + `Rows Removed by Filter: 910387` — 네모 안 7 개를 찾고도 30 개를
   채우려 **네모 밖 91 만 개를 전부** 꺼내 보고 버렸다. 약 2.2 초, 페이지 82 만 장.
3. **왜 네모 밖을 계속 보나** → 쿼리가 두 조건을 **서로 다른 목록표(색인)** 로 맡긴다:

   | 쿼리 부분 | 목록표 |
   | --- | --- |
   | 「네모 안」 `p.geom::geometry && ST_MakeEnvelope(…)` | 네모 목록표 `poi_geom_geometry_idx`(평면 좌표) |
   | 「가까운 순」 `ORDER BY p.geom <-> o.point` | 거리 목록표 `poi_geom_idx`(구면, 미터) |

   거리 목록표로 꺼내면 네모는 「꺼낸 뒤 확인하는 조건」 일 뿐이라 네모가 어디서 끝나는지 모른다. 30 개가 차거나 목록이 끝나야 멈춘다.
4. **왜 그 화면에서 거리 목록표를 골랐나** → DB 가 네모 안 개수를 크게 잘못 예상했다(예상 544~1,298 개, 실제 7~28 개). 많다고 믿으면 「가까운 것
   몇십 개만 꺼내면 끝」 이라 거리 목록표가 싸 보인다. 산이 옆 도심과 같은 통계 칸에 묶여 평균만큼 있다고 본 것으로 추정(PostGIS 위치 통계의 칸
   단위 한계). 영어 요청이면 번역을 붙이는 비용 때문에 다른 방법이 더 비싸 보여 더 잘 고른다 — 느렸던 산 영역 다섯 곳: 한국어 1 곳, 영어 5 곳.
5. **왜 이 쿼리 모양이 되었나** → `GET /pois` 는 「반경 검색」(원)과 「네모 검색」 두 방식을 한 SQL 로 처리하고 가까운 순 정렬 한 줄
   (`ORDER_BY_DISTANCE`)을 같이 쓴다(2026-09-04, MZ2AZ-314). 반경 검색은 원과 정렬이 같은 거리 목록표라 이상적이지만, 앱이 실제로 쓰는 네모
   검색에서는 엇갈린다. 결과는 언제나 맞아(네모 안·가까운 순) 기능 시험은 통과했고, 통합 테스트의 실행 계획 검사는 「전체 순차 스캔이 없나」 만
   봤다(작은 시험 데이터에서는 늘 네모 목록표를 골랐다).

### 9.4.1 실행 계획으로 좁혀 간 과정 (정상 DB, 같은 쿼리를 방법별로 강제해 비교)

같은 쿼리를 두 화면 × 두 언어로, DB 가 고른 계획(자연)과 한쪽 방법을 막아 강제한 계획을 `EXPLAIN (ANALYZE, BUFFERS)` 로 나란히 쟀다
(`enable_indexscan = off` → 네모 목록표로 전부 꺼내 정렬, `enable_bitmapscan = off` → 거리 목록표로 가까운 순). 원본 출력:
[data/case-a/after-cluster-plan-choice-explain.txt](data/case-a/after-cluster-plan-choice-explain.txt).

| 화면 | 언어 | 네모 안 예상 / 실제 | 거리 목록표 — 예상 비용 / 실제 | 네모 목록표 — 예상 비용 / 실제 | DB 의 선택 |
| --- | --- | --- | --- | --- | --- |
| 대모산 근처 | 영어 | **584 / 7** | **9,552** / **2,210ms**(페이지 82 만) | 12,399 / **0.8ms** | 거리 ✗ |
| 대모산 근처 | 한국어 | 584 / 7 | (더 비쌈) | **2,681** / 0.4ms | 네모 ✔ |
| 명동 | 영어 | 1,399 / 3,700 | **4,525** / 1.8ms | 6,554 / 18.5ms | 거리 ✔ |
| 명동 | 한국어 | 1,399 / 3,700 | **4,040** / 1.0ms | 5,430 / 8.8ms | 거리 ✔ |

**어느 값이 실제로 일어난 일인가** — 표의 「DB 의 선택」 칸이 자연 계획(앱 요청에서 실제로 일어난 일)이고, 반대쪽 칸은 **비교하려고 강제한 값**
이다. 예: 대모산 근처·영어에서 DB 가 스스로 고른 것은 거리 목록표(2,210ms)이고, 네모 목록표 0.8ms 는 `enable_indexscan = off` 로 거리 목록표를
막고 돌린 값이다. 같은 화면이라도 **한국어는 DB 가 스스로 네모 목록표를 골랐다**(0.4ms). 이 강제 설정은 실험용이라 앱에 넣지 않는다 — 넣으면 거리
목록표가 맞는 명동 같은 화면까지 느려진다(표 4 행). 그래서 해결은 「DB 가 어느 쪽을 골라도 망하지 않는 쿼리 모양」 이어야 한다.

읽은 것:
1. **개수 예상이 크게 빗나간다** — 대모산 근처 584 개 예상, 실제 7 개(명동은 반대로 1,399 예상, 실제 3,700).
2. **거리 목록표의 예상 비용은 「30 개 모이면 멈춘다」 를 전제로 깎인 값이다.** 전체를 다 꺼내는 비용 162,128 에 「584 개 중 30 개만 쓴다」 비율을
   곱해 9,552 로 봤다. 실제로는 7 개뿐이라 멈추지 못하고 전체(162,128 쪽)를 다 치렀다 — 2,210ms.
3. **영어일 때만 뒤집힌다** — 네모 목록표 쪽 예상 비용이 한국어 2,681 → 영어 12,399(번역 표를 예상 584 행마다 붙이는 비용). 그래서 영어에서는
   거리 목록표(9,552)가 더 싸 보였다. 한국어는 네모 목록표가 싸 보여 맞게 골랐다.
4. **붐비는 화면에서는 거리 목록표가 실제로도 맞다** — 명동 1.0~1.8ms 대 8.8~18.5ms. 그래서 「항상 네모 목록표로 전부 정렬」 은 답이 아니다.

### 9.4.2 실행 계획 원문과 판단 — 대모산 근처 화면, 영어 (정상 DB)

화면: 네모 경도 127.0544~127.0744, 위도 37.4670~37.4820(대모산 근처, 시험에서 6.2 초 걸린 요청과 같은 자리), 화면 중심 (127.0644, 37.4745),
`Accept-Language: en`. 앱과 같은 준비된 문장(`PREPARE`)으로 `EXPLAIN (ANALYZE, BUFFERS)`. 원문 전체:
[data/case-a/after-cluster-plan-choice-explain.txt](data/case-a/after-cluster-plan-choice-explain.txt) 의 `sparse-en`.

**① DB 가 스스로 고른 계획 — 실제로 앱 요청에서 일어난 일** (핵심 줄만, 번역·연결 붙이기 줄은 뺐다)
```
Limit  (cost=297.73..9552.07 rows=30) (actual time=2208.960..2208.984 rows=7 loops=1)
  ...
    ->  Index Scan using poi_geom_idx on poi p  (cost=0.29..162128.15 rows=584) (actual time=10.381..2208.599 rows=7 loops=1)
          Order By: (geom <-> '…화면 중심…'::geography)
          Filter: ((closed_at IS NULL) AND ((geom)::geometry && '…네모…'::geometry))
          Rows Removed by Filter: 910387
          Buffers: shared hit=819779
Execution Time: 2209.653 ms
```

이 계획을 읽은 순서와 판단:

| 읽은 줄 | 뜻 | 판단 |
| --- | --- | --- |
| `Index Scan using poi_geom_idx` + `Order By: (geom <-> 화면 중심)` | **거리 목록표**로 화면 중심에서 가까운 순으로 하나씩 꺼냈다 | DB 가 「가까운 순 꺼내기」 를 골랐다 |
| `Filter: (… && 네모)` | 네모 조건이 **찾는 범위(Index Cond)가 아니라 꺼낸 뒤 거르는 조건(Filter)** 이다 | 거리 목록표는 네모 경계를 모른다 |
| `Rows Removed by Filter: 910387` · `Buffers: shared hit=819779` | 꺼냈다가 네모 밖이라 버린 행 91 만 개, 읽은 페이지 82 만 장 | **전국을 다 훑었다** — 이게 2.2 초의 정체 |
| 앞 괄호 `rows=584` 대 뒤 괄호 `rows=7` | 예상 584 개, 실제 7 개 | **개수 예상이 크게 틀렸다** |
| `Limit (cost=297.73..9552.07)` 대 Index Scan 의 `cost=…162128.15` | 끝까지 하면 162,128 점인데 「584 개 중 30 개만 쓰고 멈춘다」 고 보고 9,552 점으로 깎았다 | 30 개가 안 차 멈추지 못하고 162,128 점어치를 다 했다 |

**② 비교하려고 강제한 계획 — 거리 목록표를 막고(`SET enable_indexscan = off`) 같은 쿼리**
```
Limit  (cost=12016.39..12399.71 rows=30) (actual time=0.591..0.609 rows=7 loops=1)
  ...
    ->  Bitmap Index Scan on poi_geom_geometry_idx  (cost=0.00..16.66 rows=584) (actual time=0.085..0.086 rows=7 loops=1)
          Index Cond: ((geom)::geometry && '…네모…'::geometry)
Execution Time: 0.830 ms
```

| 읽은 줄 | 뜻 | 판단 |
| --- | --- | --- |
| `Bitmap Index Scan on poi_geom_geometry_idx` + `Index Cond: (… && 네모)` | **네모 목록표**로 네모를 찾는 범위로 썼다 | 네모 안 7 개만 꺼내고 끝 — 0.8ms |
| `Limit (cost=…12399.71)` | 예상 점수 12,399 | ①(9,552)보다 비싸 보여 DB 가 안 골랐다. 예상 584 행마다 번역(영어)을 붙이는 비용이 들어가서다 |

**③ 같은 화면, 한국어 — DB 가 스스로 고른 계획**: `Bitmap Index Scan on poi_geom_geometry_idx`, 예상 점수 2,681, 0.4ms. 한국어는 번역을
붙이지 않아 네모 목록표 쪽 점수가 낮아 맞게 골랐다 → **영어에서만 판단이 뒤집힌다.**

**④ 명동, 영어 — DB 가 스스로 고른 계획**: `Index Scan using poi_geom_idx`(거리 목록표), `rows=31` 만 꺼내고 1.8ms. 강제로 네모 목록표를 쓰면
`Bitmap Index Scan … rows=3700`, 18.5ms. → **붐비는 화면에서는 거리 목록표가 맞다.**

**종합 판단**: 거리 목록표 자체가 나쁜 게 아니라, 쿼리 모양 때문에 거리 목록표가 네모를 「찾는 범위」 로 못 쓰는 게 문제다(①의 `Filter`). 그래서
「네모 목록표로 네모 안에서 가까운 순」 — 네모가 `Index Cond` 에 들어가면서 가까운 순으로 꺼내는 — 쿼리 모양이 필요하다(§9.5 선택지).

**확정한 원인**: 네모 검색인데 「가까운 순」 이 네모를 모르는 목록표로 처리되는 쿼리 구조 — DB 의 개수 예상이 빗나가는 한산한 화면에서 네모 밖
전국을 훑는다.
