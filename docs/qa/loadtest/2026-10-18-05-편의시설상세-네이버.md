# 05. 편의시설 상세가 사람 1 명에도 0.7 초 — 네이버 링크 찾기가 매번 시간 초과까지 기다린다 (그리고 시험이 네이버를 가짜로 안 바꿨다)

- 날짜·시각: 2026-10-18 21:04 ~ 21:05 KST(12:04~12:05 UTC)
- 커밋: 서버 `07ec1c5`(DEV), 시나리오 v2 작성 중(편의시설 상세를 처음 넣었다)
- 환경: 실험 01~04 와 같다(DEV 시험 모드).

## 0. 무슨 시험인가 — 시나리오 v2 연기 확인(smoke)
**목적**: v2 에 새로 넣은 흐름(편의시설 상세·사진, 후기 읽기, 쓰기)이 도는지만 보는 1 분짜리 확인. 부하 시험이 아니다.
**건 부하**: 초당 1 흐름 1 분, 노트북 → DEV, 흐름 다섯(둘러보기·후기 읽기·담기·여행·쓰기). 둘러보기에서 지도 결과 중 하나를 70% 확률로 눌러
`GET /pois/{id}` → `GET /pois/{id}/photos`.

## 1. 경위
v2 연기 확인에서 확인 126/126 은 모두 성공했는데, 둘러보기 p95 합격선(500ms)이 **720ms** 로 깨졌다. v1 의 같은 흐름은 p95 50ms 였다 —
사람이 1 명인데 느리다는 건 부하가 아니라 요청 하나가 원래 느리다는 뜻이다.

## 2. 수치 (SigNoz, 15 분)
| API | 건수 | p50 | p95 | 최대 |
| --- | --- | --- | --- | --- |
| `GET /v1/pois/{poiId}` | 34 | **706ms** | 732ms | 780ms |
| `GET /v1/pois/{poiId}/photos` | 34 | 3.6ms | 5.5ms | 69ms |

느린 trace 셋을 열어 보면, 그 안의 DB 쿼리 7 개(편의시설·사진·상세·리뷰·`poi_naver` …)를 다 합쳐도 15~45ms 다.

## 3. 문제 정의
**편의시설 상세는 매번 약 0.7 초를 쓰는데, 그중 DB 는 0.05 초 이하이고 나머지는 네이버 응답을 기다리다 시간 초과로 포기하는 시간이다.**

## 4. 원인 — 가설과 증거
- 남는 시간 ≈ 700ms = 네이버 호출 대기 상한 `scenetrip.naver.timeout-ms: 700`(`application.yaml`).
- scene-api 로그(SigNoz): 같은 시각에 `네이버 검색 실패 — ResourceAccessException` 이 반복 — DEV 에서 네이버 검색(`bff-gateway.place.naver.com`)이 매번
  실패한다(연결·응답 시간 초과). PRD 에서는 같은 호출이 p50 193ms·p95 286ms 로 성공했다(n=27, 준비 일지 3).
- 편의시설 상세는 네이버 지도 링크(`naverPlaceUrl`)를 채우려고 응답 전에 네이버를 기다린다(ADR 0021).

## 5. 무엇을 뜻하나 — 둘
1. **시험 쪽 빈틈**: 「바깥 회사 서버는 전부 가짜」 로 정했는데 네이버를 빠뜨렸다 — 처음 설계 때 길찾기·챗봇·로그인만 봤고, 편의시설 상세가 네이버를
   부른다는 것을 놓쳤다. v1 은 편의시설 상세를 부르지 않아 드러나지 않았다. → 가짜 서버에 네이버를 더한다(PRD 실측 지연). 그 전까지의 v2 결과는 쓰지 않는다.
2. **서비스 쪽 위험(해결 단계 후보)**: 네이버가 느리거나 막히면 **모든 편의시설 상세가 0.7 초씩 늦어진다**. 기다리는 동안 DB 연결을 붙잡는지, 실패를
   저장해 다음엔 건너뛰는지는 코드로 확인한다(아래 6) — 붙잡는다면 실험 02 의 연결 풀 병목을 크게 키운다.

## 6. 코드로 확인한 것 (2026-10-18)

| 물음 | 답 | 근거 |
| --- | --- | --- |
| 요청 안에서 기다리나 | 그렇다 — 상세 응답을 만들다 네이버 링크를 찾는다 | `web/PoisController.java:96` → `NaverLinks.java:63` → `PoiCardFetcher.java:65,74` |
| 얼마나 | 한 번 최대 700ms, 못 찾으면 「이름 + 시도 시군구」 로 재검색 — 최대 약 1.4 초(계약 「최대 1.5 초」). 첫 검색이 실패면 재검색 없이 끝 | `NaverPlaceClient.java:129-138`, `PoiCardFetcher.java:66-67` |
| **기다리는 동안 DB 연결을 잡나** | **잡지 않는다** — 트랜잭션 없이 문장마다 연결을 빌렸다 돌려준다(DB 조회 → 반납 → 네이버 대기 → 쓰기 때 새로 빌림). 가상 스레드라 기다림이 OS 스레드도 거의 안 쓴다 → **실험 02 의 연결 풀 병목을 키우지 않는다** | `PoiNaverStore.java:72-78,99-118`, `NaverLinks.java:55,84` |
| 결과를 저장하나 | 「찾음」·「못 찾음」 은 `poi_naver` 에 저장 → 다음부터 네이버를 안 부른다(유효기간 없음, 판정 규칙 판이 바뀔 때만 다시) | `NaverLinks.java:55-58,72-85`, `V14__poi_naver.sql` |
| **실패도 저장하나** | **안 한다** — 시간 초과·연결 실패·5xx 는 「다음에 다시 묻는다」. 403·429 일 때만 60 초 쉰다(파드마다 메모리) | `NaverLinks.java:59-69` |

**뜻하는 것**
- DEV(네이버가 늘 실패): 실패가 저장되지 않고 쉬지도 않아 **같은 편의시설을 다시 열어도 매번 최대 700ms**, 끝이 없다.
- PRD 에서 네이버가 느려지거나 막히면(시간 초과·5xx): 처음 여는 편의시설마다 **0.7~1.4 초**가 붙고, 부하가 오르면 같은 편의시설로도 네이버를 **동시에·횟수 제한 없이** 두드린다. DB 풀은 잠그지 않아 다른 API 까지 번지지는 않는다. 이미 저장된 편의시설은 영향 없음.
- 해결 후보: 실패도 짧게(예: 몇 분) 기억해 다시 묻지 않기, 링크 찾기를 응답 뒤로 미루기(먼저 답하고 뒤에서 채우기), 시간 초과 연속이면 잠시 쉬기(차단기).

## 7. 남은 것
- 시험 쪽: 가짜 서버에 네이버를 더했다(`POST /naver/graphql`, PRD 실측 지연 193/290ms). 가짜는 편의시설 좌표를 몰라 scene-api 판정(80m 안)에서 대부분 「못 찾음」 이 된다 — 처음 여는 편의시설마다 호출 2 번(재검색)과 DB 쓰기 1 번. 진짜로 찾은 경우와 호출 1 번 차이다(한계).
