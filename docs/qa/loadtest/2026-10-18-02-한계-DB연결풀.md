### 가설 1 — DB 연결 풀(HikariCP 기본 10)에서 기다린다 → **맞음**

| 시각 | 연결을 기다리는 요청(pending) | 풀 최대 | JVM CPU |
| --- | --- | --- | --- |
| ~10:32 | **0** | 10 | 15~19% |

- 계산: 연결 10 개 × (1 초 ÷ 연결 한 번 쓰는 시간 약 17ms) ≈ 초당 약 590 → 실측 최대 560~580 과 맞다.

  `application.yaml` 의 가상 스레드 주석이 이미 「병목이 DB 커넥션 풀로 옮겨 간다」 고 적어 두었다.
- CPU 는 아니다: JVM CPU 최대 38%, scene-api 노드 CPU 최대 65%.

## 정정 (2026-10-18, 실험 03 뒤)

§2 의 「실패 18%(대부분 60 초 시간 초과)」 는 틀렸다. 실험 03(급증)에서 gateway(nginx) 로그의 `1024 worker_connections are not enough` 를 보고
같은 구간의 ALB 지표를 다시 봤더니, 이 시험에서도 **ALB 가 5xx 89,876 건**(502 82,302 · 503 7,515 · 504 59)을 냈다 — 분당 10:33 1,919 →
10:37 7,693 → 10:40 24,493. scene-api 5xx 는 0 이므로, **실패의 대부분은 gateway 의 연결 한도(1,024)가 차서 ALB 가 돌려준 502·503** 이고 60 초
시간 초과는 일부다. 원인 사슬: DB 연결 풀 대기(§4) → 처리 중 요청이 쌓임 → gateway 연결 한도 → ALB 5xx. 자세히는 [실험 03](2026-10-18-03-급증-gateway연결.md).

## 보충 (2026-10-19) — 근거를 다시 쟀다

### 「연결 하나 17ms」 의 근거 — 처음 적은 값은 거꾸로 계산한 것이었다
§4 의 「연결 한 번 쓰는 시간 약 17ms」 는 실측이 아니라 「연결 10 개 ÷ 최대 처리량 580」 을 거꾸로 푼 값이라 근거가 될 수 없다. SigNoz 의 연결 풀
지표(`db.client.connections.use_time`·`wait_time` — 연결을 **빌린 횟수**와 **빌려 쓴 시간**, 누적값을 분마다 차분)로 다시 쟀다:

| 시각(UTC) | 초당 연결 빌림 | 한 번 빌려 쓴 시간(평균) | 평균으로 쓰고 있던 연결(10 개 중) | 빌리려고 기다린 시간(평균) |
| --- | --- | --- | --- | --- |
| 10:24~10:26 | 380~387 | 1.4~1.5ms | 0.5~0.6 | 0~0.3ms |
| 10:28~10:31 | 692~772 | 1.6~2.0ms | 1.1~1.5 | 0.2~1.6ms |
| 10:33~10:36 | 1,196~1,549 | 3.3~4.6ms | 3.9~7.1 | 20~49ms |
| 10:37~10:41 | 1,513~1,717 | **5.0~5.6ms** | **8.3~9.0** | **209~299ms** |

- 요청 하나가 연결을 **약 3 번** 빌린다(10:38: 초당 1,717 번 ÷ 초당 약 580 요청 = 2.96 — §4 의 「요청당 쿼리 3.1」 과 같다). 읽기 API 는 트랜잭션 없이
  **쿼리마다 연결을 빌렸다 돌려준다**.
- 그래서 막혔을 때 요청 하나가 연결을 쥔 시간 = 3 번 × 5.0~5.6ms ≈ **15~17ms** → 연결 10 개로 초당 약 600~660 요청이 이론 상한, 실측 최대 560~580 과
  맞는다(평균 8.3~9.0 개가 늘 쓰이고 있었다 — 사실상 꽉 참).
- **새로 보인 것**: 한 번 빌려 쓴 시간이 평소 1.4ms → 막혔을 때 5.4ms 로 **약 3.5 배** 늘었다. 같은 때 RDS CPU 가 94% 였다 — DB 가 바빠져 쿼리 하나하나가
  느려졌고, 그만큼 연결을 오래 쥐어 풀 상한이 더 내려갔다. §4 의 「쿼리 자체가 느려졌나 → 아니다」 는 **요청 전체 시간(0.6 초)에 견주면** 쿼리
  시간(14ms)이 작다는 뜻이고, 쿼리 시간도 평소의 약 3 배가 됐다. → 해결에서 **쿼리 일을 줄이면(사례 A) 연결을 쥔 시간이 줄어 같은 풀 10 개로도
  상한이 올라간다**.

### 연결 대기가 약 500 에서 멈춘 까닭 — gateway 연결 한도
연결 대기(pending)가 10:37~10:41 내내 492~498 에서 더 늘지 않았다. 사람이 그만큼만 온 것이 아니라 **gateway(nginx)가 scene-api 로 넘길 수 있는 요청
수의 상한**이다:
- gateway 의 nginx 는 `worker_processes` 를 적지 않아 기본 **1 개**이고 `worker_connections 1024`(`platform/helm/scenetrip/templates/config.yaml`) —
  nginx 전체가 동시에 연결 1,024 개.
- 요청 하나를 넘기면 연결을 **2 개** 쓴다(ALB 쪽 1 + scene-api 쪽 1) → 동시에 넘길 수 있는 요청은 약 512.
- scene-api 안에서는 그중 10 개가 연결을 쥐고 나머지 ≈ 500 이 줄을 선다 → 실측 492~498 과 맞는다. 넘치는 요청은 nginx 가 받지 못해 ALB 가 502·503 을
  냈다(위 「정정」, 실험 03).
