# 11. 사례 B — DB 연결 풀 → gateway 연쇄 (진행 중)

- 날짜·시각: 2026-10-20 00:09~00:54 KST(2026-10-19 15:09~15:54 UTC)
- 환경: DEV 시험 모드, gateway·scene-api·trip-guide 각 1 대, RDS db.t4g.medium(`max_connections` 400). 서버 `704c4b2`(사례 A 수정 + SigNoz 안정화 포함).
- 시나리오: [v3](scenario.md) `PROFILE=stress`, 흐름 여섯 전부 — 사례 A 검증과 같다. 러너 EC2, k6 v2.3.0.

## 0. 무슨 문제인가
DB 연결 풀(HikariCP, 최대 10 개)이 차면 요청이 scene-api 안에서 줄을 서고, 줄이 gateway(nginx, 동시 연결 1,024 = 넘길 수 있는 요청 약 512 개)를 넘치면
ALB 가 502·503 을 낸다(실험 02·03). 사례 A 뒤에도 초당 200 흐름 단계에서 연결 대기(평균 200ms 대)와 ALB 5xx 가 남았다(실험 10 §9.7).

## 1. 먼저 — SigNoz 안정화 (PR #348)
부하 중 SigNoz 가 생존 점검 실패로 재시작돼 가장 바쁜 몇 분의 기록이 비던 문제(실험 10 §9.7.1)를 DEV 에서 고쳤다: ClickHouse CPU 최소 필요량 250m → 1500m·
점검 3s/1s/10 → 10s/5s/6, 수집기 100m → 500m·실패 허용 6 → 12. 배포 뒤 ClickHouse 가 새 노드(c5a.large)로 혼자 옮겨졌다.

**확인**: 아래 두 시험(약 45 분) 동안 SigNoz 부품 재시작 **0 회**, scene-api trace 수가 분마다 ALB 정상 응답 수와 맞는다(빈 분 없음). ClickHouse 노드 CPU 는
최대 100% 까지 올랐다 — 점검을 늦춘 덕에 버틴 것이라 여유가 넉넉한 것은 아니다.

## 2. 측정 — 연결 10(기준) → 20
연결 수만 바꿨다: `kubectl set env deploy/scene-api SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE=20`(DEV 임시 — 다음 배포·시험 모드 재설정 때 사라진다).
지표에서 풀 최대값이 20 이 된 것을 확인했다(쓰는 연결 최대 18.4).

## 3. 읽은 것 — 이번 측정은 **앱 노드 CPU 가 섞여** 연결 풀만의 효과로 읽을 수 없다
1. **기준이 지난번보다 낮다** — 같은 연결 10 인데 초당 약 534(실험 10 의 고친 뒤 두 번은 667·688). 달라진 것은 배치다: SigNoz 안정화 배포 뒤 수집기
   (otel-collector, CPU 0.5 신청)와 ClickHouse 운영자가 **scene-api·gateway·trip-guide·가짜 바깥 서버와 같은 c5a.large(CPU 2 개)** 에 놓였고, 그 노드 CPU 가
   94~95% 였다(실험 10 고친 뒤 시험 때 같은 앱 노드 최대 85%).
2. **연결 20 은 +8% 뿐** — DB CPU 는 74% 로 여유가 있는데 연결을 한 번 쓰는 시간이 5ms → 10ms 로 두 배가 됐다. 연결 수가 늘어도 앱 노드 CPU 가 꽉 차 쿼리를
   보내고 결과를 받는 쪽(scene-api)이 느려져, 연결을 쥐는 시간만 길어진 것으로 본다(추정 — 앱 노드 CPU 와 함께 움직임).
3. 그래서 지금 DEV 에서 처리량을 막는 것은 **DB 도 연결 풀도 아니라 앱 노드 CPU** 일 가능성이 크다. 연결 풀 실험을 다시 하려면 앱 노드를 먼저 갈라야 한다.
