# 11. 사례 B — DB 연결 풀 → gateway 연쇄: 연결을 늘려도 DB CPU 에 막힌다 (진행 중)

- 날짜·시각: 2026-10-20 00:09~00:54 KST(2026-10-19 15:09~15:54 UTC)
- 환경: DEV 시험 모드, gateway·scene-api·trip-guide 각 1 대, RDS db.t4g.medium(`max_connections` 400). 서버 `704c4b2`(사례 A 수정 + SigNoz 안정화 포함).
- 시나리오: [v3](scenario.md) `PROFILE=stress`, 흐름 여섯 전부 — 사례 A 검증과 같다. 러너 EC2, k6 v2.3.0.

## 0. 무슨 문제인가
DB 연결 풀(HikariCP, 최대 10 개)이 차면 요청이 scene-api 안에서 줄을 서고, 줄이 gateway(nginx, 동시 연결 1,024 = 넘길 수 있는 요청 약 512 개)를 넘치면
ALB 가 502·503 을 낸다(실험 02·03). 사례 A 뒤에도 초당 200 흐름 단계에서 연결 대기(평균 200ms 대)와 ALB 5xx 가 남았다(실험 10 §9.7).

## 1. 먼저 — SigNoz 안정화 (PR #348)
부하 중 SigNoz 가 생존 점검 실패로 재시작돼 가장 바쁜 몇 분의 기록이 비던 문제(실험 10 §9.7.1)를 DEV 에서 고쳤다: ClickHouse CPU 최소 필요량 250m → 1500m·
점검 3s/1s/10 → 10s/5s/6, 수집기 100m → 500m·실패 허용 6 → 12. 배포 뒤 ClickHouse 가 새 노드(c5a.large)로 혼자 옮겨졌다.

**확인**: 아래 두 시험(약 45 분) 동안 SigNoz 부품 재시작 **0 회**, scene-api trace 수가 분마다 ALB 정상 응답 수와 맞는다(빈 분 없음). ClickHouse 노드 CPU 는
최대 100% 까지 올랐다 — 점검을 늦춘 덕에 버틴 것이라 여유가 넉넉한 것은 아니다.

## 2. 측정 — 연결 10(기준) → 20
연결 수만 바꿨다: `kubectl set env deploy/scene-api SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE=20`(DEV 임시 — 다음 배포·시험 모드 재설정 때 사라진다).
지표에서 풀 최대값이 20 이 된 것을 확인했다(쓰는 연결 최대 18.4).

## 3. 읽은 것 — 이번 측정은 **앱 노드 CPU 가 섞여** 연결 풀만의 효과로 읽을 수 없다
1. **기준이 지난번보다 낮다** — 같은 연결 10 인데 초당 약 534(실험 10 의 고친 뒤 두 번은 667·688). 달라진 것은 배치다: SigNoz 안정화 배포 뒤 수집기
   (otel-collector, CPU 0.5 신청)와 ClickHouse 운영자가 **scene-api·gateway·trip-guide·가짜 바깥 서버와 같은 c5a.large(CPU 2 개)** 에 놓였고, 그 노드 CPU 가
   94~95% 였다(실험 10 고친 뒤 시험 때 같은 앱 노드 최대 85%).
2. **연결 20 은 +8% 뿐** — DB CPU 는 74% 로 여유가 있는데 연결을 한 번 쓰는 시간이 5ms → 10ms 로 두 배가 됐다. 연결 수가 늘어도 앱 노드 CPU 가 꽉 차 쿼리를
   보내고 결과를 받는 쪽(scene-api)이 느려져, 연결을 쥐는 시간만 길어진 것으로 본다(추정 — 앱 노드 CPU 와 함께 움직임).
3. 그래서 지금 DEV 에서 처리량을 막는 것은 **DB 도 연결 풀도 아니라 앱 노드 CPU** 일 가능성이 크다. 연결 풀 실험을 다시 하려면 앱 노드를 먼저 갈라야 한다.

## 4. 앱 노드를 가른 뒤 다시 — 연결 10 → 20 → 30 (2026-10-20 01:44~02:54 KST)

PR #349: 시험 모드에서만 scene-api CPU 최소 필요량 1500m, 연결 풀 크기는 시험 모드 값(`LOADTEST_DB_POOL_SIZE`)으로. 배포 뒤 scene-api 가 **새 노드에
혼자** 놓였다(gateway·trip-guide·가짜 바깥 서버·수집기는 다른 노드). 시험마다 `just loadtest-mode dev on` 으로 연결 수만 바꿨다(연결 30 은 시험 시작
전 교체 완료 확인). 세 시험 동안 SigNoz 재시작 0.

### 읽은 것
1. **앱 노드를 가르니 기준이 올라갔다** — 연결 10 이 초당 약 534(노드 경합) → 711. 사례 A 검증의 667·688 보다도 높다. 실험 11 첫 측정의 낮은 값은 노드
   경합 탓이 맞았다.
2. **연결을 3 배로 늘려도 처리량은 +1~2%** — 초당 연결 빌림은 세 경우 모두 약 2,350 으로 같다. 늘어난 것은 연결을 한 번 쥐는 시간(3.7 → 7.9 → 12.1ms)
   뿐이다. 「동시에 쓰는 연결 = 초당 빌림 × 한 번 쥐는 시간」 이 8.6 → 18.5 → 28.5 로 풀 크기만큼 찼다 — DB 에 동시에 쿼리를 더 보내면 쿼리 하나하나가
   그만큼 느려진다는 뜻이다. DB CPU 가 88 → 93% 로 꼭대기에 있다.
3. **그래서 지금의 한계는 DB CPU(db.t4g.medium, CPU 2 개)다.** 연결 풀은 병목이 아니라 줄을 서는 자리일 뿐이다. 실험 02 에서 「풀만 늘리면 DB CPU 에
   막힌다」 고 예상했던 것이 사례 A 이후에도 그대로 맞았다.
4. **사용자가 보는 실패(ALB 5xx 약 2.2~2.5 만)는 연결 수로 줄지 않는다** — 줄(대기 400~500)이 gateway 한도를 넘치는 구조가 그대로다.

## 6. DB 일 줄이기 ① — 마지막 접속 시각 갱신을 한 시간에 한 번으로 (PR #351)

### 왜
연결 풀이 아니라 DB CPU 가 한계라(§4) DB 일을 줄인다. 쿼리별 DB 시간 1 위가 **계정을 확인하는 요청마다 하는 `last_seen_at` UPDATE**였다
(로그인 사용자 `app_user` + 비회원 기기 `user_device`, 합쳐 DB 일의 약 11%, 갱신 한 번 2.2·1.7ms — 같은 기본 키 읽기 0.5ms 의 3~4 배). 이 값은 마지막
이용 후 **1 년** 지난 비회원 정리(`GuestPurge`, 매일 04:05)에만 쓴다 — 시각 단위 정밀도가 필요 없다.

### 고친 것
`UserStore` 의 두 쿼리: 기기·계정은 언제나 읽어 그 값으로 판정(어느 계정·가입했나·살아 있나), `last_seen_at` 은 비었거나 한 시간 넘었을 때만 같은 문장의
데이터 변경 CTE 로 고쳐 쓴다(왕복 수 그대로). 테스트 먼저 — 「한 시간 안이면 시각 그대로, 판정 그대로(로그인 확인 true)」 3 개가 수정 전 실패.

### 같이 바꾼 시나리오 — v4
실제 앱은 상세 화면을 열 때마다 사용 기록(`POST /events`)을 보내는데 v1~v3 에 없었다 → v4 에 넣었다([scenario.md](scenario.md) v4). 그래서 이 측정은
v4 의 고치기 전·고친 뒤끼리만 견준다(v4 는 요청이 늘어 v3 숫자와 직접 견주지 않는다).

### 읽은 것
1. **같은 부하에서 DB 일은 줄었다** — 갱신 쿼리의 DB 시간이 거의 절반, 100 흐름 단계 DB CPU 가 약 10 점 내려갔다.
2. **기대(약 8% 감소)보다 작았다** — 새 쿼리도 한 번 1.5ms 를 쓴다(읽기 + 데이터 변경 CTE 를 매번 계획·실행). 단순 읽기 0.5ms 로 어림한 것이 틀렸다.
3. **가장 바쁠 때의 처리량은 거의 그대로(+2%)이고 ALB 5xx 는 오히려 조금 많다** — 시험마다 몇 % 흔들리는 범위(실험 10 의 같은 조건 두 번이 3% 차이)라
   이 변화만으로 「막히는 지점이 올랐다」 고 말할 수 없다. 꼭대기에서는 두 시험 모두 DB CPU 82%·연결 대기 약 200ms 로 같은 자리에 막혔다.
4. 결론: **효과는 「같은 부하에서 DB 를 덜 쓴다」 까지 확인, 「더 많이 받는다」 는 확인 못 함.** 남은 DB 상위(사진 목록+개수 약 11%, 작품 제목 9%,
   사용 기록 저장 7.6%, 촬영지 목록 검색 6~9%)를 더 줄여야 꼭대기가 움직일 것으로 본다.

덤: **사용 기록 저장(`INSERT … entity_view`)의 실제 비용**을 처음 쟀다 — DB 일의 7.6%, 한 번 3.0ms(앞서 1~2ms 로 어림).
