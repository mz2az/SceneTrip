## 2. 문제 정의
**① v2 는 v1(약 560)보다 이른 초당 약 370~490 요청에서 막힌다. ② 막히자 gateway·scene-api 의 상태 점검이 실패해, 바빠서 느린 서버가 「죽었다/준비 안 됨」 으로

### ② 상태 점검 실패 — 쿠버네티스 이벤트
| 시각(UTC) | 대상 | 이벤트 |
| --- | --- | --- |
| 13:28:14~13:28:34 | gateway | 준비 점검(`/healthz`) 실패 — **connection reset by peer**(연결 한도가 차 점검 요청도 못 들어감) |
| 13:30:32, 13:32:27~31 | gateway | 준비·**생존** 점검 실패(reset) |
| 13:35:40 | scene-api | 준비 점검(`/v1/actuator/health/readiness`) **14 회 실패 — 시간 초과** |
| 13:41:18~47 | gateway | 생존 점검 시간 초과(급증 시험, 실험 08) |

- gateway 준비 점검이 실패하면 쿠버네티스는 그 파드를 「준비 안 됨」 으로 뺀다 → gateway 가 1 대뿐이라 **잠깐이라도 받을 곳이 없어진다** → 13:28·13:32 의
  처리량 급락과 시각이 맞는다(ALB 의 대상 상태 지표는 1 분 최대가 0 이라 그 사이 빠짐은 잡히지 않았다 — 한계).
- scene-api 준비 점검이 시간 초과 — 점검이 DB 연결 줄(대기 460 개)에 같이 섰을 가능성이 크다(Spring 준비 상태에 DB 확인이 들어 있는지 해결 단계에서 확인).
  실패가 이어지면 scene-api 도 빠진다.
- 공통점: **바빠서 느린 것을 죽은 것으로 오판** — 점검이 실제 트래픽과 같은 줄(연결 한도·DB 연결)을 타서, 가장 바쁠 때 서버를 빼 버린다.
