## 정정 (2026-10-19) — 「처리량이 0 에 가깝게 떨어졌다」 는 틀렸다: SigNoz 가 trace 를 잃은 것이다

### 무엇이 틀렸나
§1 표의 13:28(초당 187)·13:32(초당 2)와 §2 문제 정의 ②의 「처리량이 오히려 0 에 가깝게 떨어진다」 는 **SigNoz 에 들어온 trace 수**로 계산한 값이었다.
ALB 가 센 정상 응답 수(`HTTPCode_Target_2XX_Count` — gateway 를 거쳐 scene-api 가 실제로 2xx 를 돌려준 수)와 견주니 그 분에 처리량은 떨어지지 않았다:

- SigNoz 의 DB 연결 풀 지표도 같은 말을 한다 — 13:28 에 초당 1,728 번 연결을 빌렸다(13:27 의 1,297 보다 많다). 13:33 은 지표가 비고 13:34 에 두 분 치가
  한꺼번에 들어왔다. **바쁠 때 scene-api 의 관측 데이터 내보내기(또는 SigNoz 수집기)가 일부를 버렸다** — 정확히 어디서 버렸는지는 확인하지 못했다.
- 다른 시험은 괜찮다: 실험 02(10:30~10:40)·08(13:39~13:44)·09 는 SigNoz trace 수가 ALB 와 몇 % 안에서 같다. **trace 손실은 이 시험의 13:28~13:35 에만** 있다.
  그래서 이 시험의 13:28 이후 SigNoz 수치(§1 표의 초당 요청, §「API 별 응답 시간」 단계 5 의 건수)는 **표본**으로만 읽는다 — 응답 시간 분포는 쓸 수 있지만
  건수·처리량은 ALB 를 본다.

### 고친 문제 정의
- ② 실제로 있었던 것: gateway·scene-api 의 상태 점검 실패(쿠버네티스 이벤트, §3 ②의 표 — 이 기록은 그대로 맞다)와 **13:29~13:30 ALB 정상 응답 약 12~19%
  감소**(분당 29,450 → 25,862 → 23,750, 같은 때 ALB 5xx 가 늘기 시작). 상태 점검 실패가 이 감소를 일으켰는지는 **증명하지 못했다**(분 단위라 몇 초짜리
  빠짐은 안 보인다). 「바쁨을 죽음으로 오판할 수 있는 구조」(점검이 실제 요청과 같은 줄을 탄다)는 위험으로 남기되, 이 시험에서 피해 크기는 재지 못했다.
- ① 「v1 보다 일찍 막혔다」 도 고친다. ALB 로 보면 **최대 처리량은 v1 과 비슷하다**(정상 응답 최대 v1 초당 약 570, v2 약 600). 다른 것은 **ALB 5xx 가 시작된
  때**다 — v1 은 100 흐름 단계에서 한 번 튀었다 사라지고(10:33 분당 1,919 → 10:34 3) 200 흐름 단계(10:37)부터 이어졌고, v2 는 100 흐름 단계(13:28)부터 줄곧 늘었다. 같은 단계에서 v2 가 요청을 더 많이 보냈기 때문으로 본다
  (흐름 시작 뒤 12 분째 v1 분당 25,242 · v2 29,450 — 둘러보기에 편의시설 상세·사진이 붙었다).
- 「요청 하나가 DB 에 시키는 일이 늘었다」 는 **요청 하나 기준으로는 아니다**. 막히기 전 요청 하나가 DB 연결을 쥔 시간: v1(10:29) 약 5.3ms, v2(13:23~13:24)
  4.9~5.7ms — 같다(연결 풀 지표: 평균으로 쓰고 있던 연결 ÷ 초당 정상 응답). v2 는 흐름 하나가 보내는 요청이 늘어 **같은 「초당 흐름」 에서 DB 일이 늘었다**.
  §3 ①의 「DB 시간 비중」 표는 v1(챗봇 없음)과 v2(챗봇 포함 — 챗봇은 대부분 바로 실패해 DB 를 거의 안 쓴다)의 조건이 달라 **비중끼리 견주면 안 된다**.
  비중은 「v2 안에서 무엇이 DB 를 많이 쓰나」 로만 읽는다.
