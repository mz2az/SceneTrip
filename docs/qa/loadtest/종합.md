## 3. 사례 A — 지도 POI 조회 (해결함)

원문: [실험 10](2026-10-19-10-사례A-지도POI조회.md) §9.

- **경위**: 한계 시험에서 DB 시간 1 위가 지도 조회. DB 를 정상(정리된) 상태로 만들고 같은 시험을 다시 돌리자 지도 조회의 1% 가 2~6 초씩 걸리며 DB 일의
  23% 를 차지했다(1 초 넘은 쿼리 288 번).
- **원인**(실행 계획): 쿼리가 「네모 안」 은 네모 색인(`poi_geom_geometry_idx`), 「가까운 순」 은 거리 색인(`poi_geom_idx`)에 맡긴다. 편의시설이 30 개
  미만인 화면(산·공원)에서 DB 가 개수를 많게 잘못 예상하면(예상 584, 실제 7) 거리 색인을 고르고, 네모는 꺼낸 뒤 거르는 조건이라 30 개를 못 채워 91 만 행을
  전부 훑는다. 영어 요청에서 특히(번역 붙이는 비용이 다른 방법을 비싸 보이게 함).
- **검토한 해결책**(DEV 실측, 66 곳 × 한국어·영어):

  | 방법 | 평균 | 최대 | 판단 |
  | --- | --- | --- | --- |
  | 지금 | 36~239ms | 2.4 초 | 함정 |
  | 항상 네모 색인으로 전부 정렬 | — | 명동 영어 18.5ms | 붐비는 곳이 무거워져 탈락 |
  | 거리 색인에 반경 상한 | — | 명동 영어 68ms | 탈락 |
  | 개수 먼저 보고 방법 고르기 | 2.8~4.7ms | 22.6ms | 쿼리 늘 둘, 탈락 |
  | 네모 색인 + 미터로 다시 정렬(후보 120) | 1.2ms | 1.6ms | 정확하지만 거리 정확도 불필요(사용자 판단) |
  | **네모 색인 + 위경도 거리 + 30 개만 미터 정렬** | **0.8ms** | **2ms** | **채택** |
  | (대조군) 거리 무시 | 0.6ms | 0.9ms | 거리 계산 비용은 +0.2ms 로 작다 |

- **해결**: PR #346 — 화면 네모 + 기준점 + 거리순 목록을 네모 색인 평면 KNN 으로, 고른 페이지만 미터 정렬(`distanceMeters` 오름차순 유지), 네모 전용 조건
  (일반 계획에서도 안전). 테스트 먼저(실패 확인 뒤 구현), 단위 839/839·통합 859/862·`just check`·CI 통과.
- **검증**(같은 v3 한계 시험, 두 번):

  | 지표 | 고치기 전 | 고친 뒤 1 차 | 고친 뒤 2 차 |
  | --- | --- | --- | --- |
  | 막히는 지점(ALB 초당 최대 정상 응답) | 약 497 | 약 667(+34%) | 약 688(+38%) |
  | DB CPU(초당 50 흐름 단계) | 54~81% | 25~37% | 27~36% |
  | 지도 조회 요청당 DB 시간 | 48.8ms | 3.5ms | 3.5ms |
  | 1 초 넘은 지도 조회 | 288 | 0 | 0 |
  | 둘러보기 p50(k6) | 152ms | 23ms | 19ms |
  | 실패율(k6) | 12.1% | 7.4% | 7.0% |

- **받아들인 대가**: 어느 30 개를 고르는지가 위경도 거리 기준(동서를 조금 멀게 봄). 결과는 언제나 네모 안이고 응답 순서는 미터 오름차순.
- **과정에서 틀린 것**(기록에 남김): 표 정리만으로 된다고 판단했다가 DEV 에서 오히려 13% 나빠졌다 — 실측을 한국어로만 했다. 「total 은 앱이 쓴다」 는
  계약 문장을 확인 없이 믿었다(앱은 안 읽는다). 시험 모드를 다시 켤 때 토큰 aud 를 잘못 넣어 한 번 다시 돌렸다.
