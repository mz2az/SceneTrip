# 부하 시나리오 설명서

실험 기록이 「어떤 부하였나」 를 이 문서의 **판(v1, v2 …)** 으로 가리킨다. 코드는 `tests/load/scenario.js` — 판을 올릴 때 이 문서에 새 절을 더하고
옛 절은 고치지 않는다(이전 실험을 다시 읽을 수 있게).

### 이 문서의 말 (보충 2026-10-19)
- **흐름**: 사람 한 명이 앱에서 하는 행동 한 묶음(예: 둘러보기 = 요청 6 개). 부하의 단위는 「초당 새로 들어오는 흐름 수」 다.
- **VU(가상 사용자)**: k6 가 흐름 하나를 돌리는 일꾼. 흐름이 느려지면 k6 가 VU 를 더 띄워 도착률을 지킨다(최대 2,000). VU 가 모자라 시작하지 못한 흐름은
  k6 결과에 「못 보낸 흐름(dropped)」 으로 남는다.
- **check**: k6 가 응답마다 「200 이 왔나」 를 보는 검사. 실패율은 실험마다 적은 대로 k6 의 `http_req_failed`(상태 코드가 4xx·5xx 거나 응답이 없는 요청의
  비율) 또는 흐름별 check 실패율이다. 담기의 409(이미 담김)는 성공으로 친다.
- **FLOWS**: 일부 흐름만 돌리는 옵션. **비중은 그대로 두고 뺀 흐름만큼 전체 도착률이 준다** — 예: v1 에서 챗봇(10%)을 빼면 「초당 200 흐름」 단계는 실제로
  초당 180 흐름이다.
- **분당 단위**: 코드는 도착률을 분당으로 적는다(`timeUnit: "1m"`, k6 가 소수 도착률을 받지 않아서). 아래 표는 읽기 쉽게 초당으로 적었다 — 코드 값 ÷ 60.
- 수치를 어디서 쟀는지는 [README 의 「읽는 법」](README.md#읽는-법--용어시스템-구성dev) 을 본다.

## v1 — 2026-10-18, 커밋 `72bded6`(FLOWS 옵션 `a527c59` 뒤)

### 부하를 거는 방식
- **도착률 기준**(k6 `ramping-arrival-rate`, 분당 단위): 「초당 몇 명이 새로 들어오나」 를 정한다. 서버가 느려져도 사용자는 계속 들어온다 —
  느려짐이 숨지 않는다. 가상 사용자(VU)는 필요한 만큼 늘어난다(최대 2,000).
- 흐름 하나 = 사람 한 명이 앱에서 하는 한 묶음의 행동. 흐름마다 **새 설치 ID**(비회원) — 사람마다 따로라 요청 한도(설치 ID 당 분당 60)에 안 걸린다.
- **생각하는 시간**: 단계 사이 1~3 초(균등 무작위) 쉰다.
- **언어**: 요청마다 `Accept-Language` ko 2/3 · en 1/3.
- **데이터 무작위**: 시작 전에 작품 128 · 촬영지 476 의 실제 번호를 API 로 모으고, 흐름마다 무작위로 고른다(캐시 착시를 줄인다).

### 흐름 넷과 비중(가정 — PRD 실사용자가 쌓이면 맞춘다)

| 흐름 | 비중 | 누가 | 요청 순서 |
| --- | --- | --- | --- |
| 둘러보기 | 60% | 비회원 | `GET /contents?limit=20&offset=0~99` → 쉼 → `GET /contents/{무작위}` → `GET /contents/{같은}/places` → 쉼 → `GET /search/suggestions?q=<도깨비·경복궁·부산·제주·카페·해변·궁·시장·공원·Seoul 중>&limit=8` → 쉼 → `GET /pois?bbox=<서울 경도 126.85~127.15·위도 37.45~37.65 안 무작위 0.02°×0.015° 상자>&limit=30` → 쉼 → `GET /places/{무작위}` (요청 6) |
| 담기 | 15% | 비회원 | `POST /cart/items {무작위 촬영지}` → 쉼 → `GET /cart` → 쉼 → `POST /favorites/contents {무작위 작품}` → `DELETE /cart/items/{같은}` (요청 4) |
| 여행 | 15% | 회원 | (처음 한 번 `POST /auth/google`) → `POST /courses {1일}` → 쉼 → `PUT /courses/{id}` 촬영지 1 곳 담기 → `PUT …/progress {active, 1일차}` → 쉼 → `POST /navigation/next-leg`(촬영지에서 북동쪽 약 6 km — 대중교통, **가짜 카카오**) → 쉼 → `DELETE /courses/{id}` (요청 5~6) |
| 챗봇 | 10% | 회원 | `POST /guide/chat` — 새 sessionId, 질문 셋 중 무작위(「근처 맛집 알려줘」 등), 위치 경복궁 근처. trip-guide → **가짜 Bedrock** 2 번(도구 쓰기 → 답) |

- 회원: 시험 회원 토큰 2,000 개(가짜 구글 키로 서명) 중 가상 사용자마다 하나를 잡아 **한 번 로그인하고 다시 쓴다**(사람처럼). 로그인은 진짜
  `POST /auth/google`(구글 공개키만 가짜).
- 여행 흐름은 끝에 코스를 지운다 — 실험을 거듭해도 DB 크기가 같게(실제 사용자는 지우지 않는다 — 한계).
- 바깥 가짜의 지연: LLM p50 2.6 초·p95 5.5 초, 카카오 p50 70ms·p95 500ms, 구글 공개키 120ms([계획](../../project/plans/load-test.md) PRD 실측).

### 합격선
둘러보기·담기 p95 < 500ms · 실패율 < 1%, 여행 실패율 < 1%, 챗봇 실패율 < 2%. 길찾기·챗봇은 가짜 지연(초 단위)이 들어가 응답 시간 합격선을 두지 않는다.

## v2 — 2026-10-18, 커밋 `9ac9e97`

v1 으로 실험 01~04 를 돌려 보니 빠진 것(글쓰기, 편의시설 상세, 토큰 갱신)과 시나리오의 흠(앞 요청이 실패해도 다음을 보내 가짜 4xx 연쇄)이 있었다.
v1 의 「부하를 거는 방식」·프로필·바깥 가짜 지연은 그대로다. 바뀐 것만 적는다.

### 바뀐 것
- **토큰 갱신**: 회원 요청이 `401 ACCESS_TOKEN_EXPIRED` 를 받으면 앱처럼 `POST /auth/refresh` 로 갱신하고 한 번 다시 보낸다(실험 04 끝의 401 이 이것).
- **실패하면 흐름을 멈춘다**: 앞 단계가 2xx 가 아니면 그 사람의 흐름을 거기서 끝낸다(실험 02 의 길찾기 409·장바구니 빼기 404 연쇄를 없앤다).
- **바깥 가짜에 네이버 추가**(실험 05) — *아래 「v2 정정」 으로 실제 시험에서는 링크 찾기를 꺼서 불리지 않았다*: 편의시설 상세의 네이버 링크 찾기 → 가짜 `POST /naver/graphql`(PRD 실측 p50 193ms·p95 290ms, 후보가 오는 비율 0.6).
  가짜는 편의시설 좌표를 몰라 scene-api 판정에서 대부분 「못 찾음」 — 처음 여는 편의시설마다 호출 2 번(재검색)·DB 쓰기 1 번, 다음부터는 저장된 결과.

### 흐름 여섯과 비중(가정)

| 흐름 | 비중 | 누가 | 요청 순서 |
| --- | --- | --- | --- |

| 여행 | 12% | 회원 | v1 과 같다(코스·담기·시작 중 실패면 멈춘다) |
| 챗봇 | 8% | 회원 | v1 과 같다 |

- 리뷰는 회원·촬영지마다 하나라 덮어쓰기로 쌓이지 않는다. 여행후기는 끝에 지운다 — 실험을 거듭해도 DB 가 커지지 않게(실제 사용자는 안 지운다 — 한계).
- 사진은 S3 가 진짜다(가짜로 바꾸지 않았다 — AWS 안이라 비용·한도 걱정이 적고 우리 인프라의 일부라서). 크기가 69 바이트라 실제 사진(수 MB)의 전송 부하는 재지 않는다(한계).

### v2 정정 — 실행 전 네이버 링크 찾기를 껐다 (2026-10-18, 커밋 뒤 기록)
- 사용자 결정: **편의시설 상세의 네이버 링크 찾기(ADR 0021)는 부하 시험에서 뺀다** — 비공식 바깥 호출이라 결과에 섞지 않는다. 시험 모드에서

### v1·v2 정정 — 지도 영역 조회가 앱과 다른 모양이었다 (2026-10-19, 실험 10)
- 둘러보기의 지도 영역 조회는 `GET /pois?bbox=…&limit=30` 만 보내 서버 기본값 **이름순**으로 받았다. 실제 앱(iOS·Android)은 화면 중심 `lat`·`lng` 와
  `sort=distance` 를 같이 보내 **가까운 순**으로 받는다. DB 가 하는 일은 같은 모양이라(영역 안 전부 꺼내 정렬) 실험 01~09 의 결론은 그대로지만,
  사례 A 의 검증 시험은 앱과 같은 모양으로 고친 판으로 이전·이후를 다시 잰다.

## v4 — 2026-10-20 (사용 기록 추가)

v3 와 **둘러보기의 사용 기록만** 다르다. 실제 앱(iOS `Analytics/UsageEvents.swift`·Android `analytics/UsageEvents.kt`)은 작품·촬영지·편의시설
**상세 화면이 열릴 때마다** `POST /events {type: view, entityType, entityId}` 를 보낸다(계약 「보내고 잊는다」 — 인기도 계산 재료). v1~v3 는 이 요청이
없어 실제보다 쓰기가 적었다.

| | v3 | v4 |
| --- | --- | --- |
| 작품 상세 뒤 | — | `POST /events` view·content |
| 편의시설 상세 뒤(70%) | — | `POST /events` view·poi |
| 촬영지 상세 뒤 | — | `POST /events` view·place |

- 응답을 보지 않고 흐름을 멈추지 않는다(앱과 같다). 둘러보기는 비회원이라 서버는 기록만 적고 계정 확인·마지막 접속 시각 갱신은 하지 않는다.
