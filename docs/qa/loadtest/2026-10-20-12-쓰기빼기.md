# 12. 쓰기를 빼면 처리량이 오르나 — 사용 기록·새 비회원 계정을 뺀 상한 시험

- 날짜·시각: 2026-10-20 14:15~15:01 KST(05:14~06:00 UTC), 두 번 연달아
- 환경: DEV 시험 모드, gateway·scene-api·trip-guide 각 1 대(scene-api 는 혼자 노드 — 실험 11 §4 와 같은 배치를 시험마다 확인), RDS
  db.t4g.medium, 연결 풀 10. 서버는 실험 11 §6·§7 과 같다(마지막 접속 시각 한 시간에 한 번, PR #351).
- 시나리오: [v4](scenario.md) `PROFILE=stress`(초당 흐름 5→25→50→100→200, 약 22 분), 흐름 여섯 전부. 러너 EC2, k6 v2.3.0.
- 결론: **쓰기 두 가지를 빼도 막히는 지점은 거의 그대로다.** 디스크 확정 대기는 줄었지만 그 자리를 읽기 CPU 가 채웠다. 쓰기를 비동기 커밋으로
  바꾸는 것은 처리량 대책이 아니다. 다음 대책은 읽기 CPU(언어별 이름 고르기, MZ2AZ-504)다.

## 0. 왜 했나 — 실험 11 §7 의 가설

실험 11 §7 에서 DB 의 활성 세션을 2 초마다 찍었더니 **37% 가 「쓰기를 디스크에 확정하기를 기다림」**(WalSync·WALWrite)이었다. 쓰기 쿼리 자체는
0.1ms 인데 앱 쪽에서 3ms 로 보였다. 디스크에 쓴 변경 기록(WAL)의 큰 몫은 둘이었다.

| 쓰기 | WAL 비중(실험 11 §7) | 무엇 |
| --- | --- | --- |
| 새 비회원 계정 만들기 | 29.5% | 시나리오가 흐름마다 새 설치 ID 를 써서 매번 「처음 설치한 사람」 이 된다 — **실제 앱보다 많다** |
| 사용 기록 저장(`POST /events`) | 약 23% | 상세 화면마다 한 줄 — 실제 앱도 보낸다 |

가설: 이 쓰기가 연결을 붙잡아 처리량을 막는다면, 「잃어도 되는 쓰기는 확정을 기다리지 않게(`synchronous_commit = off`)」 고칠 이유가 있다.
고치기 전에 **기능을 통째로 뺐을 때 처리량이 오르는지** 먼저 본다. 빼도 안 오르면 고칠 이유가 없다.

## 1. 방법 — 시나리오 스위치 두 개 (서버 코드는 그대로)

| 스위치 | 하는 일 |
| --- | --- |
| `NO_EVENTS=1` | 사용 기록(`POST /events`)을 보내지 않는다 |
| `INSTALL_POOL=2000` | 비회원 흐름(둘러보기·담기·후기 읽기)이 설치 ID 를 매번 새로 만들지 않고, 번호로 정한 2,000 개(모든 VU 공유) 중에서 고른다 → 계정은 처음 한 번만 생긴다. 회원 로그인은 남의 비회원 계정과 합쳐지지 않게 늘 새 설치 ID |

| 시험 | 스위치 | k6 |
| --- | --- | --- |
| ① 기준 `x-base` | 없음(= v4) | 05:14:58~05:36:08 UTC |
| ② 둘 다 빼기 `x-nowrite` | `NO_EVENTS=1 INSTALL_POOL=2000` | 05:38:25~05:59:38 UTC |

같은 날 기준을 다시 잰 이유: 같은 시험을 두 번 돌려도 막히는 지점이 3% 안팎 흔들린다(실험 10, 667·688). 효과가 작으면 바로 앞 기준과 비교해야 한다.

②는 사용 기록 요청 자체를 안 보내 요청 수가 준다. 그래서 「초당 요청 수」 만 보면 공정하지 않다 — **사용 기록을 뺀 성공 요청 수**, **DB 연결을 빌린 횟수**,
**같은 단계의 DB CPU** 를 같이 본다.

## 2. 결과

「단계」 값은 그 단계를 유지한 3 분(오르는 2 분 제외)의 분당 값 범위다.


| 지표 | ① 그대로 | ② 두 쓰기 빼고 | 출처 |
| --- | --- | --- | --- |
| 200 단계 성공 요청(사용 기록 제외, 분당) | 37,874~39,833(초당 **약 630~665**) | 37,444~42,542(초당 **약 625~710**) | SigNoz trace |
| 200 단계 ALB 정상 응답(분당, 사용 기록 포함) | 44,328~45,130 | 36,965~40,388 | ALB |
| 200 단계 DB 연결 빌림(초당) / 한 번 쓴 시간 | 2,148~2,201 / 4.0~4.1ms | 1,905~2,189 / 4.0~4.1ms | SigNoz 지표 |
| DB CPU — 25·50·100·200 단계 | 22~23 · 38~40 · 59~62 · 79~83% | 21~22 · 39 · 69~70 · 76~85% | CloudWatch |
| 200 단계 ALB 가 낸 5xx(분당) | 7,858~8,278 | 4,197~6,315 | ALB |
| WAL(디스크에 쓴 변경 기록) | 226MB | **150MB(−34%)** | pg_stat_statements |
| 활성 세션 — 디스크 확정 대기(WalSync + WALWrite) | **38.5%**(19.3 + 18.7 + 0.5) | **29.8%**(19.5 + 10.1 + 0.2) | pg_stat_activity 표본 |
| 활성 세션 — CPU 계산 중 | 55.1% | **62.1%** | 〃 |

- ①의 DB 쿼리 통계는 시험 시작 5 분 뒤(05:20 UTC)부터다. 시작 때 통계 초기화(`pg_stat_statements_reset`)가 권한 부족으로 실패해, 5 분 뒤 찍은 값과 끝 값의 차로
  셌다. 빠진 5 분은 초당 5~25 흐름 단계라 결론에 영향이 작다. ②는 ①의 끝 값과의 차다.
- ②에도 새 비회원 계정이 3,071 번 생겼다 — 회원 로그인(늘 새 설치 ID)과 풀 2,000 개의 첫 사용분이다.
- k6 흐름 수(시작된 흐름)는 ① 105,599 · ② 105,500 으로 같다(도착률을 정해 두는 시험이라 당연하다).

### 읽은 것

1. **막히는 지점은 그대로다.** 성공 요청은 +0~7%, 같은 시험의 흔들림(3% 안팎) 안팎이다. DB 연결 빌림이 초당 2,200 근처, 한 번 4ms 에서 두 시험 모두 멈췄다.
2. **디스크 확정 대기는 줄었지만 그 빈자리를 CPU 계산이 채웠다**(55% → 62%). 쓰기를 빼서 생긴 여유를 같은 시간에 더 많이 들어온 읽기가 바로 가져갔다 — 100
   단계 DB CPU 가 ② 쪽이 더 높은 것(69~70% 대 59~62%)도 같은 이유다(같은 시간에 끝낸 읽기 요청이 많았다).
3. 그래서 **쓰기는 지금 병목이 아니다.** 실험 11 §7 의 「대기 37%」 는 쓰기가 많아서 생긴 대기이지, 그것이 처리량의 천장은 아니었다. 천장은 DB 의 읽기 CPU
   (2 코어)다.

### 하나 — 100 단계에서는 차이가 보였다(한 번뿐)

| 100 단계 유지 3 분(괄호는 다음 단계로 오르기 시작한 분) | ① | ② |
| --- | --- | --- |
| ALB 가 낸 5xx(분당) | 496 → 1,258 → 2,097 (3,429) | 15 · 62 · 47 (74) |
| 연결 기다리는 요청 최대 | 309 | 22 |

①은 100 단계 후반에 흔들리기 시작했고 ②는 깨끗했다. 쓰기가 있으면 조금 일찍 흔들린다는 신호일 수 있지만 **시험 한 번이라 우연과 구분되지 않는다.**
확인하려면 같은 쌍을 한 번 더 돌린다.

## 3. 결론과 다음

- **고치지 않는 것**: 사용 기록·마지막 접속 시각의 비동기 커밋(`SET LOCAL synchronous_commit = off`). 기능을 통째로 빼도 처리량이 안 올랐으니, 확정을
  기다리지 않게 해도 안 오른다. 장애 때 기록을 잃는 대가만 남는다.
- **시나리오의 한계를 기록**: v4 는 흐름마다 새 비회원 계정을 만든다(WAL 의 30%). 실제 앱은 설치 ID 를 다시 쓴다. 다음 판에서 `INSTALL_POOL` 을 기본으로 할지
  정한다(스위치는 이 실험부터 시나리오에 있다 — [scenario.md](scenario.md) v4 스위치).
- **다음 대책은 읽기 CPU**: 실험 11 §7 의 DB CPU 상위 중 「번역 표를 통째로 부른 뒤 거르는」 쿼리 9 개(약 36%) — MZ2AZ-504. 작품 목록의 「버릴 카드까지
  촬영지 수 세기」 — MZ2AZ-505.
- **목표 부하**: 한계 시험은 막힐 때까지 올리므로 무엇을 고쳐도 마지막 단계에서는 CPU 가 찬다. 몇 명까지 버텨야 하는지는 MZ2AZ-506.
