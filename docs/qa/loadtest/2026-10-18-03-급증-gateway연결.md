## 3. 문제 정의
**갑자기 몰려 scene-api 가 느려지면, 처리 중인 요청이 gateway(nginx) 의 연결 한도 1,024 를 채워 새 요청을 받지 못하고 ALB 가 502·503 을 돌려준다.**
(scene-api 자체는 실패 없이 느려지기만 하고, 몰림이 끝나면 15 초 안에 회복한다.)

## 4. 원인 — 가설과 증거

### 가설 — nginx `worker_connections`(1,024) → **맞음**
- nginx 가 직접 「not enough」 를 4,568 번 남겼다.
- 요청 하나를 중계하면 연결 2 개(ALB 쪽 + scene-api 쪽)를 쓴다 → 동시에 처리 중인 요청 약 500 개에서 찬다. 그 시각 scene-api 앞 연결 대기가 499 —
  scene-api 가 느려진 만큼 nginx 에 요청이 오래 머물렀다.
- 연결을 못 받으면 ALB 는 대상에서 응답을 못 받아 502(대상 연결 끊김)·503 을 낸다 — ALB 의 5xx 는 15,518, 대상(nginx)이 낸 5xx 는 0.
- **실험 02 에도 같은 일이 있었다**: 같은 지표로 ALB 5xx 89,876 — 실험 02 에 정정을 덧붙였다.

### 원인 사슬
급증 → scene-api DB 연결 풀 대기(실험 02) → 응답이 느려져 nginx 에 요청이 쌓임 → nginx 연결 1,024 소진 → ALB 502·503.
뿌리는 실험 02 의 DB 쪽이고, nginx 연결 한도는 그 느려짐을 **실패로 바꾸는** 곳이다.

### 확인한 아닌 것
- scene-api 가 실패를 낸 것 아님(5xx 0). 시험 모드의 gateway IP 상한(2,000r/s·연결 4,000)도 아님 — 그 전에 nginx 전체 연결 1,024 가 찼다.
- 러너 아님 — 실험 02 와 같은 러너, 같은 수준.

## 보충 (2026-10-19)
- **1,024 는 nginx 전체 한도다**: `worker_connections` 는 worker 하나당 값인데, gateway 설정은 `worker_processes` 를 적지 않아 기본 **1 개**다
  (`platform/helm/scenetrip/templates/config.yaml`). 그래서 이 gateway 1 대가 동시에 쥘 수 있는 연결이 1,024 이고, 요청 하나를 넘기는 데 연결 2 개
  (ALB 쪽·scene-api 쪽)를 쓰므로 동시에 넘기는 요청은 약 512 다 — 실험 02 의 연결 대기가 약 500 에서 멈춘 것과 같은 까닭(실험 02 보충).
- 「15 초 만에 회복」 의 15 초는 **표의 칸 크기**(SigNoz 를 15 초 단위로 묶었다)다. 회복은 15 초 **이내** 라는 뜻이고, 몇 초인지는 이 해상도로 모른다.
