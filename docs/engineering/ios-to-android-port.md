# iOS 화면을 안드로이드로 옮길 때

검색 탭을 SwiftUI 에서 Compose 로 옮기며 실제로 걸린 함정들이다. 경로여정·커뮤니티·
마이페이지 탭을 옮길 때 같은 곳에서 다시 걸리지 않도록 남긴다.

> 왜 이런 문서가 필요한가 —
> [ADR 0002](../architecture/adr/0002-product-stack-spring-python-native-mobile.md) 가
> 네이티브 두 벌을 택하면서 **"두 앱이 어긋나지 않게 한다"** 를 스스로 검증 항목으로
> 걸었다. 그 값을 매일 치르는 자리가 화면이다.

---

## 1. 기준은 문서가 아니라 iOS 소스다

계획서와 지라는 **무엇을 하는가**를 정한다. **어떻게 보이는가**는 iOS 소스에만 있다.

검색 탭을 처음 옮길 때 계획서와 확정 동작 문서만 보고 만들었더니, 동작은 맞는데
"영 다른 앱" 이 나왔다. 색은 Material 기본(보라)이었고, 탭바는 통째로 빠져 있었고,
카테고리 칩 이름은 지어낸 것이었다.

**옮길 화면의 Swift 파일을 열고 한 줄씩 따라가라.** 그 파일의 주석에 이유가 적혀
있다 — 왜 시트가 48% 인지, 왜 하트가 아니라 체크인지, 왜 별칭을 뺐는지.

## 2. 치수를 비교할 때는 **밀도로 나눈 뒤** 비교한다

가장 비싸게 배운 것이다.

    iOS(iPhone 17 Pro)  3.0x     1206 × 2622 px = 402 × 874 pt
    Android(에뮬레이터)  2.625x   1080 × 2400 px = 411 × 914 dp

**같은 논리 크기도 픽셀로 재면 12.5% 달라 보인다.** 대조 검사 한 라운드가 픽셀을
그대로 비교한 표를 냈고, 그것을 믿고 "안드로이드가 하나같이 작다" 로 읽어 핀·버튼·
행 높이를 전부 키웠다가 다음 라운드에 정확히 반대로 뒤집혔다.

지도 핀이 교과서적 예다 — 두 기기의 비트맵은 **정확히 같은 80×119 px** 이었는데
`69×102 vs 79×117` 로 적혀 있었다.

## 3. 숫자를 옮기지 말고 **그 숫자가 뜻하는 것**을 옮긴다

iOS 의 `BottomSheet(topInset: 108)` 에서 108 은 **iOS 검색바가 덮는 높이**다.
안드로이드 검색바는 높이도 다르고 상태바와의 관계도 달라서 108 을 그대로 쓰면 맞지
않는다. 그렇다고 25 를 깎는 것도 답이 아니다 — 그 자리를 **네 번** 오갔다.

값이 어긋나면 먼저 묻는다. **이 숫자는 무엇을 뜻하는가?** 그것을 계산할 수 있으면
계산하고, 없으면 iOS 와 같은 값을 쓰되 왜 같아도 되는지 적는다.

## 4. Material 아이콘은 준 크기보다 작게 그려진다

`Icons.Filled.CheckCircle` 에 20dp 를 주면 **원이 16.7dp 로 그려진다.** 24 짜리
그림 안에 여백을 두고 그리기 때문이다. SF Symbols 는 여백이 거의 없다.

보이는 크기를 맞추려면 그만큼 키우거나, 직접 그린다. 직접 그린 것은 준 값 그대로
나온다.

**모양이 다른 것도 흔하다.** 아래는 core 에 같은 것이 없어 직접 그렸다.

| iOS (SF Symbols) | Material core | 한 일 |
| --- | --- | --- |
| `film` | 없음 | 직접 그림 (채운 띠에 흰 구멍 5개) |
| `mappin.and.ellipse` | `Place`(물방울) | 직접 그림 (구슬 머리 + 타원 받침) |
| `bag.badge.plus` | `ShoppingCart` | 직접 그림 |
| `xmark.circle.fill` | `Clear`(맨 ✕) | 직접 그림 |
| `plus.circle` | `AddCircle`(채운 원) | 직접 그림 |
| `arrow.up.right.square` | 없음 | 직접 그림 |
| `bubble.left.and.bubble.right` | 없음 | 직접 그림 (꼬리 필수) |

**음/양을 확인하라.** 필름을 외곽선으로 그렸다가 iOS(채운 띠)와 반대가 됐다.

## 5. Compose 컴포넌트는 iOS 것과 **다른 물건**이다

    TabRow              밑줄 인디케이터   →  iOS 세그먼트(회색 트랙 + 흰 알약)
    FilterChip          테두리·체크       →  iOS 칩(그냥 알약)
    TextField           네모·밑줄·라벨    →  iOS 검색바(캡슐 안 글자만)
    NavigationBar       높이 80·알약 배경 →  iOS 탭바(높이 52·칸 구분선)
    BottomSheetScaffold 자기 비율         →  iOS 스냅 14% / 48% / 최대

**`BottomSheet.swift` 가 못 박아 뒀다** — *"스냅 비율은 두 앱이 같은 숫자를 써야
한다. 플랫폼 기본값에 맡기면 미묘하게 갈린다."*

## 6. `Dialog` 의 함정 셋

- **딤을 끄는 값이 `DialogProperties` 에 없다.** `decorFitsSystemWindows` 는 인셋
  처리이지 딤과 무관하다. 창을 직접 만져야 한다 (`ui/NoDim.kt`).
- 기본 딤(60%)을 안 끄고 그 위에 우리 딤(20%)을 칠하면 **1 − 0.8 × 0.4 = 68%** 가
  된다. 끄기만 하고 안 칠하면 0% 가 된다. **끄고, 칠한다.**
- `navigationBarsPadding()` 이 `Dialog` **안에서는 먹지 않는다.** 카드가 화면 아래로
  흘러나가 모서리가 잘린다. 바깥 상자에 준다.
- `decorFitsSystemWindows = false` 가 없으면 창이 상태바 아래에서 시작해 **위쪽에
  딤이 안 걸린다.**

## 7. 네이버 지도 — 두 SDK 가 다른 곳

| | iOS | Android |
| --- | --- | --- |
| 키 주입 | 코드 (`NMFAuthManager.ncpKeyId`) | **매니페스트** (`NCP_KEY_ID`). 코드로 넣으면 SDK 안에서 NPE |
| `fitBounds` 여백 | pt | **px** — dp 를 곱해서 넘겨야 한다 |
| 여백과 카메라 | `contentInset` 이 화면을 민다 | `setContentPadding` 의 **다섯째 인자**가 미느냐 마느냐를 가른다 |
| 글자 언어 | 기기 로케일 | 기기 로케일 — 영어 기기에서 `Daegu 대구` 로 겹친다. 못 박아야 한다 |
| 핀 이름표 | `captionMinZoom` | 같은 이름. 안 주면 전국 뷰에서 이름이 겹쳐 뭉개진다 |

**뷰가 배치되기 전에 `fitBounds` 를 부르면 크기 0 을 기준으로 계산된다.**
`getMapAsync` 콜백이 그 시점일 수 있다 — 한 프레임 기다린다(`withFrameNanos`).

## 8. 카메라가 움직이는 자리를 **빠짐없이** 옮긴다

첫 진입만 맞추고 넘어갔더니, 장소 하나를 검색했을 때 iOS 는 골목이 보이고
안드로이드는 경복궁까지 보였다(**3.2 배**). iOS 는 한 곳일 때 줌 16 으로 확대하는데
14 로 적어 뒀기 때문이다.

옮길 자리는 다섯이다 — **첫 진입 · 탭 전환 · 검색 확정 · 드릴다운 · 장소 선택.**
그리고 iOS 는 **맞추기 전에 매번 여백을 다시 건다.**

검색 확정은 **결과가 도착한 뒤**에 맞춘다. 확정 즉시 맞추면 직전 검색의 핀 범위로
맞춰지고 새 핀이 와도 카메라는 그대로다 (iOS 의 `pendingFit`).

## 9. `just fmt` 가 치환을 조용히 깨뜨린다

ktlint 가 들여쓰기를 바꾸면 다음 편집의 문자열 대조가 실패한다. **빌드는 통과한다** —
고치지 않은 코드가 그대로 컴파일되기 때문이다.

한 라운드에서 커밋 메시지가 고쳤다고 적은 것 중 **넷이 실제 코드에 없었다.**

**고친 뒤 `grep` 으로 확인하고 커밋한다.** 상수를 정의하는 것과 호출부를 바꾸는 것은
다른 일이다 — `capsuleButton` 을 정의만 하고 쓰는 곳을 안 바꾼 적이 있다.

## 10. 스스로 보지 말고 **따로 검사시킨다**

직접 비교하면 "비슷하니 됐다" 로 넘어간다. 별도 에이전트에게 두 기기를 실제로
조작하고 **픽셀로 재게** 하면 다르다. 첫 검사 총평은 「영 다른 앱」이었고 일곱 번째는
「나란히 놓으면 같은 앱으로 보인다」였다.

검사 지시에 넣으면 좋은 것:

- **소스 검증을 먼저** — 정의한 상수가 호출부에 닿았는가
- **심각도 순으로 위에서부터**, 항목마다 결과를 적어 두고 시간이 모자라면 아래를
  못 했다고 적기 (중간에 끊겨 전부 날아간 적이 있다)
- **밀도로 나눈 논리단위**로 재기
- **주장한 것 중 실제 반영된 비율**을 숫자로

## 11. 한쪽에만 먼저 넣지 않는다

작품 찜(하트)을 회의에서 확정했지만 iOS 에 없던 때가 있었다. 안드로이드에 먼저
넣었다가 **그 자체가 어긋남**이 되어 도로 뺐다.

**iOS 가 먼저다.** 안드로이드는 베끼는 쪽이므로, 한쪽에만 있는 기능을 안드로이드에서
먼저 만들면 기준이 뒤집힌다.

## 12. 옮기기 전에 스펙이 굳었는지 본다

검색 탭은 「확정 동작」 문서가 있어서 옮길 수 있었다. 그런데도 대조 검사를 일곱 번
돌렸다. 스펙이 흔들리는 화면을 옮기면 그 위에 스펙 변경까지 두 배로 쫓게 된다.

**탭이 확정되면 그 탭만 옮긴다.** iOS 전부를 만들고 안드로이드 전부를 만드는 것도,
둘을 동시에 만드는 것도 아니다.
