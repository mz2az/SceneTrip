# 인증·인가

## v1 에는 인증이 없다

로그인, 토큰, 세션이 모두 없다. 모든 엔드포인트가 익명으로 열려 있다.

**의도한 것이다.** 사용자 테이블이 아직 없어서다 — 스키마에 `app_user` 에 해당하는
테이블이 없고, `saved_place.user_id` 와 `user_event.user_id` 가 참조할 대상이 없다.
스프린트에서 *"개인 로그인까지 다 만들고 난 뒤에"* 재논의로 정리된 사안이다.

그래서 이 문서는 "어떻게 인증하는가" 가 아니라 **"인증이 없는 동안 무엇으로 사용자를
구분하는가"** 를 설명한다.

## 장바구니만 주체가 필요하다

조회 API 는 누가 부르든 같은 결과를 준다. 장바구니만 "누구의 것" 인지 알아야 한다.

```
GET    /v1/cart
POST   /v1/cart/items
DELETE /v1/cart/items/{placeId}
```

이 셋은 `X-Device-Id` 헤더를 **필수**로 받는다.

```
POST /v1/cart/items
X-Device-Id: 9f2c8a10-4b3e-4d21-9c7f-1a2b3c4d5e6f
Content-Type: application/json

{ "placeId": 7, "sourceContentId": 42 }
```

없거나 UUID 형식이 아니면 `400 MISSING_DEVICE_ID` 다.

## X-Device-Id 는 무엇인가

**앱이 최초 실행 때 한 번 만들어 기기에 보관하는 UUID** 다. 서버가 발급하지 않는다.

| 항목 | 값 |
| --- | --- |
| 만드는 쪽 | 앱 (최초 실행 시 1회) |
| 형식 | UUID |
| 보관 | iOS 키체인 · Android EncryptedSharedPreferences 권장 |
| 수명 | 앱을 지우면 사라진다 |

**앱 저장소가 아니라 키체인에 두는 것을 권한다.** 앱을 지웠다 다시 깔아도 살아남아,
사용자가 장바구니를 잃지 않는다.

## 무엇을 보장하지 않는가

**이것은 인증이 아니다.** 남의 `X-Device-Id` 를 알면 그 장바구니를 읽고 고칠 수 있다.
막을 방법이 없다 — 헤더 값 하나가 전부이기 때문이다.

그래서 **장바구니에 민감한 것을 담지 않는다.** 지금 담기는 것은 공개 장소의 ID 이고,
그것이 새어도 피해가 없다. 이 전제가 깨지는 기능(예: 개인 메모, 결제)이 들어오면
그때는 실제 로그인이 선행 조건이다.

UUID 는 **추측할 수 없어야 한다.** 순번이나 기기 식별자(IDFV·ANDROID_ID)에서 파생하지
말고 안전한 난수로 만든다.

## 로그인이 생기면

**이 헤더를 없애지 않고 사용자 계정에 이어 붙인다.**

```
지금       X-Device-Id → 장바구니
로그인 후   X-Device-Id → 사용자 계정 → 장바구니
```

로그인 시점에 그 기기의 장바구니를 계정으로 옮기면, **비로그인 상태에서 담아 둔 것을
잃지 않는다.** 로그인을 먼저 요구하지 않고 앱을 쓸 수 있게 하려면 이 승계가 필요하다.

계약이 바뀌는 지점은 그때다 — `Authorization` 헤더가 추가되고 `X-Device-Id` 는
로그인 전에만 쓰이게 된다.

## 그 밖에

**요청 제한(rate limit)이 없다.** v1 은 로컬·내부 환경에서만 돌기 때문이다. 외부에
노출하기 전에 반드시 붙여야 하며, 그때 `429` 와 대응 코드를 [errors.md](./errors.md)
에 더한다.

**CORS 설정이 없다.** 소비자가 네이티브 앱이라 브라우저 출처 검사가 걸리지 않는다.
웹 클라이언트가 생기면 그때 정한다.
