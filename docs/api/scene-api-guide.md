# scene-api 사용 가이드

앱의 **작품검색 탭**을 채우는 API 를 어떻게 부르는지 설명한다.

**정의는 여기가 아니라 [`contracts/openapi/scene-api-v1.yaml`](../../contracts/openapi/scene-api-v1.yaml)
에 있다.** 이 문서는 그 명세를 화면 흐름에 어떻게 끼워 넣는지, 그리고 **명세만 봐서는
알 수 없는 것**을 적는다.

> [!important]
> **아직 구현되지 않았다.** 계약과 서버 껍데기까지 있고 엔드포인트는 비어 있다
> (MZ2AZ-166~171). 이 문서는 프론트가 화면을 미리 맞출 수 있도록 먼저 낸다.

---

## 1. 기본 규칙

| 항목 | 값 |
| --- | --- |
| 로컬 주소 | `http://localhost:8081/v1` |
| 형식 | JSON |
| 언어 | `Accept-Language` 헤더 (`ko` · `en` · `ja` · `zh-Hant`) |
| 저장 주체 | `X-Device-Id` 헤더(설치 UUID)로 찾아낸 계정 — [auth.md](./auth.md) |
| 오류 | 공통 `ApiError` 형식 — [errors.md](./errors.md) |

**언어는 헤더로 보낸다.** 서버가 실제로 고른 언어는 `Content-Language` 응답 헤더에
담긴다 — 요청한 언어의 번역이 없으면 `ko` 로 폴백하므로, 요청과 응답이 다를 수 있다.

```
GET /v1/places/7
Accept-Language: ja

200 OK
Content-Language: ko        ← 일본어 번역이 없어 한국어로 내려감
```

### 목록은 전부 같은 모양이다

```json
{ "items": [ ... ], "total": 128, "limit": 20, "offset": 0 }
```

**`total` 이 `items` 길이보다 크면 잘린 것이다.** 무한 스크롤은 `offset` 을 늘려 가며
부르고, 지금까지 받은 개수가 `total` 에 닿으면 멈춘다.

정렬은 **인기도 내림차순**이 기본이다. 인기도 점수 자체는 응답에 없다 — v1 의 값은
임시로 고정한 것이라 의미가 없고, 프론트가 쓸 것은 점수가 아니라 순서다. 나중에
사용자 행동 기반 계산이 붙어도 이 계약은 바뀌지 않는다.

## 2. 화면별 호출 패턴

### 검색 — 검색어 하나로 두 탭을 동시에 채운다

사용자가 탭을 먼저 고르지 않는다. 검색어 하나를 **두 엔드포인트에 같이** 던지고,
각 탭이 자기 결과를 받는다.

```
사용자가 "도깨비" 입력
  ├─ GET /v1/contents?q=도깨비    → 작품 탭 목록
  └─ GET /v1/places?q=도깨비      → 장소 탭 목록 + 지도 핀 (좌표 포함)
```

**두 목록 엔드포인트는 같은 텍스트 뭉치를 본다.** 다른 것은 결과를 작품으로 내느냐
장소로 내느냐뿐이다.

| 부르는 곳 | 무엇에 걸리나 |
| --- | --- |
| `GET /search/suggestions` | 이름·별칭만 |
| `GET /contents?q=` | 작품 제목·별칭 · 작품 설명 · 인물 이름 |
| `GET /places?q=` | 장소명·별칭 · 장소 설명 · **그리고 위의 작품 쪽 전부** |

장소가 작품 쪽 텍스트에도 걸리는 이유는 **탭이 비면 안 되기 때문이다.** 사용자는
탭을 먼저 고르지 않으므로, 한쪽만 넓게 걸리면 다른 탭이 빈 화면이 되어 고장으로
보인다.

```
"공유" 입력
  작품 탭  →  도깨비                              인물 이름에 걸림
  장소 탭  →  순보석 · 인천아트플랫폼 · 북촌한옥마을   그 작품의 촬영지
```

장소는 `place_content` 로 작품에 이어져 있으므로, 작품 쪽에 걸린 것은 그 작품의
촬영지로 옮겨진다.

**자동완성만 범위가 좁다.** 한 줄짜리 제안에 "줄거리 어딘가에 그 낱말이 있다" 를
보여 줄 방법이 없기 때문이다.

### 자동완성 — 누르면 어디로 갈지가 응답에 있다

```
GET /v1/search/suggestions?q=gob

{ "items": [
    { "type": "content", "id": 3, "name": "도깨비",
      "matchedTerm": "Goblin", "subtitle": "tvN · 2016" } ] }
```

`type` 에 따라 다음 호출이 정해진다. 추가 조회가 필요 없다.

| `type` | 누르면 |
| --- | --- |
| `place` | `GET /v1/places/{id}` |
| `content` | `GET /v1/contents/{id}` |
| `person` | `GET /v1/contents?personId={id}` — 그 인물의 작품 목록 |

`matchedTerm` 은 **실제로 걸린 표기**다. 별칭으로 걸리면 `name` 과 다르다 — 위 예에서
사용자는 `Goblin` 을 쳤고 화면에 뜨는 이름은 `도깨비` 다. 검색어를 강조 표시할 때 쓴다.

### 지도 — 뷰포트와 근처 검색

```
지도를 움직임          GET /v1/places?bbox=126.9,37.5,127.1,37.6
"현 지도 내 성지 검색"  GET /v1/places?lat=37.55&lng=127.0&radiusMeters=5000&sort=distance
```

`bbox` 는 **경도-위도 순서**다(`minLng,minLat,maxLng,maxLat`). GeoJSON 과 같은 순서라
위경도를 뒤집기 쉬우니 주의한다.

**`bbox` 와 `radiusMeters` 는 함께 못 쓴다.** 둘 다 보내면 400 이다.
`sort=distance` 는 `lat`·`lng` 가 있을 때만 유효하다.

지도용 `limit` 은 기본 50, 최대 200 이다(목록용 기본 20 보다 크다). `total` 이 그보다
크면 인기도 상위만 온 것이다.

### 드릴다운 — 작품 → 촬영지 → 장면

```
작품 카드를 누름   GET /v1/contents/{id}          작품 상세 (줄거리·출연진·별칭)
                  GET /v1/contents/{id}/places   촬영지 목록 = 지도 핀
촬영지를 누름      GET /v1/places/{id}            장소 상세 + 이 장소의 장면들
```

**촬영지 목록의 번호는 프론트가 매긴다.** 목업은 번호를 촬영 순서처럼 보여 주지만
수집 데이터에 촬영 순서가 없다. 응답은 인기도순이고 번호는 배열 순서다.

**장면 팝업은 추가 호출이 필요 없다.** 장소 상세의 `scenes[]` 가 그 장소를 성지로
가진 작품들을 **인기도 내림차순**으로 담고, 각 항목이 팝업에 필요한 것을 이미
들고 있다.

| 필드 | 팝업에서 쓰는 곳 |
| --- | --- |
| `contentTitle` · `posterUrl` | 목록의 작품 카드 |
| `sceneDescription` | 팝업 본문 |
| `sceneImageUrl` | 팝업의 장면 사진 |

`posterUrl` 은 작품 포스터, `sceneImageUrl` 은 그 장면의 스틸이다. **사진이
`null` 이면 자리를 비우고 설명만 보여 준다** — 포스터로 대신 채우면 사용자가
그것을 장면 사진으로 읽는다.

장면 스틸의 저작권 판단은 아직 끝나지 않았다. 지금 넣기로 한 근거와 되돌리는
조건은 [ADR 0007](../architecture/adr/0007-scene-still-images-pending-rights.md).

거리를 보여 주려면 `lat`·`lng` 를 함께 보낸다. 그러면 각 항목에 `distanceMeters` 가
채워진다. 안 보내면 `null` 이다.

"이어서 걷기 좋은 곳" 은 별도 필드가 아니다 — 그 장소의 좌표로 다시 부르면 된다.

```
GET /v1/places?lat={그 장소 위도}&lng={그 장소 경도}&radiusMeters=1000&limit=3
```

### 장바구니

담는 경로가 셋(장소 카드 `+`, 상세의 저장 버튼, 장면 팝업 북마크)인데 **전부 같은
하나**를 부른다.

```
POST   /v1/cart/items          { "placeId": 7, "sourceContentId": 42 }
GET    /v1/cart
DELETE /v1/cart/items/{placeId}
```

`sourceContentId` 는 **어떤 작품을 보다가 담았는지**다. 선택 사항이지만 장바구니
목록에 대표 작품을 보여 주려면 필요하다.

같은 장소를 두 번 담으면 **409** 다. 이때 "이미 저장된 장소입니다" 토스트를 띄운다.

## 3. v1 응답에 없는 것

목업에 그려져 있으나 **수집 데이터에 소스가 없어** 뺐다. 화면에서 빼든 자리를 비우든
프론트가 판단해야 한다.

| 목업 요소 | 왜 없나 |
| --- | --- |
| 신뢰도 % · 검수 완료 배지 · 제보 건수 | 대응 테이블도 데이터도 없다 |
| 루트 N개 · 루트 마켓 | `route` 테이블이 없고 루트는 이번 범위 밖 |
| 회차 · 타임코드 (`2화 34분`) | 수집 컬럼이 없다 |
| 명대사 | 컬럼이 없고 저작권 논점이 미결이다 |
| 운영 시간 · 가는 방법 | 수집 소스가 없다 |
| 촬영 앵글 팁 | 수집 소스가 없다 |
| 촬영 순서 번호 | 순서 컬럼이 없다 (위 참조) |
| 장소 카테고리 칩 6종 | `place_type` 이 37종 자유 문자열이라 정제 전이다 |

반대로 **연도(`releaseYear`)와 장르(`genres`)는 있다** — 수집 데이터에 실제로 들어
있어서 넣었다.

`type`(장소 유형)은 가공 없이 그대로 내려간다. 37종이라 **필터 값으로 쓰기에 적합하지
않다.** 칩으로 묶는 매핑은 데이터 정제 후에 정한다.

## 4. 알려진 한계

이 셋은 **구현이 끝나도 당분간 그대로**다. 버그가 아니다.

**설명 중에서는 장면 설명만 걸린다.** 명세는 설명 셋을 검색 대상으로 적고 로직도 셋 다
훑는데, 실제로 값이 있는 것은 하나뿐이다.

| 설명 | 채워진 값 | 검색에 걸리나 |
| --- | --- | --- |
| 장면 설명 (작품 × 장소) | 157 / 157 | **걸린다** |
| 장소 설명 | 0 / 155 | 값이 없어 못 걸린다 |
| 작품 설명 | 0 / 8 | 값이 없어 못 걸린다 |

장면 설명은 *"2화에서 지은탁이 등장하는 버스정류장"* 같은 문장이라 `지은탁`·`버스정류장`
으로 검색하면 **작품 탭과 장소 탭이 함께 찬다.** 나머지 둘은 수집이 되면 코드 변경 없이
살아난다 — 컬럼과 질의는 이미 있다.

**영어로 치면 작품만 걸린다.** 작품에는 영어 별칭이 있다(`Queen of Tears`,
`Goblin`, `Itaewon Class`). 장소명은 한국어 표기뿐이라 `Yeouido Park` 로는 안 걸린다.
장소 영문명 확보는 별도 작업이다.

**인기도는 임시 고정값이다.** 정렬 순서는 보장하지만, 그 순서가 실제 인기를 반영하지는
않는다. 사용자 행동 로그가 쌓인 뒤에 진짜 계산이 붙는다.
