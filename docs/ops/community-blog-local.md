# 기존 가이드의 블로그형 본문·AI 사진 적용

MZ2AZ-428. 대상은 이전 지역 가이드 적재 상태에 기록된 추천 글 20개다. 글 ID·제목·작성자·
게시일·첨부 코스와 원본 사진은 보존하며 본문 문단 배치와 사진 연결만 바꾼다.
로컬 `kind-scenetrip`과 MinIO에서만 실행하며 `SCENETRIP_DB_HOST`가 있으면 거절한다.

먼저 `just db-migrate`로 V32를 적용하고 `just update scene-api`로 새 서버를 실행한다.
공용 로컬 API를 사용하는 다른 세션에 재시작을 알린다. 기본 가이드 자료와 기존 적재
상태 폴더를 유지하고 새 상태 폴더를 지정한다.

```sh
# 사진 이력·파일 해시·32개 첨부 대응·본문 길이·기존 원본 해시를 먼저 확인
just community-blog-local <기존-가이드-상태-폴더> <새-블로그-상태-폴더>

# 명시적으로 로컬 글·사진을 적용하고 실제 API·파일까지 확인
just community-blog-local <기존-가이드-상태-폴더> <새-블로그-상태-폴더> --apply

# 적용한 글·본문 순서·사진 바이트·원본 사진·코스 보존을 다시 확인
just community-blog-local <기존-가이드-상태-폴더> <새-블로그-상태-폴더> --verify

# 새 시험 글 한 개로 실제 사진 업로드·블록 게시·읽기를 확인하고 시험 글·사진만 정리
just community-blog-local <기존-가이드-상태-폴더> <새-블로그-상태-폴더> --smoke
```

입력은 기존 자료 판의 `state.json`과 저장소의 최종 AI 사진 제작 이력이다. 기존
원본의 해시와 생성 입력 해시가 일치해야 하며 PUT 직전 출력 해시도 확인한다.
새 저장 키는 가이드·사진 순서·출력 해시에서 계산한 UUID다. 조건부 PUT으로 기존
객체를 덮지 않는다. MinIO 안에서 실행하는 `mc pipe`는 16MiB·동시 업로드 1개로
로컬 컨테이너 메모리 한도에 맞춘다.

`rows-before.json`, `patch.json`, 원본 객체, 적용·검증 결과를 새 상태 폴더에 보존한다.
원본 객체는 임시 파일에 쓰고 해시를 확인한 뒤 원자적으로 옮긴다. DB는 지정된 행을
잠그고 원래 또는 이미 적용된 글/사진 및 코스 상태를 대조하며, 본문·배치·사진 키만
한 트랜잭션으로 갱신한다. JSON은 SQL 구문에 삽입하지 않고 COPY의 CSV 데이터로
보낸다. 대조나 SQL이 실패하면 트랜잭션 전체가 되돌아간다.

중단되면 같은 두 상태 폴더로 `--apply`를 다시 실행한다. 상태 파일을 지워 새 글을
만들거나 기존 키를 덮지 않는다. 사진이 준비되고 DB가 갱신됐지만 마지막 API 확인이
끊겼다면 `--verify`로 확인할 수 있다. DB 갱신 전에는 원래 글이 그대로다. 기존
객체도 남아 있어 백업된 원래 행과 사진 키를 이용해 복구할 수 있다.

`--smoke`는 `smoke.json`에 시험 글 ID와 확정 여부·정리 결과를 기록한다. 기록이
있으면 새 POST를 보내지 않는다. 결과가 불확실한 시험은 이 파일을 보존하고 내 글에서
정확한 제목·본문을 대조한 뒤 해당 시험 글만 정리한다.

적용 후에는 이 명령의 `--verify`를 사용한다. 이전 원본 가이드의 `--verify`는
원래 본문과 원본 사진을 대조하므로 블로그 적용 후에는 일부러 일치하지 않는다.
기기 전용 옛 글·사진을 서버에 게시하거나 운영 DB/AWS에 자동 전파하지 않는다.
