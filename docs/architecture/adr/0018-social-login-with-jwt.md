# ADR 0018: 로그인은 구글·애플 소셜 로그인과 JWT 로 한다

## 배경

마켓·길찾기·가이드 챗봇이 `401 SIGN_IN_REQUIRED` 로 막혀 있는데, 가입시키는 길이 없어
아무도 넘지 못한다(`app_user.registered_at` 을 채우는 코드가 없다). 로그인이 필요하다.

실제 제약:

- **백엔드는 `scene-api` 하나다.** 클라이언트는 iOS·Android 네이티브 앱이고 웹은 없다.
- 비회원도 이미 계정(`app_user`)이 있고, 모든 데이터가 그 id 에 붙어 있다(V8). 로그인은
  그 행에 신분을 붙이는 일이다 — 설계는 MZ2AZ-256.
- `UserStore.resolve` 가 **이미 요청마다 DB 를 한 번 본다**(설치 UUID → 계정, `last_seen_at`).
- 비밀번호를 저장하면 유출 사고의 대상이 된다. 팀이 그 책임을 지고 싶지 않다.
- iOS 에서 구글 로그인을 내면 **애플 로그인도 내야 한다**(App Store 심사 4.8), 앱 안에서
  탈퇴할 수 있어야 하고, 애플 로그인은 탈퇴 때 애플 쪽 연결도 끊어야 한다.

## 결정

우리는 **구글·애플 소셜 로그인만 받고, 우리 쪽 인증은 짧은 JWT 액세스 토큰과 DB 에 두는
일회용 리프레시 토큰으로 한다.**

- 사람의 구분은 `(provider, sub)` 다. 이메일로 가르지 않는다 — 애플은 대리 주소를 준다.
- 액세스 토큰: 서명된 JWT, 수명 30 분(설정). 서버는 서명·만료만 본다.
- 리프레시 토큰: 추측 불가한 난수, DB 에는 해시만. 쓸 때마다 새 것으로 바꾸고, 쓴 것이
  다시 오면 탈취로 보아 그 계정의 리프레시 토큰을 전부 폐기한다. 수명 60 일(설정).
- 기존 API 는 `X-Install-Id` 를 계속 받고 토큰은 선택이다. **가입한 계정은 설치 UUID
  만으로 열리지 않는다**(`SESSION_REQUIRED`).

계약: `contracts/openapi/scene-api-v1.yaml` 1.3.0 의 `auth` 태그.
계획: [docs/project/plans/social-login.md](../../project/plans/social-login.md).

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| 이메일·비밀번호 가입 | 비밀번호 해시가 유출 대상이 된다. 찾기·재설정·메일 발송까지 만들어야 한다 |
| **서버 세션**(DB 에 불투명 토큰, 요청마다 조회) | 기술적으로는 더 단순하고 즉시 끊을 수 있다 — 서버가 하나이고 이미 요청마다 DB 를 보므로 우리 조건에서는 오히려 유리했다. 그래도 JWT 로 간 것은 **서비스가 나뉘거나 다른 서비스(trip-guide 등)에 신원을 넘길 때 인증 구조를 다시 짜지 않기 위해서**다(2026-09-30 결정). 비용은 아래 「나빠지는 것」 |
| 긴 수명 JWT 하나(리프레시 없음) | 한 번 새면 만료까지 막을 수 없다. 로그아웃·탈퇴가 서버에서 효력이 없다 |
| 구글·애플을 한 창구(`/auth/sign-in` + `provider`) | 애플만 `authorizationCode`·이름을 더 보낸다. 「애플일 때만 필수」 를 생성 클라이언트가 표현하지 못한다 |
| 쿠키로 토큰 전달 | 네이티브 앱이라 쿠키 자동 전송의 이점이 없다. iOS 는 기본으로 쿠키를 다루고 OkHttp 는 다루지 않아 두 앱의 동작이 갈린다 |

## 결과

**좋아지는 것**

- 비밀번호가 없다 — 가장 위험한 자산을 갖지 않는다.
- 보호 API 는 서명만 보고 계정을 정한다. 서비스가 늘어도 같은 토큰을 검증하면 된다.
- 생성 클라이언트에 토큰을 넣을 자리가 생긴다(`security` 선언).

**나빠지는 것 / 감수하는 비용**

- 로그아웃·탈퇴 뒤에도 이미 발급된 액세스 토큰은 **최대 30 분** 서명상 유효하다. 탈퇴는
  계정 행이 사라지므로 서버가 조회 시점에 `ACCESS_TOKEN_INVALID` 로 막는다. 로그아웃은
  앱이 토큰을 지우는 것에 기댄다.
- 앱이 **refresh 재시도**(401 → 갱신 → 원래 요청, 동시에 한 번만)를 두 플랫폼에 각각
  만들어야 한다. 생성기가 만들어 주지 않는다.
- 서명 키를 관리한다(Secrets Manager, 교체 절차).
- 보호 API 는 결국 계정 행을 본다(가입 여부·탈퇴 확인). 「DB 를 안 본다」 는 JWT 의
  이점은 지금 구조에서는 크지 않다 — 위 대안 표에 적은 그대로다.

**후속 작업**

- MZ2AZ-331 서버 구현, MZ2AZ-256 병합
- 앱 로그인 화면·토큰 저장·refresh 재시도 (프론트)
- 개인정보처리방침 (구글 동의 화면·App Store 요건)

## 검증

- 로그인 → 보호 API → 만료 → refresh → 로그아웃이 로컬 배포에서 실제 토큰으로 돈다.
- 리프레시 토큰 재사용이 그 계정의 토큰 전부를 폐기하는 통합 테스트가 있다.
- 첫 배포 뒤 한 달, `REFRESH_TOKEN_INVALID` 비율을 본다. 재사용 판정이 잦으면 앱의 동시
  갱신 막기가 새는 것이다 — 그때 유예 시간(직전 토큰을 몇 초 더 인정)을 검토한다.
