# ADR 0023: 에이전트의 읽기 요청은 자격 증명 대신 한도 열쇠를 단다 — 열쇠는 서비스 비밀값이 맞을 때만 믿는다

> [0013](./0013-guide-chat-is-served-by-the-python-agent.md) 을 보정한다. 「에이전트는 사용자의 자격 증명을
> 받지 않는다」 는 그대로다. 에이전트가 **누구 몫으로 셀지**(계정 UUID 를 담은 한도 열쇠)는 알게 된다.

## 배경

챗봇 한 턴 안에서 에이전트는 장소를 읽으려고 scene-api 를 다시 부른다(도구 하나에 GET 1~2 번, 한 턴에 도구 최대
4 번). 0013 이 「읽기는 헤더가 필요 없으니 지금처럼 직접 부르는 것이 맞다」 고 정한 대로 이 요청에는
`Authorization`·`X-Install-Id` 가 없다.

그 뒤 일반 요청 한도(MZ2AZ-334, [rate-limit.md](../../project/plans/rate-limit.md))가 들어왔다. 한도 필터는 헤더가
없는 요청을 보낸 주소로 센다. 에이전트의 읽기는 전부 **에이전트 주소 하나**로 세어지고 비회원 상한(분당 60)이
걸린다 — 모든 사용자의 챗봇이 한 칸을 나눠 쓴다. 2026-10-11 로컬 실측에서 그 칸을 채운 직후 챗봇이
`503 GUIDE_UNAVAILABLE` 로 실패했다(같은 질문이 칸이 빈 때는 200, [guide-rate-subject.md](../../project/plans/guide-rate-subject.md) §1).

읽기 요청을 그 사용자 몫으로 세려면 에이전트가 「누구인지」 를 알아야 한다. 0013 이 막은 것은 에이전트가
**자격 증명**을 쥐는 일이다. 쓰기 API 는 `Authorization`(JWT) 이나 `X-Install-Id` 만 보고 계정을 연다
(`CurrentAccount`). 챗봇은 가입자만 쓰므로, 앱 헤더를 그대로 넘기면 에이전트는 그 사용자의 JWT 를 쥐고 토큰이
만료될 때까지 그 사용자로 무엇이든 할 수 있다.

## 결정

우리는 **에이전트에게 자격 증명이 아니라 한도 열쇠만 넘기고, 한도 필터는 서비스 비밀값이 맞을 때만 그 열쇠를
믿는다.**

- scene-api 는 앱의 `/guide/*` 요청을 센 열쇠(`user:<UUID>` · `install:<UUID>` · `ip:<주소>`)를 `X-Rate-Subject`
  로 에이전트에 넘긴다. `Authorization`·`X-Install-Id` 는 지금처럼 넘기지 않는다.
- 에이전트는 그 턴의 scene-api 읽기에 `X-Rate-Subject` 와 서비스 비밀값 `X-Service-Token` 을 단다.
- 한도 필터는 `X-Service-Token` 이 맞고 열쇠 형식이 맞을 때만 그 열쇠로 센다. 아니면 헤더를 무시하고 원래 규칙
  (JWT → 설치 UUID → 주소)으로 센다.
- 계정을 정하는 `CurrentAccount` 는 `X-Rate-Subject` 를 읽지 않는다. 이 헤더로 열리는 창구는 없다.
- 게이트웨이는 바깥 요청의 `X-Service-Token`(이미)과 `X-Rate-Subject` 를 지운다.

에이전트가 사용자 데이터를 읽어야 하는 기능이 생겨도 이 결정을 넓히지 않는다. 0013 의 방식대로 scene-api 가 읽어
요청에 싣는다.

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| 앱의 `Authorization`·`X-Install-Id` 를 그대로 에이전트에 넘긴다 | 에이전트가 사용자의 쓰기 권한을 쥔다. LLM 이 만든 도구 인자, 에이전트의 버그, 에이전트 침해가 곧 사용자 데이터 변경의 길이 된다. 0013 이 기각한 안 그대로다 |
| 에이전트의 읽기만 한도에서 뺀다(서비스 비밀값만) | 가장 작다. 챗봇 한도(1 시간 15 턴)가 양을 묶어 위험도 작다. 그러나 사람별로 세지 않아 「이 사용자가 분당 몇 번」 이 사라지고, 사용자가 직접 보낸 요청과 챗봇이 대신 보낸 요청이 다른 장부에 남는다. 사용자가 사람별 카운트를 골랐다(2026-10-11) |
| 클러스터 안 주소면 예외 | 바깥 요청도 게이트웨이(클러스터 안)를 거쳐 오고 scene-api 는 그 주소를 본다(`getRemoteAddr`). 클러스터 주소를 빼면 바깥 요청 전부가 빠진다 |
| 열쇠를 공개 계약(`contracts/openapi`)에 싣는다 | 앱이 보낼 일이 없는 서비스끼리의 약속이다. 생성 클라이언트에 쓸 일 없는 인자가 생긴다. 에이전트 쪽 계약 문서에 적는다 |

## 결과

**좋아지는 것**

- 챗봇이 다른 사용자의 사용량 때문에 함께 막히지 않는다.
- 사용자가 직접 보낸 요청과 그 사용자의 챗봇이 대신 보낸 읽기가 같은 칸에 쌓인다.
- 에이전트가 쥐는 것은 여전히 쓰기 권한이 없는 값뿐이다.

**나빠지는 것 / 감수하는 비용**

- 서비스 비밀값이 하나 생긴다(환경마다). 새면 누구나 아무 열쇠로나 셀 수 있다 — 다른 사용자의 칸을 채워 그 사람의
  읽기를 1 분 막을 수 있다. 쓰기·읽기 권한은 생기지 않는다. 게이트웨이 IP 상한은 그대로 남는다.
- 비밀값이 비면 조용히 옛 동작(한 칸)으로 돈다. 양쪽이 기동 때 경고를 남기고, 완료 기준을 실제 요청으로 확인한다.
- 에이전트가 계정 UUID 를 본다. 로그에는 남기지 않는다.

**후속 작업**

- 비밀값 교체 절차(두 값을 잠시 함께 받기) — 지금은 바꾸면 두 파드를 함께 다시 띄운다.
- scene-api 가 실제 클라이언트 주소를 읽지 못하는 문제 — 헤더 없는 바깥 요청이 모두 게이트웨이 주소 한 칸이다. 따로.

## 검증

[guide-rate-subject.md](../../project/plans/guide-rate-subject.md) §6 의 실측 — 헤더 없는 요청으로 공유 칸을 채운 직후
챗봇이 200 으로 답하고, 그 턴의 읽기가 그 사용자 칸에 쌓인다(`RateLimit-Remaining`). PRD 공개 뒤 첫 한 달 동안
`GUIDE_UNAVAILABLE` 비율과 `RATE_LIMITED` 를 받은 열쇠의 앞머리를 SigNoz 에서 본다 — `ip:` 가 계속 나오면 비밀값이
어긋난 것이다.
