# ADR 0030: 우리 S3 사진의 작은 사진은 scene-api 배경 작업이 JDK ImageIO 로 만든다 — 긴 변 720 JPEG, 응답에 nullable 칸

## 배경

목록·카드가 작은 칸(44~350px)에 우리 S3 의 원본을 그린다 — 후기·리뷰 사진 장당 약 700KB(긴 변 2048), 촬영지 사진 0.33~0.5MB(1280×720).
웹(app.scenetrip.io) 첫 방문 바깥 이미지가 2.76MB 다. 관광공사 사진만 작은 사진(약 300px)이 있다.

제약(2026-11-13):

- 팀 데모 11/28, 남은 2 주. 웹이 먼저, iOS 1.0.0 은 동결(웹뷰로 갈 예정), Android 는 범위 밖.
- 사용자 사진은 비공개 버킷의 한 시간 서명 주소로만 나간다. 파드 권한은 `uploads/tmp/*`·`reviews/*`·`posts/*`.
- 촬영지 사진은 세 환경이 함께 읽는 공개 버킷 `scenetrip-media-prod` 에 있고, 적재 데이터(`seed/candidates.csv`)로 DB 에 들어간다.
- 빌드는 Bazel 이 밀폐로 한다. MODULE.bazel 에 이미지 라이브러리가 없고 Python pip 의존성도 없다. JDK 의 `javax.imageio` 는 JPEG·PNG 를 읽고 JPEG 를 쓴다.
- scene-api 메모리 1Gi(상한 가까이 쓴다). 서버 배포는 main 커밋을 수동으로 올린다.

## 결정

우리는 우리 S3 사진의 작은 사진을 **긴 변 720px JPEG(q0.80) 한 가지**로, **JDK ImageIO 만으로** 만든다.
사용자 사진은 **scene-api 의 1 분 배경 작업**이 DB 에서 작은 사진이 없는 줄을 골라 만들고 키(`thumbnail_key`)를 적는다 — 새 사진과 옛 사진(백필)이 같은 길이다.
촬영지 사진은 같은 줄이기 코드를 쓰는 **사람이 한 번 돌리는 도구**가 공용 버킷의 새 경로(`place/thumb-720/…`)에 올리고, 적재 데이터가 `place_image.thumbnail_url` 을 채운다.
응답은 **nullable 칸을 더할 뿐**이고(없으면 앱이 원본을 쓴다) 기존 칸의 뜻은 바꾸지 않는다.

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| 업로드 완료 때 요청 안에서 바로 만들기 | 글 저장이 사진 수 × (받기·풀기·올리기)만큼 느려진다. 동시에 여러 장을 풀면 1Gi 파드가 위험하다. 백필 길이 따로 필요하다 |
| 처음 요청될 때 만들기 | 첫 사용자가 느리고, 목록 한 번에 여러 장이 동시에 생긴다(위와 같은 메모리 위험) |
| S3 이벤트 → Lambda | 새 배포 단위·IAM·Bazel 밖 코드(또는 새 규칙), 결과를 DB 에 알릴 길이 따로 필요. 2 주에 인프라를 늘리는 것이 위험 |
| CloudFront + Lambda@Edge / CloudFront Functions 변환 | 새 배포(지금 CDN 없음). 사용자 사진은 서명 주소라 CDN 캐시 열쇠가 매번 달라 캐시가 듣지 않는다 |
| Cloudflare 이미지 변환 | 웹 Pages 가 다른 사람 계정에 있다. 서명 주소가 매번 달라 변환 수가 늘어난다. 공개 버킷 사진에만 쓸 수 있다 |
| 앱이 올릴 때 작은 것도 올리기 | iOS 1.0.0 동결이라 옛 앱 사진에는 영영 없다. 기존 사진 백필이 따로 필요하다 |
| WebP | JDK 가 쓰지 못한다. 네이티브(JNI) 라이브러리를 들여야 해 밀폐 빌드가 깨진다. 이득(같은 화질 약 25%)이 그 비용만 못하다 |
| 여러 크기(480·960) | 칸 크기별 고르기가 앱마다 늘어난다. 한 크기로 가장 큰 목록 칸(350px, 2 배 화면)까지 덮는다. 키 이름에 크기를 넣어 나중에 더할 수 있다 |
| `imageUrl` 값을 작은 것으로 바꾸기(계약 그대로) | `PlaceDetail` 이 `PlaceSummary` 를 이어받아 iOS 1.0.0 상세 머리 사진이 흐려진다 |

## 결과

**좋아지는 것**

- 목록·카드의 우리 S3 사진이 장당 약 100KB 이하로 준다. 새 의존성·새 인프라·IAM 변경이 없다.
- 새 사진·옛 사진이 같은 작업을 지나 백필이 따로 없다. 작업이 멈춰도 응답은 원본으로 돌아갈 뿐이다.

**나빠지는 것 / 감수하는 비용**

- 새 사진의 작은 사진은 최대 1 분 늦게 생긴다(그동안 원본).
- 작은 사진 파일이 지우기 목록·고아 청소에 함께 들어가야 한다 — 빠뜨리면 남거나(개인정보) 지워진다(깨짐).
- 촬영지 사진을 바꾸면 도구를 다시 돌려야 한다(적재 데이터의 한 단계가 는다).
- JPEG 만이라 WebP 보다 약 25% 크다.

**후속 작업**

- 장면 스틸(`sceneImageUrls`)의 작은 사진.
- 서명 주소를 시간 단위로 고정해 브라우저 캐시가 맞게 하는 일.
- 카드 크기가 커지면 둘째 크기(`thumb-960`)를 더한다.

## 검증

- app.scenetrip.io 첫 방문(390×844, 캐시 끔) 홈 탭의 우리 S3 사진 바이트 합계가 70% 이상 준다(계획 [photo-thumbnails.md](../../project/plans/photo-thumbnails.md) §6).
- PRD 배포 2 주 뒤(12 월 초) `thumbnail_key IS NULL AND thumbnail_attempts >= 3` 인 줄 수와 scene-api 메모리·작업 소요 시간(SigNoz)을 본다. 실패가 1% 를 넘거나 작업이 메모리 경보를 내면 다시 본다.
