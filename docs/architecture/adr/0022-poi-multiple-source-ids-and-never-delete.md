# ADR 0022: 편의시설은 출처 번호를 여럿 갖고 지우지 않는다 — 영업 여부는 상가정보가 판단

> [0014](./0014-poi-source-is-public-data.md) 를 보정한다. 출처가 공공데이터라는 결정은 그대로다. 0014 의 「출처 교체는
> `--prune` 으로 이번 입력에 없는 행을 지운다」 와 「관광공사 음식·숙박은 상가정보에 있으면 넣지 않는다(버린다)」 를 바꾼다.

## 배경

편의시설 91 만 곳은 상가정보·관광공사·교통 원본 97 만 줄을 적재 규칙으로 합친 것이다. 2026-10-09 에 원본 줄마다 어느 POI 가
됐는지 재구성해 DB 와 한 줄도 다르지 않음을 확인했다([poi-source.md](../../project/plans/poi-source.md) §2-1). 그 과정에서
세 가지가 드러났다.

- **합친 기록이 없다.** 다른 POI 에 합쳐진 줄 22,818 의 번호가 DB 어디에도 없다 — 관광공사 → 상가정보 11,664, 상가정보 →
  관광공사 685 등. 관광공사 상세(사진·개요·영업시간, MZ2AZ-376)는 관광공사 번호로 받으므로 이 곳들에 붙일 수 없다.
- **갱신이 다른 출처를 모른다.** `poi_update.sql` 은 같은 출처끼리만 잇는다. 상가정보가 관광공사 POI 와 같은 가게를 새로
  들고 오면 그 POI 는 폐업 표시되고 빈 새 POI 가 생긴다. 상가정보가 가게를 빼면 가려져 있던 관광공사 줄이 새 POI 로 되살아나
  문 닫은 가게가 지도에 다시 나온다.
- **지우면 사용자 자료가 사라진다.** `review`(V21) · `course_item.poi_id`(V26) · `place_poi_link`(V25) · `poi_i18n` ·
  `poi_image`(V17)가 POI 를 `ON DELETE CASCADE` 로 참조한다. 그런데 적재에 POI 를 지우는 길이 둘 있었다 — `--prune`(입력에
  없는 행)과 §5-1(제외 분류).

## 결정

우리는 **POI 를 지우지 않고, 출처 번호를 여럿 기록하며, 영업 여부는 정해진 출처 하나가 판단한다.**

- POI 하나가 출처 번호를 여럿 가진다(`poi_source`). `poi.source_id` 는 대표 번호로 남는다. 합칠 때 번호를 버리지 않는다.
- 다른 출처와 새로 합치는 것은 **같은 건물(도로명 + 건물번호) + 이름 유사도 0.8 이상** 처럼 확실한 것만이다. 애매하면 합치지
  않는다 — 놓치면 핀이 둘이지만, 잘못 합치면 한 가게가 사라지고 남의 정보가 붙어도 티가 안 난다.
- 영업 여부는 상가정보 번호가 있는 POI 는 **상가정보**가, 관광공사에만 있는 POI 는 관광공사가 판단한다. 판단하지 않는 출처가
  빠지면 그 번호에 표시만 남긴다. 관광공사가 줄을 빼는 이유는 알 수 없다(`showflag` 에 사유가 없다).
- **POI 는 어떤 경우에도 지우지 않는다.** 보이지 않아야 할 POI 는 `closed_at` 으로 숨긴다. `--prune` 을 없애고, 제외 분류도
  지우지 않고 숨긴다.

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| 지금처럼 번호 하나 | 관광공사 상세를 1.2 만 곳에 못 붙이고, 갱신의 두 구멍이 남는다 |
| 둘 중 한 출처라도 빼면 폐업 | 문 닫은 가게가 남을 일은 가장 적지만, 관광공사는 폐업 말고도(사유 불명, 지역 코드 이관 사례) 줄이 빠진다. 상가정보에 영업 중으로 있는 가게가 사라진다 |
| `--prune` 을 막지 않고 경고만 | 출처 교체(TMAP → 공공데이터)는 끝났다. 남은 쓰임이 없고 한 번의 실수가 리뷰·코스를 지운다 |
| FK 를 CASCADE 에서 RESTRICT 로 | 지우는 길을 없애는 것과 같은 효과지만 마이그레이션 여섯 개의 FK 를 바꿔야 한다. 지우는 길을 코드에서 없애는 것으로 충분하다 — 다시 생기면 그때 |
| 유사도로 넓게 합치기(논문 방식의 분류기) | 상가정보끼리는 공통 지점명(`버거킹/던킨 원주기업도시점`) 때문에 유사도가 속는다(같은 건물 · 0.6 이상 약 4 만 쌍 대부분이 다른 가게). 정답지 없이 기준을 정할 수 없다 |

## 결과

**좋아지는 것**

- 리뷰·코스 항목이 적재 때문에 사라지지 않는다.
- 관광공사 상세를 합쳐진 곳까지 붙일 수 있다.
- 분기 갱신이 다른 출처의 같은 가게를 폐업 처리하거나, 문 닫은 가게를 되살리지 않는다.

**나빠지는 것 / 감수하는 비용**

- 출처를 다시 통째로 바꾸면 옛 행을 지우는 대신 숨겨야 한다 — 표에 행이 쌓인다.
- 상가정보가 실수로 가게를 빼면 그 가게가 숨겨진다. 판마다 「두 출처의 말이 다른 POI」 를 찍어 사람이 본다.
- 확실한 것만 합치므로 같은 가게 핀 둘이 남는다(관광공사 ↔ 상가정보 같은 건물 · 유사도 0.6~0.8 의 359 쌍 등).

**후속 작업**

- `poi_source`(V27)와 재구성 결과로 첫 채움, 적재·갱신 순서 — [poi-source.md](../../project/plans/poi-source.md) §4·§5.
- 배포 판에 건물 열쇠·지점명·원 번호 칸.

## 검증

- 적재에 `DELETE FROM poi` 가 없다. `just seed-poi --prune …` 은 멈춘다.
- 제외 분류로 바뀐 POI 는 행이 남고 `closed_at` 이 있다.
- 다음 분기 갱신에서: 관광공사 → 상가정보로 합쳐진 POI 가 폐업 처리되지 않고, 상가정보가 뺀 가게가 관광공사 줄로 되살아나지 않는다.
- 다시 볼 시점: 「두 출처의 말이 다른 POI」 가 판마다 수백 곳을 넘으면 영업 여부 판단 출처를 다시 본다.
