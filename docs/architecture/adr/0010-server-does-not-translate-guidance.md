# ADR 0010: 서버는 안내문을 번역하지 않는다 — 표시 문장은 앱이 조립한다

## 배경

앱이 ko·en·ja·zh-Hant 를 지원한다. 길찾기 응답에는 두 종류의 글이 있다 —

- **우리 문장**: 「도보 3분 · 210 m」「3 정거장 · 7분」「마을 종로02」. 숫자와 이름을 조립한 것.
- **제공자 원문**: 「반석빌라까지 110m 이동(북촌로11길)」. 카카오가 만든 턴바이턴 안내문.

처음 구현은 서버가 우리 문장을 한국어로 조립해 `title`·`detail` 로 내렸다. 이 서비스가
표시용 문장을 만드는 첫 사례였다 — 지금까지 i18n 은 전부 DB 행(`place_i18n` 등)이고
서버에 `MessageSource` 도 `messages_*.properties` 도 없으며, 문장은 앱이 만들어 왔다
(프로토타입 `KakaoTransit.swift` 의 `walkDetail`·`transitDetail`).

카카오는 비공식 `lang` 파라미터로 ko·en 만 온전히 준다(실측 2026-09-03: ja 는 영어
문장에 한글 고유명사가 섞인 반쪽, zh-Hant 는 한국어 폴백). `vehicles[].type` 은 어느
언어에서도 한국어다. 제공자 원문을 ja·zh-Hant 로 만들려면 기계 번역이 필요하다.

## 결정

우리는 **서버가 표시 문장을 만들지도 번역하지도 않는다.** 계약은 재료를 나른다.

- `RouteLeg` 는 `guidance`(제공자 원문)·`meters`·`seconds`·`stopCount`·`vehicleType`·
  `vehicleName` 을 든다. 「도보 3분 · 210 m」는 앱이 자기 로케일로 조립한다.
- `NextLeg.guidanceLang`(ko|en)이 원문의 언어를 말한다. 서버는 `Accept-Language` 가 ko 면
  ko, 그 외는 en 으로 카카오에 보낸다 — 일본어 사용자에게 한국어보다 영어가 낫고, 영어판은
  고유명사가 로마자라 실제 표지판과 맞는다.
- 앱이 `guidanceLang` 과 자기 로케일을 견줘 그대로 보여 줄지, 기기 안에서 번역할지 정한다.
  서버 쪽 결정은 여기서 닫히고 앱 쪽은 열어 둔다.

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| 서버가 우리 문장을 4개 언어로 조립 (`MessageSource`) | 서버가 처음으로 표시 문장의 주인이 된다. 복수형·숫자 포맷을 4개 언어로 서버가 관리하고, 안드로이드가 오면 두 앱의 표시를 서버 문장 하나가 맞춰야 한다. 저장소 관행(서버는 데이터, 앱은 표시)과 반대다 |
| 서버가 제공자 원문을 기계 번역 (Papago·DeepL) | 길찾기는 사용자가 기다리는 요청인데 카카오 1~3회 위에 번역 1회가 얹힌다. 번역 결과를 저장하면 제공자 파생 데이터 저장이라 「실시간 호출만」 규칙에 걸려 매번 번역료를 낸다. 벤더·키·비용을 지금 정해야 한다 |
| ja·zh-Hant 도 카카오 `lang` 그대로 | 반쪽 일본어와 한국어 폴백은 영어보다 못하다. 실측으로 확인했다 |
| 서버가 조립하되 앱이 덮어쓰기 | 두 곳이 같은 문장을 만든다. 어느 쪽이 정본인지 흐려진다 |

## 결과

**좋아지는 것**

- 서버 코드에서 문장 조립 함수 넷이 사라졌다. 「서버는 데이터만」이 코드로 보인다.
- 앱이 iOS `String(localized:)`·복수형·`NumberFormatter` 를 그대로 쓴다. 안드로이드도
  자기 것을 쓴다.
- 기기 안 번역(iOS `Translation`, Android ML Kit)이 공짜·오프라인이고 데이터가 기기 밖으로
  안 나간다. 영어→일본어가 한→일보다 품질이 낫다.
- 어느 쪽이 번역하든 계약은 그대로다 — `guidance` 원문과 `guidanceLang` 이 있으면 서버에서
  번역해 `guidanceLang: ja` 로 찍어 보내는 것도 가능하다.

**나빠지는 것 / 감수하는 비용**

- 앱이 할 일이 는다. 지금 앱은 자기 UI 문구도 한국어 리터럴이라(「계단 있음」「여기 도착함」)
  다국어 장치 자체를 이번에 들여야 한다.
- ja·zh-Hant 사용자는 당분간 영어 안내문을 본다. 「Go 110m along Bukchon-ro 11-gil」의 골목
  이름은 표지판에 그렇게 로마자로 적혀 있어 오히려 실용적일 수 있다 — 번역이 꼭 필요한지는
  사용자 반응을 보고 정한다.
- `vehicleType`(간선/마을/직행)은 카카오가 번역하지 않아 앱이 자기 표로 옮긴다. 모르는
  값이 오면 그대로 보여 준다.

**후속 작업**

- 앱: `RouteLeg` 재료로 문장 조립, `guidanceLang` 비교, 기기 안 번역 붙일지 결정.
- 웹 클라이언트가 생기면 「기기」가 없어진다 — 그때 서버 번역을 다시 본다. `guidance` +
  `guidanceLang` 계약이 그 길을 막지 않는다.

## 검증

- 서버 코드에 사용자가 읽을 한국어 문장 리터럴이 없다 — `NextLegPlanner` 에 「도보」「정거장」
  문자열이 없다. 오류 `message` 는 예외다(사용자에게 보이지 않는 로그용, `errors.md`).
- ja 로 요청하면 `guidanceLang: en` 이고 `guidance` 가 로마자 영어다 — `just navigation-smoke`
  가 매번 본다.
- 다시 볼 때: 일본어 사용자 세션에서 길찾기 화면 이탈이 다른 언어보다 눈에 띄게 높으면
  영어 안내문이 문제라는 신호다. 그때 기기 안 번역 → 서버 번역 순으로 올린다.
