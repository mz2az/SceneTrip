# ADR 0005: 통합 테스트의 의존성을 CI 가 직접 공급한다

> **보정([0009](./0009-seed-dataset-in-repository.md), 2026-09-01):** 아래 본문의
> "저장소에 표본 CSV(12 행)" 는 이제 정예 4 작품 전량(164 행, `seed/v6.csv`)이다.
> "적재 데이터를 테스트 데이터로 쓴다" 는 결정은 그대로고, 그 데이터가 커졌을 뿐이다.

> 이 ADR 은 [0001](./0001-bazel-as-the-single-build-system-and-just-as-the-single-command-surface.md)
> 을 **보정한다.** 그 결정(Bazel + `just`, 얇은 CI 껍데기)은 그대로 유효하고, 어긋난 것은
> "`just ci` 가 파이프라인을 로컬에서 그대로 재현한다" 는 **전제** 하나다. 이 ADR 이 그
> 전제를 복원한다.

## 배경

`tests/integration/`·`tests/e2e/`·`tests/load/` 세 레인은 저장소 골격을 세울 때 만들어
두고 **비어 있었다.** 태그 체계(`AGENTS.md` §4.2)와 레인별 레시피는 있었지만, 그 레인에
실제로 도는 테스트가 없어 "CI 는 이것들을 어떻게 다루는가" 를 정할 일이 없었다.

MZ2AZ-149 에서 scene-api 의 Store 4 개를 실제 PostgreSQL 에 태우는 통합 테스트 28 개를
넣으면서 그 빈칸이 드러났다. `ci-full` 이 태그 필터 없이 `bazel test //...` 를 돌려서
GitHub 러너가 그 테스트를 집었고, 러너에는 DB 도 접속 정보도 없어 여섯 클래스가 전부
`@BeforeAll` 에서 죽었다 (PR #14 의 `verify` 잡).

### 지금 문서에 있는 것과 없는 것

| 물음 | 정해져 있나 | 어디에 |
| --- | --- | --- |
| DB 가 필요한 테스트에 어떤 태그를 다나 | 있음 | `AGENTS.md` §4.2, `CLAUDE.md` §4 |
| 그 테스트를 어느 레인에서 돌리나 | 있음 | `just test-integration` |
| **로컬에서** 의존성을 누가 띄우나 | 있음 | `tests/integration/README.md` — `just cluster-up` |
| **CI 에서** 의존성을 누가 띄우나 | **없음** | — |
| CI 가 이 레인을 돌려야 하나 | **없음** | — |

즉 규칙 위반이 아니라 **규칙의 공백**이다. 급한 불을 끄려고 `ci-full` 에서
`integration`·`e2e` 태그를 제외해 두었는데(PR #14), 그것은 빈칸을 코드로 임의로 메운
것이고 두 가지 문제를 남긴다.

1. **통합 테스트 28 개를 아무도 자동으로 지키지 않는다.** 검색 대칭이 다시 깨져도 CI 는
   초록으로 남는다. 그 테스트를 만든 이유가 바로 "사람이 손으로 curl 을 날려서야 결함이
   드러났다" 는 것이었는데, 지금도 사람이 기억해야 돌아간다.
2. **[ADR 0001](./0001-bazel-as-the-single-build-system-and-just-as-the-single-command-surface.md)
   의 전제가 깨졌다.** 그 ADR 은 "`just ci` 가 파이프라인을 로컬에서 그대로 재현한다" 고
   했고 검증 기준으로 "CI 와 로컬이 어긋나는 경우가 **레시피가 틀렸을 때뿐**" 을 걸었다.
   지금은 레시피가 아니라 **환경이 달라서** 어긋난다. `AGENTS.md` §5.1 의 "`just ci` |
   exactly what CI runs" 도 더는 사실이 아니다.

### 실제 제약

- 팀은 3 인이고 전용 CI 인프라가 없다. GitHub Actions 무료 러너가 전부다.
- 로컬 의존성은 kind 클러스터로 띄운다. **러너에는 쿠버네티스가 없다.**
- 데이터 적재(`just seed`)가 `kubectl cp` 와 `kubectl exec` 로 동작해 클러스터에 묶여
  있다. 하는 일의 본질은 "CSV 를 psql 에 먹인다" 뿐이고 kubectl 은 통로일 뿐이다.
- 스키마는 **앱이 기동할 때** Flyway 가 적용한다. CI 에는 앱을 띄울 이유가 없는데
  스키마는 필요하다.

## 결정

**우리는 CI 러너가 통합 테스트의 의존성을 직접 공급하게 하고, `integration` 레인을 CI 에서
돌린다.** 로컬이 kind 로 얻는 것을 러너는 서비스 컨테이너로 얻으며, 그 위에 스키마와
데이터를 올리는 일은 **로컬과 CI 가 같은 `just` 레시피**로 한다.

구체적으로 넷을 정한다.

1. **DB** — GitHub Actions 의 서비스 컨테이너로 `postgis/postgis` 를 띄운다. 로컬 kind 의
   Postgres 와 같은 이미지 계열·버전을 쓴다.
2. **스키마** — Flyway 를 앱 기동에만 얹어 두지 않고 **Bazel 타깃으로 뽑는다**
   (`//services/scene-api:migrate`, `just db-migrate`). 지금은 앱을 띄워야만 스키마가
   생기는데, 그것은 CI 뿐 아니라 운영에서도 불편하다.
3. **데이터** — `just seed` 를 그대로 쓴다. 접속 정보가 환경변수로 주어지면 `psql` 을
   직접 부르고, 없으면 지금처럼 kubectl 경로를 탄다. `v6.sql` 은 손대지 않는다 —
   그 파일은 kubectl 을 모른다.
4. **등식 회복** — `ci-full` 에서 `integration` 제외를 되돌린다. `just ci` 와 CI 가 같은
   것을 돌게 하여 ADR 0001 의 전제를 복원한다. `e2e` 는 전체 스택이 필요해 이 ADR 의
   범위 밖이며 제외를 유지한다.

### 갈렸던 지점과 고른 이유

**테스트 데이터 — 적재 데이터(`just seed`)를 쓴다.** 테스트가 자기 픽스처를 직접 넣고
지우는 대안이 CI 붙이기는 더 쉽다. 그럼에도 적재 데이터를 고른 이유는 **검증 대상이
실제 수집 데이터의 모양**이기 때문이다. 세미콜론으로 묶인 별칭(`김수현;김지원`), 한국어
표기뿐인 장소명, PostGIS 좌표 — 이것들은 손으로 만든 픽스처에서 재현하려 들수록 실제와
멀어진다. 별칭 `Goblin` 으로 `도깨비` 가 걸리는지 같은 검증은 실데이터라야 뜻이 있다.
저장소에 표본 CSV(12 행)를 둔 이유가 바로 "볼트 없이도 동작을 확인할 만큼" 이었고, 이
결정이 그 의도를 이어받는다.

**스키마 — Bazel 타깃으로 뽑는다.** CI 에서 앱 jar 를 잠깐 띄워 Flyway 를 돌리고 끄는
대안은 작업이 적지만 "테스트를 위해 서버를 켠다" 는 군더더기가 남고, 기동 대기와 종료
처리가 파이프라인의 불안정 요인이 된다. 마이그레이션을 독립 명령으로 뽑으면 CI 뿐 아니라
운영에서도 쓸 곳이 있다 — 배포 전에 스키마만 먼저 올리는 경우가 그렇다.

**`e2e` — 지금 정하지 않는다.** 타깃이 0 개라 정할 근거가 없고, 전체 스택은 서비스
컨테이너로 해결되지 않아 성격이 다르다. 첫 e2e 테스트가 들어올 때 이 ADR 을 보정하는
형태로 다룬다. 그때까지 `ci-full` 은 `-e2e` 제외를 유지한다.

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| **CI 에서 통합 레인을 계속 제외한다** (현 상태 유지) | 테스트 28 개를 사람의 기억이 지킨다. 그 테스트를 만든 이유가 "사람이 손으로 확인해야만 드러나는 결함" 이었으므로 자기모순이다. ADR 0001 의 검증 기준도 계속 미달이다. |
| **Testcontainers 를 도입한다** | 테스트가 자기 DB 를 띄우므로 CI·로컬 구분이 사라진다. 다만 Maven 의존성이 늘고 Docker 상시 실행이 새 전제로 붙는다. `tests/integration/README.md` 가 이미 "`just cluster-up` 이 띄운 실제 의존성" 을 규정했고, 새 의존성 없이 되는 길이 있으므로 미룬다. |
| **CI 에도 kind 클러스터를 세운다** | 러너에서 kind 를 띄우는 것은 가능하지만 매 실행마다 클러스터 부팅과 이미지 적재가 붙어 파이프라인이 몇 분 늘어난다. 통합 테스트에 필요한 것은 클러스터가 아니라 **PostgreSQL 하나**다. |
| **통합 테스트를 단위 테스트로 되돌린다** (Store 를 가짜로) | 원래 상태다. SQL 이 한 줄도 실행되지 않아 컬럼 오타와 PostGIS 인자 순서를 못 잡는다. 이번에 실제로 못 잡았다. |
| **야간 빌드에서만 돌린다** | PR 시점에 못 잡으면 이미 머지된 뒤다. 통합 테스트가 잡는 것(검색 대칭, SQL 성립)은 PR 단위로 확인해야 뜻이 있다. |

## 결과

**좋아지는 것**

- 통합 테스트 28 개가 PR 마다 자동으로 돈다. 검색 대칭이 깨지면 머지 전에 잡힌다.
- `just ci` = CI 등식이 회복되어 ADR 0001 의 검증 기준("어긋나면 레시피의 버그")이 다시
  성립한다.
- 스키마 적용이 앱 기동에서 떨어져 나와 독립 명령이 된다. 운영에서도 "마이그레이션만 먼저
  돌리기" 가 가능해진다.
- `just seed` 가 kubectl 없이도 동작해, 클러스터가 없는 환경(CI, 원격 DB)에서도 쓸 수 있다.

**나빠지는 것 / 감수하는 비용**

- CI 파이프라인이 길어진다. DB 기동 + 마이그레이션 + 적재가 붙는다 — 표본 12 행 기준 수십
  초 규모로 예상하나 실측이 필요하다.
- 워크플로 YAML 이 두꺼워진다. ADR 0001 의 "CI 워크플로는 얇은 껍데기" 와 긴장 관계다.
  서비스 컨테이너 선언은 Actions 고유 문법이라 `just` 레시피로 감쌀 수 없다 — 이 ADR 이
  인정하는 예외이며, **그 예외를 서비스 컨테이너 선언 하나로 한정한다.** 그 위에서 도는
  명령은 전부 `just` 레시피여야 한다.
- 러너의 PostgreSQL 과 kind 의 PostgreSQL 이 완전히 같지는 않다. 버전과 확장을 한곳에서
  관리하지 않으면 "CI 에서만 되는" 상황이 새로 생긴다.

**후속 작업**

- `//services/scene-api:migrate` 타깃과 `just db-migrate` 레시피
- `seed.sh` 에서 kubectl 의존 분기 (환경변수가 있으면 psql 직접)
- `integration-test.sh` 우회로 — `SCENETRIP_TEST_JDBC_URL` 이 이미 있으면 포트포워드 생략
  (절반 되어 있음)
- `.github/workflows/ci.yml` 에 서비스 컨테이너와 통합 잡
- `ci-full` 의 `-integration` 제외 되돌리기
- `tests/README.md` 의 "CI 가 덮지 않는 레인" 절 삭제
- `AGENTS.md` §5.1 의 "exactly what CI runs" 가 다시 사실이 되는지 확인
- ADR 0001 에 `amended-by: 0005` 와 안내 문단 추가

## 검증

**이 결정이 작동하고 있다고 말할 수 있는 조건**

- PR 에서 검색 대칭을 일부러 깨면 CI 가 **빨강**이 된다. 사람이 아무것도 하지 않아도.
- `just ci` 를 로컬에서 돌린 결과와 CI 결과가 갈리는 경우가 **레시피가 틀렸을 때뿐**이다.
- 통합 잡이 붙어도 PR 피드백이 5 분 안에 온다.

**다시 볼 시점**

- 첫 e2e 테스트가 들어올 때. 전체 스택은 서비스 컨테이너로 해결되지 않으므로 갈래 C 를
  그때 정한다.
- 통합 테스트가 100 개를 넘거나 CI 시간이 10 분을 넘을 때. 그때는 Testcontainers 나 원격
  캐시 같은 다른 선택지를 다시 검토한다.
- 두 번째 서비스가 생겨 DB 가 둘이 될 때. 서비스 컨테이너 선언이 서비스마다 늘어나면
  "얇은 껍데기" 원칙이 실제로 깨지는 시점이다.
