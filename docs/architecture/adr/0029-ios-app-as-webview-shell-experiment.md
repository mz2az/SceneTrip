# ADR 0029: iOS 앱을 웹앱의 WKWebView 껍데기로 만드는 실험 — 빌드 스위치 뒤, 로그인은 네이티브 공급자 단계만

## 배경

팀은 세 명이고 같은 화면을 iOS(Swift)·웹(React)으로 두 번 만든다(Android 는 2026-11-07 중단). 웹이 먼저 바뀌고 iOS 가
따라잡는 일이 반복된다(MZ2AZ-525·526·529·547). iOS 1.0.0 은 App Store 에 있고 1.0.1 을 준비 중이다.

제약:

- 1.0.0 사용자를 깨면 안 된다 — 실험은 끌 수 있어야 하고 기본은 꺼짐.
- 구글은 내장 웹뷰의 OAuth 를 `disallowed_useragent` 로 막고, Apple JS 로그인은 팝업 창이 필요하다.
- App Store 심사 지침 4.2(최소 기능)는 웹사이트를 감싼 앱을 거절할 수 있다.
- 웹의 비회원 데이터는 웹 자신의 설치 번호(localStorage)에 붙어 있다.

## 결정

우리는 iOS 앱에 **빌드 시점 스위치**(`--define=scenetrip_web_shell_url=<주소>`, 기본 빈 값 = 끔) 뒤에 `WKWebView` 껍데기를 두고,
로그인은 **네이티브가 공급자 단계(GIDSignIn·ASAuthorization)만** 해 그 자격(ID 토큰·nonce 등)을
`WKScriptMessageHandlerWithReply`(`scenetripAuth`)로 웹에 돌려주며, 서버 교환·토큰 저장·갱신은 **웹이 지금 코드 그대로** 한다.

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| 네이티브가 서버 세션(토큰+me)까지 받아 웹에 넘긴다 | 서버 교환에 네이티브 설치 번호가 실려 웹의 비회원 데이터가 합쳐지지 않는다. 웹의 `settle`·분석 이벤트도 우회된다 |
| 웹뷰 안에서 구글 OAuth 를 그대로 연다(사용자 에이전트 위장) | 구글 정책 위반, 언제든 막힌다 |
| `ASWebAuthenticationSession` 으로 웹 OAuth 를 연다 | 웹용 클라이언트 ID·리디렉트가 필요하고(웹은 아직 미설정) 돌아온 값을 다시 웹으로 옮겨야 한다. 네이티브 SDK 가 이미 있다 |
| 런타임 원격 스위치(서버 플래그) | 실험 단계에서 심사 빌드에 숨은 동작을 넣게 된다. 빌드 스위치가 더 단순하고 정직하다 |
| Capacitor 등 하이브리드 프레임워크 | 새 툴체인(CLAUDE.md §9). 필요한 다리는 메시지 처리기 하나뿐이다 |

## 결과

**좋아지는 것**

- 스위치를 켜면 화면 코드는 웹 하나 — iOS 따라잡기 작업이 사라진다.
- 로그인은 구글·Apple 정책을 지키는 네이티브 창을 쓰고, 웹 계정 로직은 바뀌지 않는다.

**나빠지는 것 / 감수하는 비용**

- 심사 4.2 위험. 1.0.0 대비 기능 후퇴(백그라운드 여행 안내, 네이티브 지도 반응)로 보일 수 있다.
- 위치 권한 질문이 앱·사이트로 두 번 뜰 수 있다.
- 웹이 배포되면 심사 없이 앱 화면이 바뀐다 — 심사 지침 2.5.2(코드 내려받기)와는 무관하지만 리뷰 시점 화면과 달라질 수 있다.

**후속 작업**

- 채택하면: 네이티브 위치 폴리필, 오프라인 화면 다듬기, 유니버설 링크, 푸시 등 "앱다운" 기능, 1.0.1 심사 메모.
- 기각하면: 스위치와 `src/WebShell/` 를 지운다(웹의 `nativeAuth.ts` 는 감지 실패 시 아무 일도 하지 않으므로 남겨도 무해).

## 검증

- 실험 보고(MZ2AZ-557): 시뮬레이터에서 `dev.scenetrip.io` 로딩·지도·네이티브 로그인 창 확인.
- 채택 시 1.0.1 TestFlight → 심사 결과가 4.2 로 거절되면 이 결정을 다시 본다.
