# ADR 0012: 여행 가이드 챗봇은 서버가 부른다 — 앱은 화면 상태를 보내고, LLM 호출과 도구 실행은 scene-api 가 한다

## 배경

여행 가이드 챗봇은 프로토타입(`apps/navi_proto`, 파이썬)에서 만들어졌다. iOS 앱이 맥의 파이썬 서버
(:8899)를 부르고, 그 서버가 로컬 LLM(:8900, mlx_lm)을 도구 호출 규격으로 부른다. 코스 플래너는 앱이
:8900 을 **직접** 불렀다. 둘 다 navi-proto 브랜치에만 있고 main 은 「준비 중」 스텁이다(MZ2AZ-297).

실제 제약 셋.

- **도구가 곧 데이터 질의다.** `poi_nearby` 는 47만 건 편의시설에서 반경·갈래·인기로 고르는 일이고,
  `route` 는 카카오 길찾기, `add_to_cart` 는 장바구니 쓰기다. 셋 다 이미 `services/scene-api` 안에
  있다(`PoiStore`·`poi_naver`(ADR 0011)·`KakaoRoutingClient`(ADR 0009)·`CartStore`).
- **LLM 은 갈아 끼운다.** 개발은 맥의 mlx_lm(gpt-oss-20b), 배포는 상용 API 가 될 수 있다. 모델 이름·키가
  앱에 박히면 배포마다 앱을 다시 내야 하고, 키가 앱 바이너리에 남는다.
- **화면에서 일어난 일을 모델이 알아야 한다.** 2026-09-05 실측 — 발자국이 다 찍혔는데 「방문 여부는
  알려지지 않았어요」. 원인은 모델이 아니라 앱이 보내는 화면 상태에 다녀옴·여행 단계가 없던 것이다.

팀은 셋(iOS·백엔드·안드로이드)이고 프로토타입은 iOS 담당이 파이썬으로 썼다.

## 결정

우리는 챗봇의 **LLM 호출·도구 실행·프롬프트를 `services/scene-api` 에 둔다.** 앱은
`POST /guide/chat` 한 번에 대화 이력·지금 위치·**화면 상태 스냅샷**(담은 지점과 다녀옴, 여행 단계·가는
곳·남은 직선거리·걸은 거리)을 보내고, 답과 근거(부른 도구·찾은 장소·경로)를 받는다. 앱은 LLM 의
주소·모델·키를 모른다.

화면 상태의 모양은 계약(`GuideContext`, `contracts/schemas/guide/context.schema.json`)이다. 질문별
답을 서버에 적지 않는다 — **상태의 항목을 넓히고 도구를 늘리는 것**이 챗봇을 똑똑하게 만드는 유일한
두 통로다.

## 검토한 대안

| 선택지 | 채택하지 않은 이유 |
| --- | --- |
| 앱이 LLM 을 직접 부른다 (navi-proto 의 코스 플래너 방식) | 모델·키가 앱에 박힌다. 도구(47만 건 질의)를 앱이 못 한다. iOS 와 Android 가 같은 오케스트레이션을 두 번 짜게 된다 |
| 파이썬 에이전트 서비스(`agents/guide/`)를 따로 두고 scene-api 가 프록시한다 | 도구가 전부 scene-api 의 데이터라 서비스 하나가 더 생기고 왕복만 는다(실측 도구 1회 30초에 네트워크 홉 추가). 프롬프트·오케스트레이션이 300줄 안팎이라 언어를 하나 더 들일 크기가 아니다. 파이썬이 정말 필요해지면(에이전트 프레임워크·평가 도구) 그때 `agents/` 로 뺀다 — 계약은 그대로다 |
| 대화를 서버가 저장한다 | 데모 규모에서 필요 없다. 이력은 앱이 보내고, 서버는 「보여 준 장소」만 세션별 메모리로 기억한다 |
| 화면 상태 대신 `screen_state` 도구로 모델이 물어보게 한다 | 왕복이 한 번 더 붙어 모든 답이 30초짜리가 된다. 상태는 코스 열댓 곳 분량이라 밀어 넣는 쪽이 싸다 |

## 결과

**좋아지는 것**

- 앱 둘(iOS·Android)이 같은 한 계약을 부른다. 모델을 바꿔도 앱은 그대로다.
- 도구가 데이터 옆에 있어 정확하고, 한 번 고치면 양쪽 앱에 적용된다.
- 「무엇을 근거로 말했나」(`toolsUsed`)가 계약에 있어 화면이 헛소리를 걸러 보일 수 있다.

**나빠지는 것 / 감수하는 비용**

- 프로토타입 파이썬 코드를 자바로 다시 쓴다(오케스트레이션·도구 셋·프롬프트 적재·채널 표식 풀기).
- 서버가 LLM 지연(2~60초)을 안고 있어야 한다 — 요청 스레드가 오래 산다. 데모 규모에선 문제 없고, 커지면
  비동기·스트리밍은 별도 결정.
- 상용 API 로 가면 사용자 위치·담은 지점 이름이 밖으로 나간다. 좌표는 모델에게 안 주므로 안 나간다.

**후속 작업**

- MZ2AZ-285 구현 — 계획서 `docs/project/plans/guide-chat.md` §9.
- iOS `RouteGuide.ask` 를 생성 클라이언트로(별개 티켓). Android 동일.
- 코스 플래너(`RoutePlanner`)의 LLM 호출도 같은 원칙으로 서버에 둘지 — 별도 ADR.

## 검증

- 계획서 §8 의 검수 표가 통과한다 — 여행 상태 질문 5종은 도구 0회, 주변 질문은 `poi_nearby` 1회.
- 앱 바이너리에 LLM 주소·모델·키 문자열이 없다(`strings` 로 확인).
- LLM 을 끄면 `503 GUIDE_UNAVAILABLE` 이 오고, 앱이 그 사실을 화면에 말한다.
