# 도시 추천 코스를 AI 로 — 후보를 추려서 넘긴다 (2026-11-10)

새 코스의 「도시로 시작 → 며칠 → 알아서 짜 주세요」 가 보여 주는 추천 코스를, 앱 안의 단순 계산 대신 AI 일정 짜기로 만든다.
「작품으로」 가 이미 쓰는 창구(`POST /guide/plan`)와 에이전트(`agents/trip-guide`)를 도시에도 쓰게 넓힌다.

티켓: MZ2AZ-548.

## 지금

| | 작품으로 | 도시로(알아서 짜 주세요) |
| --- | --- | --- |
| 누가 고르나 | 모델(`llm_planner.py`) — 작품의 촬영지·좌표·작품 안 인기도를 받고 날짜별 일정을 낸다 | 앱(`CityPlanRules.plan`, 웹·iOS·안드로이드 같은 규칙). 모델 없음 |
| 어떻게 | 모델이 못 주면 결정적 엔진(`planner.py`)이 짠다 | 인기순 촬영지에서 필요한 수의 2배를 잡아, 1등에서 시작해 매번 가장 가까운 곳을 잇고 하루 3·5·7곳으로 자른다 |
| 시간 | 로컬 실측 3.4초(도깨비 2일, 2026-10-14) | 즉시 |

도시 계산은 같은 작품만 몰리거나, 한 날에 먼 동네가 섞이거나, 대표 촬영지를 빼도 알 수 없다.

## 실측 (2026-11-10, 로컬)

- 도시는 96곳(`GET /places/cities`). 촬영지 수: 서울 124 · 제주 28 · 인천 20 · 부산 19 · 수원 16 · 포항 14 · 대구 12 · 나머지 10 이하.
  **서울만 크다.**
- 서울 범위(네모)의 촬영지 133곳을 지금 모델에 주는 줄 모양 그대로 만들면 약 17,700자. 토큰은 6천~8천으로 **추정**한다(토크나이저로 세지 않음).
  입력 단가는 100만 토큰당 $0.15(`config/model.json`).
- 「작품으로」 도 작품 5개를 고르면 이미 최대 90곳(작품당 18곳)을 넘긴다.

크기보다 문제는 고르는 질이다 — 후보가 많을수록 먼 동네를 같은 날에 섞을 위험이 크다(숫자를 주자 다른 지역을 끌어온 사례, `config/llm_planner.json` 의 `_pace_설명`).

## 사용자가 정한 것

- **후보는 코드가 추려서 넘긴다**(2026-11-10). 전부 넘기기·동네로 나눠 두 번 묻기는 하지 않는다. 평가에서 서울만 「전부 넘기기」 와 비교한다.

- 인기 위주로 하되 작품을 섞는다. 찜한 작품 우선은 하지 않는다.
- 이번에는 촬영지만. 식당·카페는 나중에 따로.
- 3~4초 기다림 — 「작품으로」 의 「짜는 중」 화면을 그대로 쓴다.

## 1. 계약 (`contracts/openapi/scene-api-v1.yaml`, 1.27.0 → 1.28.0)

`GuidePlanRequest` 에 `city` 를 더한다.

- `city`: string, maxLength 40. 값은 `GET /places/cities` 의 `key` 그대로(예: `서울`, `경기 광주`).
- `titles` 는 필수에서 뺀다. **`titles` 와 `city` 중 정확히 하나** — 둘 다 오거나 둘 다 없으면 400 `INVALID_PARAMETER`.
- `titles` 의 1~5개, `days` 1~7, `pace`, `latitude`·`longitude`, `must`·`avoid` 는 그대로(도시에도 쓴다).
- 400 설명에 더한다: 모르는 도시, 좌표 있는 촬영지가 하나도 없는 도시.
- 응답(`GuidePlanReply`)은 그대로 — 앱이 초안을 받는 코드를 한 벌로 둔다.

## 2. 서버 (`services/scene-api`)

`POST /guide/plan` 이 위 검증을 하고 에이전트의 `POST /plan` 에 `city` 를 그대로 넘긴다. 에이전트가 400 을 주면 그대로 400.

## 3. 에이전트 (`agents/trip-guide`)

- **후보 받기:** `GET /places?city=<key>&sort=popularity` 로 좌표 있는 촬영지를 서버 순서(인기순)로. 데이터는 서비스를 거친다(DB 직접 금지).
- **추리기:** 필요한 수 = 하루 곳 수 × 일수. 후보 = 인기순 앞에서 `필요한 수 × 3`, 적어도 15곳, 도시 전체보다 많으면 전체.
  예: 서울 당일 보통 5곳 → 15곳, 서울 3일 빡빡 21곳 → 63곳, 강릉(9곳)은 늘 9곳.
  배수·최소·하루 곳 수는 `config/llm_planner.json` 에 둔다(하루 곳 수는 개수 셈에만 쓰고 모델에게 숫자로 주지 않는다 — 위 사례).
- **줄 모양:** `id`·`name`·`area`(시·도를 뺀 구·시·군, 예: 「종로구」)·`lat`·`lng`·`popularity`(인기 순위에서 1.0 부터 내려가는 값)·`work`(대표 작품 1~2개).
  지금 줄의 `location`(「서울특별시 종로구」)보다 짧고, 모델이 하루를 한 동네로 묶을 단서가 된다.
- **프롬프트:** 새 파일 `prompts/plan_city.txt`. 하루는 한두 동네 안에서, 작품이 고루 섞이게, 인기 높은 곳을 먼저. 답 형식은 지금과 같은 JSON.
  「작품으로」 는 규칙 문장을 넣지 않기로 했다(2026-10-02, `llm_planner.py` 머리말). 도시는 사용자가 「인기 위주 + 작품 섞기」 를 정했으므로 적고,
  효과는 평가에서 본다.
- **도시 창구:** `PlaceSource.by_city` — scene-api 창구만 구현한다(CSV 에는 도시 열이 없다). 받는 상한은 설정 `fetch_limit`(200).
- **요청 검증:** 에이전트의 `POST /plan` 도 `titles`·`city` 중 정확히 하나를 본다. `city` 는 1~40자 문자열.
- **응답:** `plan.titles` 는 일정에 든 작품들(처음 나온 차례).
- **하루 몫 자르기**(2026-11-10 로컬 실측 뒤 사용자 결정): 모델은 하루 곳 수를 지키지 않았다 — 서울 2일 빡빡에 13·12곳, 부산 당일 여유에 5곳.
  모델이 고른 날·순서는 그대로 두고, 날마다 앞에서 하루 곳 수(여유 3·보통 5·빡빡 7)까지만 남긴다. 모델에게는 여전히 숫자를 주지 않는다.
  잘라서 빈 날은 없다(모델이 고른 날에 적어도 한 곳은 남는다).
- **구역과 순서**(2026-11-10 첫 평가 뒤 사용자 결정, [평가](../../ai/evals/trip-guide-2026-11-10-city.md)): 모델이 「하루는 가까운 동네끼리」 를 지키지 않아
  하루 이동이 제주 150~178km 까지 나왔고, 제주는 `area` 가 「제주시」·「서귀포시」 둘뿐이라 단서가 되지 못했다.
  1. **구역:** 코드가 후보를 좌표로 묶어 줄마다 `zone`(「A」·「B」…)을 붙인다. 구역 수 = 올림(후보 수 ÷ (하루 곳 수 × 2)), 적어도 1.
     묶는 법은 결정적이다 — 인기 1등에서 시작해 이미 고른 중심에서 가장 먼 곳을 다음 중심으로(가장 먼 점 고르기), 각 곳은 가장 가까운 중심에,
     중심을 무리의 평균으로 옮기기를 10번. 이름은 인기순으로 처음 나온 무리부터 A·B·C. 프롬프트: 「하루는 한 구역(zone) 안의 곳으로 채우세요(여러 날이 같은 구역을 써도 됩니다)」.
  2. **순서:** 자른 뒤 날마다 모델이 고른 첫 곳에서 시작해 매번 가장 가까운 곳으로 차례를 다시 잡는다. 고른 곳은 바꾸지 않는다.
- **빈자리 채우기와 더 잘은 구역**(같은 날 두 번째 평가 뒤 사용자 결정): 모델이 하루 몫보다 적게 고르거나(서울 2일 여유 [3, 2]) 날을 빠뜨렸다(부산 3일 빡빡에 2일).
  서울 「전부」 가 「추림」 보다 하루 이동이 짧았다 — 구역이 잘수록 짧은 것으로 보인다.
  1. **구역 크기:** 구역 하나 ≈ 하루 곳 수 × `zone_factor`(설정, 1). 구역 수 = 올림(후보 수 ÷ (하루 곳 수 × zone_factor)), 적어도 1.
  2. **채우기:** 자른 뒤, 하루 곳 수보다 적은 날은 그날 곳들과 **같은 구역**의 아직 안 쓴 후보 가운데 그날 곳에서 가장 가까운 것부터 채운다
     (그날 곳이 여러 구역이면 그날 첫 곳의 구역). 날이 모자라면 아직 안 쓴 후보 가운데 가장 인기 있는 곳으로 새 날을 열고 같은 방식으로 채운다.
     같은 구역에 채울 곳이 없으면 그대로 둔다(다른 구역에서 끌어오지 않는다). 순서 다시 잡기는 채운 뒤에.
- **검증·대신 짜기:** JSON 이 아니거나 후보에 없는 id 를 넣으면 앱의 계산(`CityPlanRules.plan`)과 같은 규칙으로 짠다 — 인기순 앞에서 필요한 수의 2배(`fallback_factor`)를 잡아 1등에서 시작해 매번 가장 가까운 곳을 잇고 하루 몫으로 자른다. 「작품으로」 의 엔진(`planner.make_plan`)은 작품 기준이라 쓰지 않는다. 사용자는 늘 초안을 받는다.
- 모델 ID·파라미터는 설정 그대로(`config/model.json`).

## 4. 평가 (`agents/trip-guide/evals`, 결과는 `docs/ai/`)

도시 서울·부산·제주 × 1·2·3일 × 여유·빡빡. 비교 셋:

1. 지금 앱 계산(인기순 2배 → 가까운 곳 잇기)
2. 추려서 넘기기(이 계획)
3. 전부 넘기기 — 서울만

| 지표 | 뜻 |
| --- | --- |
| 대표 촬영지 | 도시 인기 상위 5곳 가운데 일정에 든 수 |
| 하루 이동 | 그날 장소를 차례로 이은 직선 거리의 최댓값(km) |
| 작품 섞임 | 일정에 나온 서로 다른 작품 수 |
| 시간 | 요청에서 답까지(초) |
| 대신 짜기 | 모델이 실패해 엔진이 짠 비율 |

결정적 시험은 모델을 부르지 않는다(기록한 응답·가짜 클라이언트). 실제 모델 평가는 `integration`·`requires-network`.

## 5. 앱 (iOS 먼저 → 사용자 확인 → 웹·안드로이드)

2026-11-10 사용자 결정으로 처음 안을 바꿨다 — **서버만 쓴다**(앱 계산으로 대신하지 않는다), **도시 촬영지 전부를 미리 받지 않는다**
(서울 124곳을 받을 까닭이 없다), **꾹 눌러 순서 바꾸기를 뺀다**(시뮬레이터에서 스크롤과 엉켜 동작하지 않았다).

- 「알아서 짜 주세요」 → 「AI 가 동선을 짜고 있어요」 → `POST /guide/plan {city: 도시 key, days, pace: normal}` → 추천 코스 카드.
  작품(`titles`)은 보내지 않는다. 도시 질문은 속도를 묻지 않으므로 보통이다.
- 못 받으면(503·시간 초과·네트워크·하나도 남지 않음) 「코스를 못 짰어요」 와 「다시 시도」. 앱 계산(`CityPlanRules.plan`)으로 대신하지 않는다.
- 카드는 응답만으로 그린다: 날마다 정지점을 `order` 순으로, `placeId` 가 없는 줄은 뺀다, 빈 날도 뺀다.
  카드에 쓰는 사진·작품은 정지점의 `imageUrl`·`contents`(아래 계약 덧붙임). 도시 촬영지 목록(`GET /places?city=`)은 받지 않는다.
- 「다른 곳으로 바꾸기」: 누를 때 그 카드 자리에서 가까운 그 도시 촬영지 10곳만 묻는다(`GET /places?city&lat&lng&sort=distance&limit=10`).
  그중 코스에 아직 없는 첫 곳으로 바꾼다. 없으면 그대로. 「빼기」 는 그대로.
- 꾹 눌러 순서 바꾸기·접근성 「위로/아래로 옮기기」 를 뺀다. 안내 글은 「빼거나 다른 곳으로 바꾼 뒤 저장하세요」.
- 미뤄 둔 카드 뒤집기(사진을 누르면 장면 그림, [motion-works-drawer-parity.md](motion-works-drawer-parity.md) §6)를 이 화면에 함께 넣는다.

### 계약 덧붙임 (1.28.0 안, 아직 내보내지 않음)

`GuidePlanStop` 에 둘을 더한다. 둘 다 선택값이고 기존 앱은 무시한다.
- `imageUrl`: 그 장소의 대표 사진(`PlaceSummary.imageUrl` 과 같은 값). 없으면 null.
- `contents`: 그 장소가 나온 작품들(`ContentRef` — `contentId`·`title`), 서버 순서. 촬영지가 아니면 없음.
에이전트는 `GET /places` 응답의 `imageUrl`·`contents` 를 장소에 들고 있다가 그대로 싣는다. effects 정본(`contracts/schemas/guide/effects.schema.json`)도 같이 고친다.
