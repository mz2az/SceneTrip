# 검색 탭 네이티브 구현 계획 (iOS · Android)

- **티켓**: [MZ2AZ-148](https://mz2az.atlassian.net/browse/MZ2AZ-148) — 에픽 MZ2AZ-106 "검색·지도"
- **브랜치**: `MZ2AZ-148-목업-기반-프론트-구현` (스토리 키. 커밋은 서브태스크 키 — [AGENTS.md §7.2](../../../AGENTS.md))
- **작성일**: 2026-08-05 (2026-08-06 Android 포함으로 개정)
- **모듈**: `apps/scenetrip-ios/` · `apps/scenetrip-android/`
- **순서**: **iOS 를 먼저 만든다** (§7)

---

## 1. 무엇을 만드는가

앱의 **작품검색 탭**을 iOS 네이티브(Swift)와 Android 네이티브(Kotlin)로 만든다. `apps/` 에
들어가는 첫 앱 모듈이므로, 화면 구현만이 아니라 **저장소에 모바일이라는 갈래를 여는 일**을
함께 한다 — Bazel Apple·Android 규칙 활성화, macOS CI 잡, OpenAPI 클라이언트 생성기 연결이
전부 이 계획에 딸려 있다.

화면은 이미 한 번 만들어 봤다. Flutter 로 만든 프로토타입이 `~/workspace/mobile` 에 있고
iOS 시뮬레이터에서 동작한다. **그 코드는 이 저장소로 옮기지 않는다.** [ADR 0002](../../architecture/adr/0002-product-stack-spring-python-native-mobile.md)
가 크로스 플랫폼 프레임워크를 쓰지 않기로 확정했기 때문이다. 프로토타입이 남기는 것은
코드가 아니라 **확정된 화면 구조와 검색 규칙**이며, 그 내용이 §3 이다.

프로토타입을 버리지 않고 남겨 두는 이유는 두 가지다. 화면 동작을 눈으로 비교할 대조군이
되고, §3 의 규칙이 애매할 때 실제로 돌려 볼 수 있다.

### 두 앱을 같이 계획하는 이유

ADR 0002 가 감수하기로 한 비용이 **"모바일 기능을 두 번 만든다"** 이고, 같은 문서가 검증
항목으로 **"두 모바일 앱이 실제로 어긋나지 않는가"** 를 걸어 뒀다. 어긋남은 화면을 만들 때가
아니라 **규칙이 한쪽에만 적혀 있을 때** 생긴다. 그래서 §3 을 두 앱의 공통 기준으로 두고,
플랫폼마다 다른 것은 §5 에 몰아 둔다.

## 3. 프로토타입이 확정한 것

Flutter 로 만들면서 여러 차례 고쳐 잡은 결과다. **iOS 와 Android 구현 모두 이것을 기준으로
삼는다.** 두 앱이 어긋나지 않게 하는 장치가 이 절이다 — 여기 없는 동작은 어느 쪽에서도
임의로 만들지 않는다.

### 3-1. 화면 구조

- 지도는 **항상 보인다.** 그 위에 바텀시트가 얹혀 3단으로 드릴다운한다 — 목록 → 작품 상세 → 촬영지 상세.
- 시트는 3단 스냅(14% / 42% / 최대)이고, 최대 높이는 검색바 바로 아래까지 기기별로 계산한다.
- 목록은 **작품 / 장소** 두 탭으로 나뉜다. 검색어 하나로 두 탭이 동시에 채워지며, 사용자가 탭을 먼저 고르지 않는다.
- 상단에 검색창과 장바구니가 한 덩어리로 고정된다.

시트 컴포넌트는 플랫폼마다 이름이 다르다(iOS `UISheetPresentationController` 계열,
Android `BottomSheetBehavior`). **스냅 비율과 최대 높이 계산은 위 숫자를 그대로 맞춘다** —
컴포넌트 기본값에 맡기면 두 앱이 미묘하게 달라진다.

### 3-2. 검색이 걸리는 범위

| 입력 | 작품 탭 | 장소 탭 |
| --- | --- | --- |
| 작품 제목·별칭 (`도깨비`, `Goblin`, `케데헌`) | 그 작품 | 그 작품의 촬영지 |
| **배우·감독 이름** (`김수현`) | 그 사람의 작품 | **그 작품들의 촬영지 전부** |
| 장소명 (`북촌한옥마을`) | — | 그 장소 |
| 지역 (`마포구`) | — | 그 지역의 촬영지 |

배우로 검색했을 때 **장소 탭까지 채워지는 것** 이 핵심이다. 프로토타입에서 이것이 빠져 있을
때는 "김수현을 쳤는데 촬영지가 안 나온다"가 되어 탭 하나가 죽은 화면이 됐다.

### 3-3. 자동완성

- 검색창에 포커스가 있는 동안만 뜬다. 시트를 끌거나 지도를 만지면 닫힌다 — 안 그러면 결과 목록을 가린다.
- 검색창이 비어 있으면 **최근 검색어** 와 **추천 검색어** 를 깔아 준다.
- 글자를 치면 **작품 → 인물 → 장소 → 연관 검색어** 순으로 보여 준다.
- 랭킹은 **앞글자 일치 > 단어 앞 일치 > 중간 포함** 이고, 동점이면 인기도순이다.
- 작품이 배우로 걸린 경우 `출연 김수현` 배지를 달아 제목으로 걸린 것과 구분한다.

### 3-4. 연관 검색어는 별칭 컬럼에 몰아넣지 않는다

별칭 컬럼은 "그 작품의 다른 표기"라는 뜻이 분명한 자리다. 거기에 배우·지역·장르까지 넣으면
컬럼의 의미가 뭉개지고, 배우 한 명이 작품 10편에 나오면 이름이 10번 중복 저장된다.

대신 이미 있는 컬럼에서 검색어를 파생시킨다. 프로토타입은 적재 시점에 작품 제목·별칭, 배우,
감독, 장소명, 지역(주소 앞 두 토막), 장르·채널을 훑어 검색어 사전을 만들었다.

**서버 스키마가 이미 같은 방식이다.** `search_term` 이 테이블이 아니라 다섯 곳을 `UNION ALL`
로 합친 MATERIALIZED VIEW 다([scene-api-search-map.md §5](./scene-api-search-map.md)). 프론트가
따로 만들 필요가 없고, 목데이터를 걷어내면 그대로 서버 것을 쓴다.

### 3-5. 지도와 목록을 어긋나지 않게 한다

- 검색이 **확정되는 시점**(추천어 선택·엔터)에 핀을 결과로 갈고 그 범위로 카메라를 맞춘다.
- 글자마다 갱신하지 않는다. 프로토타입에서 핀 아이콘을 위젯에서 이미지로 굽는 구조라 타이핑마다 수십 개를 다시 그리면 버벅였다. 네이티브에서도 같은 판단을 유지한다.
- **카테고리 칩은 목록만 좁히고 지도는 건드리지 않는다.** 칩을 눌렀을 때 지도에서 핀이 사라지면 오히려 혼란스럽다고 봤다. 팀 의견이 다르면 바꾼다.

## 4. API 계약과 대조 — 다 맞는다

[`contracts/openapi/scene-api-v1.yaml`](../../../contracts/openapi/scene-api-v1.yaml) 을 §3 과
맞춰 봤다. 프로토타입은 이 명세를 보지 않고 만들었는데도 결론이 같다.

| §3 의 요구 | 명세 | 상태 |
| --- | --- | --- |
| 자동완성에 작품·인물·장소가 섞여 나온다 | `GET /search/suggestions` 가 `type` 으로 place·content·person 을 구분해 돌려준다 | 맞음 |
| 누른 항목이 어디로 가는지 안다 | 각 항목이 `type` 과 `id` 를 들고 있다 | 맞음 |
| 배우 이름으로 작품이 걸린다 | `GET /contents?q=` 가 인물 이름에 걸린다 | 맞음 |
| 자동완성에서 인물을 누르면 그 사람 작품 | `GET /contents?personId=` | 맞음 |
| 작품명으로 장소 탭이 채워진다 | `GET /places?q=` 가 등장 작품 제목·별칭에 걸린다 | 맞음 |
| 랭킹 = 앞글자 우선, 인기도순 | 명세에 같은 규칙이 적혀 있다 | 맞음 |
| **배우 이름으로 장소 탭이 채워진다** | `GET /places?q=` 가 **출연진 이름에도 걸린다** | 맞음 |

### 마지막 줄은 서버가 이미 메웠다 (MZ2AZ-167)

이 계획의 초안(8/5)을 쓸 때는 마지막 줄이 비어 있었다. `GET /places` 의 `q` 가 장소명·별칭·
장소 설명·**등장 작품의 제목** 까지만 봤기 때문에, `김수현` 을 치면 작품 탭은 채워지는데
장소 탭이 비었다. §3-2 가 죽는 상태였다.

8/6 에 권호가 고쳤다(커밋 `499c5d1`, MZ2AZ-167). **`personId` 파라미터를 더하는 대신 `q` 의
검색 폭 자체를 넓히는** 쪽을 택했다. 장소 쪽에 두 경로가 추가됐다.

```
작품 설명  → place_content → 장소
인물 이름  → content_cast → place_content → 장소
```

명세의 `q` 설명도 그에 맞게 바뀌었다.

> 장소명·별칭·장소 설명·등장 작품의 제목·별칭·**설명·출연진 이름**을 함께 검색

**이 선택이 초안이 제안했던 `personId` 방식보다 낫다.** `personId` 를 더했다면 프론트가
"이름을 쳤다"와 "자동완성에서
인물을 골랐다"를 구분해 호출을 갈라야 했다. `q` 를 넓히면 **작품 탭과 장소 탭이 같은
파라미터, 같은 문자열로 채워진다** — 프론트는 `GET /contents?q=` 와 `GET /places?q=` 에 같은
값을 넣기만 하면 되고, 그 코드가 iOS 와 Android 에서 같은 모양이 된다.

[scene-api-search-map.md §5](./scene-api-search-map.md) 가 근거를 이렇게 적어 뒀다 —
"한쪽 탭에 걸리는 것은 다른 탭에도 걸려야 한다. 결과의 종류만 다를 뿐 질문은 하나다."
§3-2 표가 말하려던 것과 같은 얘기다.

검증은 서버 쪽에서 이미 끝났다. `공유`·`김고은`·`도깨비` 셋 다 작품 탭 1건 · 장소 탭 3건으로
같이 채워진다.

**프론트가 할 일은 없다.** 우회 로직도, 추가 파라미터도 필요 없다.

### 프론트가 알고 있어야 할 명세의 한계

[scene-api-search-map.md §4·§5](./scene-api-search-map.md) 가 적어 둔 것이다. 화면에서
빈칸이 보일 때 버그로 오해하지 않으려면 미리 알아야 한다.

- **장소는 영어로 검색되지 않는다.** 작품에는 영어 별칭이 있지만 장소명에는 없다. 다만 위 확장 덕에 **영어 작품명·배우명으로는 장소가 걸린다** — `Goblin` 이 도깨비 촬영지를 부른다.
- **설명 검색은 당분간 아무것도 잡지 못한다.** 작품 설명은 4편 중 1편만 있고, 장소 설명은 수집 컬럼 자체가 없다. MZ2AZ-167 이 "작품 설명 → 장소" 경로를 열어 뒀지만 채울 데이터가 아직 없다.
- **장면 설명(`relation_description`)은 검색되지 않는다.** 장소와 작품 사이에 붙은 값이라 어느 탭의 대상으로도 삼지 않기로 했다.
- **인기도는 v1 에서 적재 시 고정한 임의값이다.** 정렬에만 쓰이고 응답에는 안 들어온다.
- 목업에 있으나 v1 응답에 없는 필드(신뢰도 배지·회차 타임코드·명대사·운영시간 등)는 그 문서 §6 에 표로 있다.

## 5. 모바일이라는 갈래를 여는 데 필요한 것

화면 코드보다 이쪽이 먼저 막힌다. **iOS 와 Android 는 막히는 지점이 서로 다르다.**

| | iOS (Swift) | Android (Kotlin) |
| --- | --- | --- |
| Bazel 규칙 | `apple_support` · `rules_swift` · `rules_apple` | `rules_kotlin` · `rules_android` |
| 밖에서 깔아야 하는 것 | **정식 Xcode** (10~15GB) | Android SDK |
| 빌드되는 OS | **macOS 만** | 리눅스에서도 된다 |
| CI | **macOS 잡을 새로 만들어야 함** | 기존 ubuntu 잡이 그대로 처리 |
| BUILD 파일 | Gazelle 이 만들어 준다 (`swift_gazelle_plugin`) | **손으로 쓴다 — 쓸 만한 Gazelle 확장이 없다** |
| 스캐폴드 | `just new-app-ios <name>` | `just new-app-android <name>` |

이 비대칭이 §7 작업 순서를 정하는 근거다. 준비 비용만 보면 Android 가 가볍지만
**iOS 를 먼저 만들기로 했다** — 이유는 §7 에 적는다.

### 5-1. Bazel 규칙 활성화

`MODULE.bazel` 에 두 블록이 주석으로 대기하고 있다.

- **Swift/Apple**: `apple_support` 2.8.0, `rules_swift` 3.6.1, `rules_apple` 4.5.3,
  `rules_swift_package_manager` 0.34.0
- **Kotlin/Android**: `rules_kotlin` 2.4.0, `rules_android` 0.7.3

**Apple 블록은 팀 전체에 영향이 있다.** ADR 0002 의 실측 기록에 따르면 `apple_support` 를
선언하기만 해도 정식 Xcode 없이 Command Line Tools 만 있는 macOS 에서는 iOS 타깃이 하나도
없는데도 `bazel build //...` 전체가 크래시한다(`DottedVersion` 파싱 실패). 즉 이 규칙을 푸는
순간 **백엔드만 만지는 권호와 AI 만 만지는 태환도 Xcode 를 설치해야** `just check` 가 돈다.

푸는 시점을 두 사람에게 미리 알린다. 세 명 모두 맥북을 쓰므로 설치 자체는 가능하지만
10~15GB 다운로드가 걸린다. **Android 블록에는 이런 부작용이 없다** — 먼저 풀어도 안전하다.

### 5-2. Android BUILD 파일은 손으로 쓴다

ADR 0002 와 `MODULE.bazel` 이 같은 내용을 적어 뒀다. Aspect 의 Kotlin Gazelle 플러그인은
스스로 EXPERIMENTAL 이라 밝히고 `kt_jvm_library`·`kt_jvm_binary` 만 만든다. 우리가 정작
필요한 `android_library`·`android_binary`·`kt_android_library` 를 만들어 주지 못하고,
Gazelle 에 Android 확장은 공식·비공식 모두 사실상 없다.

그래서 `just gen` 이 Android 모듈의 BUILD 파일을 갱신해 주지 않는다. **소스를 추가할 때마다
BUILD 파일을 직접 고쳐야 하고, 잊으면 "파일은 있는데 빌드에 안 들어간" 상태가 된다.**
Android 모듈 README 에 이 사실을 적어 둔다.

### 5-3. iOS 타깃에 플랫폼 제약을 건다

```python
target_compatible_with = ["@platforms//os:macos"]
```

`just ci-full` 은 `bazel test //...` 를 돌린다. `//...` 는 저장소의 모든 타깃이라 iOS 도
포함되고, 리눅스 러너가 그것을 빌드하려다 실패한다. 이 선언이 있으면 Bazel 이 호환되지 않는
타깃을 자동으로 건너뛴다.

이것은 검사를 회피하는 장치가 아니라 **"이 타깃은 이 플랫폼에서만 지어진다"를 코드에 적는
것** 이다. 같은 `just ci-full` 명령이 리눅스 잡과 macOS 잡 양쪽에서 각자 할 일을 하게 된다.

**Android 타깃에는 이 선언을 붙이지 않는다.** 리눅스에서도 지어지므로 붙이면 오히려 기존
ubuntu 잡의 검사 범위에서 빠진다.

`platforms` 모듈은 이미 `MODULE.bazel` 에 있다. 다만 `target_compatible_with` 를 쓰는 것은
이번이 처음이라 저장소 문서 어디에도 용례가 없다 — `docs/engineering/onboarding.md` 의
Bazel 절에 한 줄 남긴다.

### 5-4. CI 에 macOS 잡을 추가한다

ADR 0002 의 후속 작업 "CI 에 macOS 러너 잡 추가 — 첫 iOS 모듈이 생길 때" 가 지금이다.

`.github/workflows/ci.yml` 의 `verify` 잡은 `ubuntu-latest` 에서 돈다. 리눅스에는 Xcode 가
없어 iOS 앱을 지을 수 없으므로 `macos-latest` 잡을 하나 더 둔다. 워크플로는 얇은 껍데기를
유지하고 파이프라인 로직은 `tools/just/ci.just` 에 남긴다.

저장소가 공개이므로 GitHub 표준 러너는 무료다. 비공개였다면 macOS 는 분 단위 사용량이
10배로 차감돼 미루는 쪽이 합리적이었으나, 공개 전환으로 그 제약이 없어졌다.

**Android 는 이 작업을 기다리지 않는다.** 기존 ubuntu 잡이 그대로 짓는다. 다만 러너에
Android SDK 가 필요하므로 `ubuntu-latest` 이미지에 포함된 것을 쓸지 설치 단계를 넣을지는
모듈을 만들면서 확인한다.

### 5-5. 클라이언트 생성기를 붙인다

[scene-api-search-map.md §9](./scene-api-search-map.md) 가 예고해 둔 작업이다. 서버 인터페이스
(`spring`)는 이미 `contracts/openapi/BUILD.bazel` 에 붙어 있고, `MODULE.bazel` 이
**"생성기 이름만 바꾸면 언어가 바뀐다 — `spring` · `swift5`(iOS) · `kotlin`(Android)"** 라고
적어 뒀다. 앱 모듈이 생기는 지금이 그 시점이다.

**앱은 API 클라이언트를 손으로 쓰지 않는다**([CLAUDE.md §5](../../../CLAUDE.md)). 명세에서
생성한 것을 쓴다. 두 앱이 같은 명세에서 생성한 클라이언트를 쓰는 것이 §1 의 "어긋나지 않게
한다"를 지키는 가장 값싼 방법이기도 하다.

같은 문서가 그 시점에 **도구 선택을 ADR 로 승격** 하라고 적어 뒀다 —
`openapi_tools_generator_bazel` 의 유지보수자 부재 위험을 기록으로 남겨야 하기 때문이다.
ADR 0003 은 이미 쓰였으므로(Spring Boot · Bazel) 다음 번호는 **0004** 다.

### 5-6. 포매터·린터

`just doctor` 가 `swiftformat`·`swiftlint`·`ktlint` 를 "해당 언어 소스가 아직 없어 필요 없음"
으로 대기시켜 두고 있다. `tools/scripts/lint.sh`·`format.sh` 에는 Kotlin·Swift 절이 이미
쓰여 있어 소스가 생기면 바로 걸린다. 도구를 안 깔면 `missing_tool` 로 알려 주지만, 그
상태로 두면 정리되지 않은 코드가 그대로 커밋된다.

## 7. 작업 순서

**iOS 를 먼저 만든다.** 준비 비용만 보면 Android 가 가볍지만, iOS 의 준비 작업이
**팀 전체를 멈춰 세우는 종류**라서다 — 정식 Xcode 설치는 세 명이 각자 10~15GB 를 받아야
하고, 그때까지 `just check` 가 도는지 아무도 확신할 수 없다. 이 불확실성은 미룬다고
줄지 않는다. 반대로 Android 는 언제 시작해도 팀의 다른 작업을 건드리지 않는다.

프로토타입이 iOS 시뮬레이터에서 도는 것도 이유다 — §3 의 항목을 화면끼리 바로 대조할 수 있다.

```
[완료] Flutter 프로토타입으로 화면·검색 규칙 확정   ← ~/workspace/mobile
  ↓
[완료] 계획 문서 (이 파일)
  ↓
[완료] 모듈 이름·순서 확정                          ← §6
  ↓
      팀 공지 — 권호·태환도 Xcode 를 깔아야 한다    ← §5-1
  ↓  (설치 확인될 때까지 아래로 못 간다)
      MODULE.bazel Apple 블록 활성화                 ← §5-1
  ↓
      just new-app-ios scenetrip-ios
  ↓
      target_compatible_with 선언 → just check 초록  ← §5-3
  ↓
      CI macOS 잡 추가                               ← §5-4
  ↓
      swift5 클라이언트 생성 타깃 + 도구 ADR 0004    ← §5-5
  ↓
      iOS 화면 구현 (§3 을 기준으로)
  ↓
      just check → PR
  ↓
  ─────────── 여기서부터 Android ───────────
      MODULE.bazel Kotlin/Android 블록 활성화        ← §5-1
  ↓
      just new-app-android scenetrip-android
  ↓
      BUILD 파일 손으로 작성 (Gazelle 없음)          ← §5-2
  ↓  기존 ubuntu CI 가 이미 검사한다 — 새 잡 불필요
      Android 화면 구현 (§3 을 같은 기준으로)
  ↓
      두 앱 대조 → just check → PR                   ← §8
```

**§5 를 먼저 끝내야 화면 작업이 시작된다.** 순서를 뒤집으면 소스 파일은 쌓이는데 Bazel 이
그것을 짓지 못하는 상태가 되고, [CLAUDE.md §0](../../../CLAUDE.md) 의 제1법칙("Bazel 이 짓지
못하면 완료가 아니다")에 걸린다.

화면 구현은 §3 의 소제목이 그대로 티켓 단위가 된다 — 화면 구조 / 검색 범위 / 자동완성 /
지도 연동. 각각이 독립적으로 확인 가능하고 크기도 비슷하다.

**서브태스크 하나가 두 플랫폼을 덮는다.** iOS 를 먼저 만들기로 했으므로, 이는 iOS 가 끝나도
서브태스크가 한동안 진행 중으로 남는다는 뜻이다. 그 상태를 감수한다 — iOS 만 된 것을 완료로
찍으면 보드가 "검색 탭 끝남" 으로 보이는데 실제로는 사용자 절반이 못 쓰는 상태다. iOS 가
어디까지 됐는지는 **커밋의 서브태스크 키**가 이미 기록한다(AGENTS.md §7.3). 티켓을 닫는 것과
진척을 남기는 것은 다른 일이다.

Android 를 언제 시작할지가 §6 의 남은 결정 #6 이다. 그 답이 나오면 이 문단을 갱신한다.

## 8. 검증

- `just check` 가 초록인가 — macOS 에서는 iOS 타깃까지, 리눅스에서는 그것을 건너뛰고 Android 는 짓고.
- CI 의 두 잡이 각자 자기 몫을 하는가 — 리눅스 잡이 **iOS 만** 건너뛴 것을 로그로 확인한다. Android 까지 건너뛰었다면 §5-3 을 잘못 붙인 것이다.
- Android 모듈에 소스를 하나 더해 보고 BUILD 파일을 고치지 않으면 빌드에서 빠지는지 확인한다 — §5-2 의 함정을 팀이 실제로 겪어 두는 편이 낫다.
- §3-2 표의 네 줄이 실제 화면에서 다 되는가. 배우 이름 줄은 서버에서 이미 확인됐으므로(`공유`·`김고은`·`도깨비` → 작품 1건 · 장소 3건, §4), 화면에서는 **그 응답이 두 탭에 제대로 갈라져 들어가는지**를 본다. 같은 세 검색어를 그대로 쓰면 서버 결과와 대조할 수 있다.
- **두 앱을 나란히 놓고 §3 의 항목을 하나씩 대조한다.** ADR 0002 가 검증 항목으로 건 "두 앱이 어긋나지 않는가"가 이것이다.
- 프로토타입과도 나란히 놓고 화면 동작을 비교한다.
