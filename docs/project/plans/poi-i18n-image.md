## 1. 무엇을 하는가

편의시설(POI)을 **우리가 직접 정보를 모으는 우리 앱의 POI** 로 키운다. 그 첫걸음으로 표를 셋 만든다.

| 표 | 담는 것 |
| --- | --- |
| `poi_i18n` | 가게마다 다른 글 — 이름·주소의 번역 |
| `poi_term_i18n` | 여러 가게가 나눠 쓰는 낱말 — 분류·시도·시군구의 번역 (→ 분류만 남긴다, §6-2) |
| `poi_image` | 우리가 모은 사진 |

네이버 카드(`poi_naver`)는 **더 쓰지 않는다.** 모은 것은 백업해 두고, 표와 코드는 지우지 않는다
— 나중에 쓸 일이 생기면 다시 쓴다.

## 3. 결정

| 결정 | 근거 |
| --- | --- |
| 한국어 원본은 `poi` 에 그대로 둔다. `poi_i18n` 에는 **번역만** 든다 | 대부분의 POI 는 오래 한국어뿐이다. 폴백이 `COALESCE(번역, poi.name)` 한 번의 조인으로 끝나고, 한국어 화면의 지도 조회와 기존 한국어 검색 인덱스가 그대로다. `place` 는 처음부터 다국어라 `ko` 도 i18n 에 두었다 — 사정이 다르다. V12 주석의 「name 을 옮긴다」 는 이 결정으로 대신한다 |
| 분류·지역은 낱말 사전 하나(`poi_term_i18n`)로 번역한다 **(지역은 2026-10-05 뒤집힘 → §6-2)** | 95만 가게가 42 개 분류를 나눠 쓴다. 가게마다 "Cafe" 를 적으면 12 만 번 반복되고, 표기를 고칠 때 12 만 줄을 고친다. 사전이면 한 줄이다 |
| 사전에 FK 를 걸지 않는다 | `poi.category` 는 출처가 정하는 값이다. FK 를 걸면 출처가 새 분류를 들고 왔을 때 **적재가 실패한다.** 걸지 않으면 새 분류는 일단 한국어로 보이고, 사전에 한 줄 넣는 순간 번역된다. 빠진 낱말은 질의 하나로 찾는다(§4-2) |
| `poi_image` 는 `place_image` 모양에 **출처·저작자** 를 더한다 | 우리가 모으는 사진이라 누가 찍었고 어디서 왔는지가 남아야 한다. 라이선스 표기 의무가 있는 출처(관광공사 등)가 있다 |
| 네이버 카드 백업은 `source_id` 를 함께 뜬다 | `poi_naver` 는 내부 `poi.id` 를 들고 있다. `just seed-poi --prune` 으로 출처를 갈면 id 가 바뀌므로, 되살릴 때 잇는 열쇠는 `source_id` 다 |
| 백업 파일은 저장소에 넣지 않는다 | 비공식 경로로 받은 자료다(ADR 0011, 데모 한정) |
| 이번 단계는 계약을 바꾸지 않는다 | 빈 표를 만들 뿐 응답 모양이 같다. 계약의 「편의시설은 언제나 `ko`」 도 그대로 참이다 |

## 4. 스키마 (V17)

### 4-1. `poi_i18n`

```sql
poi_id       BIGINT REFERENCES poi (id) ON DELETE CASCADE
lang         lang_code          -- 'ko' 는 넣지 않는다. 원본은 poi 에
name         TEXT NOT NULL
address      TEXT
road         TEXT
trans_status trans_status       -- place_i18n 과 같은 뜻 (기계 번역·검수 등)
PRIMARY KEY (poi_id, lang)
CHECK (lang <> 'ko')
```

영어 이름 검색용 trigram 인덱스(`search_normalize(name)`)를 함께 건다 — `poi_name_trgm_idx` 와 같은 꼴.

### 4-2. `poi_term_i18n` (→ `poi_category_i18n` 으로 바뀌었다, §6-6 3a)

```sql
kind  TEXT  CHECK (kind IN ('category', 'region', 'city'))
ko    TEXT  -- poi 의 그 컬럼 값 그대로. 예 ('category', '카페')
lang  lang_code
name  TEXT NOT NULL                     -- 예 'Cafe'
PRIMARY KEY (kind, ko, lang)
CHECK (lang <> 'ko')
```

`city` 는 이름이 겹친다(서울 중구·부산 중구). 영어 표기도 같으므로(`Jung-gu`) 낱말로만 잇는다.

새 분류가 생겼는데 번역이 빠졌는지는 이것으로 본다.

```sql
SELECT DISTINCT p.category FROM poi p
LEFT JOIN poi_term_i18n t ON t.kind = 'category' AND t.ko = p.category AND t.lang = 'en'
WHERE t.ko IS NULL;
```

### 4-3. `poi_image`

```sql
id         BIGSERIAL PRIMARY KEY
poi_id     BIGINT REFERENCES poi (id) ON DELETE CASCADE
url        TEXT NOT NULL
sort_order INT NOT NULL DEFAULT 0   -- 첫 번째가 대표. place_image 와 같은 규칙
source     TEXT                     -- 어디서 왔나 (예 'tour_api', 'own')
credit     TEXT                     -- 화면에 붙일 저작자·라이선스 표기
created_at TIMESTAMPTZ
UNIQUE (poi_id, url)               -- 수집을 다시 돌려도 같은 사진이 늘지 않게
INDEX (poi_id, sort_order)
```

사진 파일을 어디에 두는지(S3·CDN)는 이 문서의 범위가 아니다. 표는 주소만 든다.

`--prune` 적재에서 지워지는 POI 의 번역·사진은 CASCADE 로 함께 지워진다 — 가게가 없어졌으므로 맞다.
**(2026-10-05: 「지워지면 가게가 없어진 것」 이라는 전제가 틀렸다 → §6-4)**

### 6-1. 원본·변환·DB 는 일치한다

  빈 시도 899 행은 거의 `여행코스` 다.

### 6-2. 시도·시군구를 따로 번역하지 않는다 — 주소 한 줄로

`region`·`city` 는 서버가 `PoiDetail` 에 실어 보낼 뿐 거르기·검색·앱·에이전트 어디서도 쓰지 않는다.
사람이 보는 것은 주소 한 줄이다. 그래서:

- `region`·`city` 컬럼은 원본으로 **남겨 둔다**(지역 필터가 생기면 쓴다). 번역하지 않는다.
- `poi_term_i18n` 의 `region`·`city` 는 쓰지 않는다 — **분류 전용 `poi_category_i18n` 으로 줄인다.**
  V17 은 아직 커밋 전이고 로컬 DB 에만 올라가 있으므로 고쳐 쓴다(로컬은 V17 을 내렸다 다시 올린다).
- 교통·관광 시도 1,130 행은 화면에 안 나오므로 지금 고치지 않는다.

### 6-3. 영문 주소는 행정안전부 영문도로명주소DB 로 붙인다 — 번역하지 않는다

[영문도로명주소DB](https://www.data.go.kr/data/15050414/fileData.do) — 무료·이용 제한 없음, 월 단위 전체분과
변동분. 받으려면 business.juso.go.kr 에서 신청·본인인증이 필요하다(사람이 받는다). 레이아웃은 공개
「영문도로명주소DB 활용가이드」 의 18 칸 — 열쇠는 `도로명코드(12)`·`건물본번`·`건물부번`·`지하여부`,
기본 키는 `건물관리번호(25)`.

상가정보 원본에 같은 열쇠가 있다. 실측(상가정보 920,738 행 ↔ 영문 DB 8,194,644 행):

| 맞춘 열쇠 | 행 | 비율 |
| --- | --- | --- |
| 건물관리번호 | 915,251 | 99.40 % |
| 도로명코드 + 건물번호 | 3,645 | 0.40 % |
| 못 맞춤 | 1,842 | 0.20 % |

**열쇠 순서는 도로명코드 + 건물번호 먼저, 건물관리번호는 보조다.** 원본 한 행 안에서 두 열쇠가 다른 건물을
가리키는 행이 있다 — 예: 「울엄마」 의 도로명주소는 `둔내로 66` 인데 건물관리번호는 이웃한 `둔내로 64-1`
건물의 것이다(원본부터 그렇다). 다른 번지를 가리키는 행이 587 개이고 그중 443 개가 전남광주다. 화면의
한국어 주소가 도로명주소이므로 같은 열쇠로 찾아야 한국어·영어가 같은 번지를 말한다. 표본 확인: 영화국밥
(초안산로 7)은 도로명주소 쪽이 맞았고, 둘은 지도에 없었다(폐업 추정).

표기는 `{본번[-부번]} {영문 도로명}, {읍·면이면 읍면}, {시군구}, {시도}` — 예
`25 Gumi-ro 9beon-gil, Bundang-gu, Seongnam-si, Gyeonggi-do`. 지하 건물 표기(`B…`)는 아직 임시다 —
공식 표기를 확인한다. 원본에 지상·지하 구분이 없으므로 같은 번지가 둘이면 지상을 고른다.

못 맞춘 0.2 % 는 영문 주소 없이 둔다(한국어로 폴백).

**관광공사·교통(DB 의 40,416 행, 위 658 포함)** 은 도로명코드가 없고 주소 문장뿐이다. 실측(2026-10-05):

1. 문장에서 「도로명 + 건물번호」 를 뽑는다(띄어쓰기 변형 `지하 396`·`한강대로 23길 55`·`마산역광장로18` 을
   먼저 붙인다). 영문 DB 에는 한국어 도로명이 없으므로 **상가정보 원본 277 만 행에서 만든 「한국어 도로명 →
   도로명코드」 사전**을 다리로 쓰고, 같은 이름의 도로가 여럿이면 POI 좌표에서 3 km 안의 가장 가까운 것을 고른다.
   도로명이 없는 지번 주소는 영문 DB 의 지번 열쇠(법정동코드·산·본번·부번)로 — 법정동명 → 법정동코드도 같은
   사전에서. → **32,094 행(79.4 %)**. 영문 시도가 한국어 주소의 시도와 다른 것은 1 건이고 그것도 맞았다
   (군위군은 2023 년 대구 편입).
2. 남은 것 중 주소가 제대로 적힌 2,623 행을 행정안전부 **영문주소 검색 API**(`addrEngApi.do`)로 —
   **1,675 행**(결과 1 건이거나 같은 번지가 겹친 여러 건).
3. API 가 0 건인 것은 주소를 건물번호까지 잘라(`… 623 (잠원동) 우일빌딩 4층` → `… 623`) 다시 — **90 행**.
   시도·시군구를 떼고 도로명 + 번호만으로 찾는 것은 **쓰지 않는다** — 같은 이름 도로가 전국에 있어 경주
   `용담로 107` 이 제주로 나왔다.

| | 행 | 영문 주소 |
| --- | --- | --- |
| 상가정보 | 908,442 | 99.8 % |
| 관광공사·교통 | 40,416 | 33,859 (83.8 %) |
| 전체 | 948,858 | 약 99.1 % |

못 채우는 약 8,400 행 — 주소가 덜 적힌 산·섬·해변·버스정류소 5,699, 건물 없는 지번(공원·광장·비석) 684,
API 로도 없는 주소 154, 상가정보 못 맞춤 1,842 — 는 **한국어 주소를 그대로 보인다**(2026-10-05 결정).

영문 DB 로 조립할 때도 이 꼴을 따른다. API 키는 저장소에 두지 않는다(환경변수 `JUSO_ENG_API_KEY`).

**관광공사 원본에 붙은 영문·일문 목록은 그대로 쓰면 안 된다.** 국문↔영문 contentid 가 달라 좌표 11 m 로
이었는데, 이웃한 다른 장소가 붙은 행이 있다 — `오대산로 164` 음식점에 `Odaesan National Park`,
`가야대로 779` 관광지에 `Gakkaun Pharmacy`. 이름을 쓰려면 이름 유사도 검증을 거친다.

### 6-4. 분기 갱신 — 상가업소번호는 같은 가게의 열쇠가 아니다

상가정보는 분기마다 나온다(공식 설명은 「영업 중인 전국 상가업소 데이터」, 주기 「분기」 뿐이다. 폐업을
어떻게 빼는지는 명시돼 있지 않다). 다음 판은 2026-10-31 예정. 2025-12 판과 2026-06 판을 상가업소번호로
비교했다(음식·숙박):

| | 행 |
| --- | --- |
| 12월판 · 6월판 | 879,565 · 920,738 |
| 두 판 모두 | 760,385 |
| 12월에만(사라짐) | 119,180 (13.5 %) |
| ↳ 같은 이름이 30 m 안에 새 번호로 있음 | 42,406 |
| ↳ 같은 도로명주소·같은 소분류에 새 번호가 있음 | 14,157 — 이름만 바뀐 같은 가게와 폐업 뒤 새 가게가 섞여 있다 |
| ↳ 남는 폐업 후보 | 62,617 (12월판의 7.1 %) |

- **폐업은 빠진다.** 폐업 후보 표본 6 곳 중 5 곳이 지도에 없었다. 나머지 1 곳(`종로플레이스`, 창경궁로 120)은

  **번호도 새로 바뀌었다.** 상호명에 「스타벅스」 가 든 행이 12월판 20 → 6월판 2,154.
- **번호는 이름 정정·행정구역 개편만으로도 바뀐다**(예: 인천 중구 → 영종구). 6개월에 적어도 4 만 2 천 곳.
  두 판에 모두 있는 가게도 75,010 곳의 도로명주소가 바뀌었다 — 영문 주소는 분기마다 다시 맞춘다.

그래서 지금 적재(`source_id` UPSERT + `--prune`)로 분기 갱신을 하면 이름만 바뀐 가게도 지워졌다 새로
들어오고, 우리가 붙인 번역·사진(CASCADE)과 사용자 코스가 끊긴다. 다음 판 전에 정할 것:

1. 번호가 같으면 같은 가게. 번호가 달라도 **같은 도로명주소 + 같은 소분류 + 비슷한 이름**이면 같은 가게로
   잇는다(`source_id` 를 새 번호로 갈고 `poi.id` 는 유지).
2. 이어지지 않는 가게는 지우지 않고 **폐업 표시**(소프트 삭제)한다 — 번역·사진·코스가 남는다.
3. 사용자 코스에 담긴 POI 가 폐업했을 때 앱에 무엇을 보일지.

## 8. 덧붙임 (2026-10-05) — 분기 갱신 `just seed-poi --update`

§6-4 의 「다음 판 전에 정할 것」 을 정했다. 지금 있는 두 방식은 둘 다 분기 갱신에 맞지 않는다 — 기본은
폐업이 쌓이고, `--prune` 은 번호만 바뀐 같은 가게를 지웠다 새로 넣는다(붙인 번역·사진이 사라진다).
세 번째 방식 `--update` 를 만든다.

### 8-1. 가게마다 넷 중 하나

| 경우 | DB 에서 |
| --- | --- |
| 같은 `source_id` 가 새 판에 있다 | 갱신 (지금과 같다). 폐업 표시가 있었으면 지운다 — 다시 문을 연 것 |
| 없지만 **같은 가게로 보이는** 새 번호가 있다 | 기존 행의 `source_id` 만 새 번호로 갈아 끼운다. `poi.id` 와 거기 붙은 행은 그대로 |
| 없고 이어 줄 것도 없다 | 지우지 않고 **폐업 표시**(`closed_at`) |
| 새 번호인데 이어 줄 기존 가게가 없다 | 추가 |

폐업 표시된 POI 는 서버가 지도·검색·상세 어디에도 내보내지 않는다(상세는 404 — 계약에 이미 있는 응답이라
계약 변경이 없다). 지우지 않는 까닭: 잘못 판정해도 되돌릴 수 있고, 우리가 붙인 번역·사진과 나중의 사용자
코스가 남는다.

### 8-2. 「같은 가게로 보인다」 — 좌표 30 m 안에서, 셋 중 하나

이름은 소문자로 바꾸고 공백·괄호·`·.,&_/-` 를 지운 뒤 비교한다.

| 규칙 | 분류 |
| --- | --- |
| 이름이 같다 | 상관없다 — 공단이 분류만 다시 매긴 경우가 많다(`황금포차` 백반 → 요리 주점) |
| 한쪽 이름이 다른 쪽에 들어 있다. 짧은 쪽이 3 글자 이상 | 같아야 한다 (`구리갈매역` → `스타벅스 구리갈매역`) |
| 글자 편집 거리 비율 `1 − levenshtein / 긴 쪽 길이` ≥ 0.8 | 같아야 한다 (`피자스쿨신풍점` → `피자스쿨신풍역점`) |

후보가 여럿이면 규칙 순서 → 가까운 순으로 고르고, **양쪽 모두에게 서로가 최선인 쌍만** 잇는다(새 번호 하나는
옛 가게 하나에만). 애매하면 잇지 않는다 — 놓치면 「폐업 + 새 가게」 가 되어 숨긴 행이 남지만, 잘못 이으면
다른 가게에 우리 정보가 붙어 나가고 티가 안 난다.

**같은 출처끼리만 비교한다.** 출처는 `source_id` 앞의 영문(`MA`·`tour`·`busstop`…)이다. 입력에 없는 출처의
POI 는 갱신이 건드리지 않는다 — 상가정보 파일만 넣어도 관광지가 폐업되지 않는다.

### 8-3. 실측 — 2025-12 판을 「기존 DB」, 2026-06 판을 「새 판」 으로 (음식·숙박, 제외 분류 뺌)

| | 행 |
| --- | --- |
| 사라진 번호 · 새 번호 | 114,365 · 153,005 |
| 이름 같음(분류 상관없이) | 42,154 |
| 포함(같은 분류) | 3,040 — 짧은 쪽 2 글자 이하 225 는 잇지 않는다 |
| 비슷함 | 777(파이썬 difflib 0.8) — DB 의 편집 거리 0.8 로는 559 |
| **폐업 판정** | **약 6 만 8 천 (12월판의 8.1 %)** |

편집 거리 기준은 이어야 할 쌍 777 과 잇지 말아야 할 쌍(같은 분류·5 m·이름 다름) 2,000 표본으로 골랐다 —
0.8 은 잘못 이음 0, 0.7 은 19(`둘둘치킨망양점 → 자담치킨망양점` 같은 브랜드 교체). `pg_trgm` 유사도 0.5 는
510·2 였다. 사람 확인: 이은 쌍 표본 6 곳 모두 같은 가게였다(네이버 지도). 공단 새 판의 이름이 오히려 실제와
다른 경우가 있다(`뉴황제단란주점` → 6월판 `황제단란주점`, 지도는 앞의 이름) — 우리 출처가 공단인 이상 최신판
이름을 따른다.

### 8-4. 구현

- V18: `poi.closed_at TIMESTAMPTZ`.
- `seed/poi_update.sql` — 순수 SQL(psql 메타 명령 없음). `t_load` 와 `poi` 를 받아 잇기·폐업 표시를 한다.
  `poi.sql` 이 `--update` 일 때 UPSERT 바로 앞에서 부른다. 순수 SQL 이라 통합 시험이 같은 파일을 JDBC 로

가게 이름의 공식 영어 자료는 없다. 상가정보에 영어 이름 칸이 없고, 정부도 가게 이름(고유명사)의 영어를
갖고 있지 않다. 그래서 **당분간 이름은 한국어**로 둔다 — 간판이 한글이라 외국인이 지도와 간판을 맞춰
보기에도 한국어가 낫다. `poi_i18n.name` 은 비워 둘 수 있게 한다(§11).

네이버 지도의 영어 이름은 두 갈래로 보인다(공식 설명은 못 찾았다 — 추정이다). `PARKCHANHU TUNA` 는 사업주가
넣은 꼴이고, `Nuri Maeul Back-bone Stew`(누리마을감자탕)는 고유명사는 로마자, 음식 낱말은 번역한 꼴이다.
뒤의 것은 우리도 만들 수 있다. 재료는 둘 다 공식 기준이 있다.

| 재료 | 기준 |
| --- | --- |
| 고유명사 → 로마자 | 국어의 로마자 표기법(문화체육관광부 고시) — 규칙이라 프로그램으로 바꾼다 |
| 음식 낱말 → 영어 | 한식진흥원 주요 한식명 외국어 표기 표준(약 800 메뉴. 예: 감자탕 Gamja-tang (Pork Back-bone Stew)) |

여기에 프랜차이즈 사전(`스타벅스 → Starbucks` — 외래어가 로마자로 망가지는 것을 막는다)과 관광공사 공식
영문명(검증 뒤)을 더한다. 만든 이름은 `trans_status = 'machine'`. 어려운 곳은 이름을 「고유명사 + 음식 낱말」
로 쪼개는 일이다(`할머니순대국밥`, `역전할머니맥주`). 영문 주소(3d) 다음에 표본 수백 개로 실험해 품질을 본다 —
단계 3g. 기계 번역은 고유명사를 뜻으로 옮겨(`동구짬뽕` → 「East Gate Champon」) 쓰지 않는다.

## 11. 덧붙임 (2026-10-05) — 영문 주소 적재(3d) 설계

```
[1] just poi-addr-en <POI 폴더> <영문도로명주소DB zip> <상가정보 zip> <결과 폴더>      (로컬, tools/poi)
      각 POI 줄에 addr_en · addr_en_source(juso_db | juso_api) 를 덧붙인 jsonl 을 결과 폴더에 쓴다
[2] just seed-poi [--update] <결과 폴더>/poi_*.jsonl                                   (기존 적재)
      addr_en 이 있으면 poi_i18n(en).address 로 UPSERT, 없어졌으면 비운다
```

- [1] 은 §6-3 의 실측 그대로다. 상가정보는 도로명코드 + 건물번호 → 건물관리번호. 관광공사·교통은 문장에서
  도로명·건물번호(없으면 법정동·지번)를 뽑아 상가정보 원본에서 만든 「한국어 도로명 → 도로명코드」 사전으로 잇는다.
  남는 것은 `JUSO_ENG_API_KEY` 가 있을 때만 API 로 — 결과 1 건이거나 같은 주소가 겹친 것만 받고, 0 건이면
  건물번호까지 잘라 한 번 더. 시도·시군구를 떼고 찾지 않는다(§6-3).
- API 결과는 결과 폴더의 캐시 파일에 남겨 다시 돌릴 때 부르지 않는다.
- 표기는 공식 꼴 `55 Hangang-daero 23-gil, Yongsan-gu, Seoul` — 번지 뒤 쉼표 없음. 영문 DB 로 조립한 것과 API
  표기를 표본으로 대조한다.
- 결과는 파일이라 서버 적재(3f)도 같은 파일을 쓴다. 분기 갱신 때도 [1] → [2] 를 다시 하면 바뀐 주소가 따라온다.
- `poi_i18n.name` 은 NULL 을 허용한다 — 칸마다 따로 폴백한다(`COALESCE(t.name, p.name)`, `COALESCE(t.address, p.address)`).
  V17 은 main·서버에 올라가지 않아 새 마이그레이션 없이 고쳐 쓴다.
