## 1. 무엇을 하는가

POI 하나가 **출처 번호를 여러 개** 가지게 한다(`poi_source`). 지금은 `poi.source_id` 하나뿐이라 적재 때 합친 줄의 번호가
사라진다. 그 번호가 있어야 관광공사 상세(사진·개요·영업시간)를 상가정보 POI 에 붙일 수 있고, 분기 갱신이 다른 출처의 같은
가게를 폐업으로 잘못 처리하지 않는다.

## 2. 실측 (2026-10-09, 로컬 kind DB · 2026-06 판)

### 2-1. 원본 줄마다 어느 POI 가 됐나

### 2-2. 아직 합쳐지지 않은 같은 가게

같은 건물(도로명 + 건물번호) 안에서 이름을 비교했다. 이름 유사도는 기호를 지우고 자모로 쪼갠 편집 거리 비율.

| | 쌍 | 표본으로 본 판정 |
| --- | --- | --- |
| 관광공사 ↔ 상가정보, 같은 건물 · 유사도 0.8 이상 | 258 | 거의 전부 같은 가게(`들국화떡볶이/들국화떡볶기`) |
| 관광공사 ↔ 상가정보, 같은 건물 · 0.6~0.8 | 359 | 넷 중 셋쯤 같은 가게 |
| 상가정보끼리, 같은 건물 · 이름 같음 | 685 | 거의 전부 같은 가게(인허가 기록 두 줄) |
| 상가정보끼리, 같은 건물 · 이름 포함 | 4,553 | 섞임(`달봉비어/달봉비어 평촌점` 같음, `행복한/행복한빵세상` 다름) |
| 상가정보끼리, 같은 건물 · 유사도 0.6 이상 | 약 4 만 | **대부분 다른 가게** — 공통 지점명(`버거킹/던킨 원주기업도시점`), 호실(`마리나큐브 710호/1217호`) |

다른 건물인데 이름이 비슷하면 다른 가게가 섞인다(`김영애할머니순두부/김정옥할머니순두부`). **같은 건물인지가 결정적이다.**
지금 §4-1 은 포함 비교에 최소 길이가 없어 이름이 전혀 다른 짝으로 뺀 관광공사 줄도 있다(136 중 일부, `공탄/낭만`).

### 2-3. 지금 갱신 규칙의 구멍

`poi_update.sql` 은 같은 출처끼리만 잇는다. 그래서

1. 상가정보에 없던 관광공사 음식점이 POI 로 들어가 있다가, 다음 판에 상가정보가 같은 가게를 들고 오면 §4-1 이 관광공사 줄을
   뺀다 → 그 POI 는 사라진 번호가 되고 이을 같은 출처 후보가 없어 **폐업 표시**, 상가정보 가게는 **빈 새 POI**.
2. 반대로 상가정보가 가게를 빼면 그 POI 는 폐업 표시되고, 가려져 있던 관광공사 줄이 **새 POI 로 되살아난다** — 문 닫은 가게가
   다시 지도에 나온다. 옛 POI 에 붙인 번역·사진은 폐업 POI 에 남는다.

### 2-4. POI 를 지우면 같이 지워지는 것

`ON DELETE CASCADE` 로 POI 를 참조하는 표: `poi_i18n`·`poi_image`(V17), `review`(V21), `place_poi_link`(V25),
`course_item.poi_id`(V26), `poi_naver`(V14). **POI 하나를 지우면 사용자 리뷰와 코스 항목이 함께 사라진다.** `just seed-poi
--prune` 은 이번 입력에 없는 POI 를 지운다.

## 3. 결정

| 결정 | 근거 |
| --- | --- |
| POI 는 출처 번호를 여러 개 가진다(`poi_source`). `poi.source_id` 는 대표 번호로 남긴다 | 합친 줄의 번호가 있어야 관광공사 상세를 붙이고(§2-1 의 11,664 + 685), 갱신이 다른 출처 줄을 같은 POI 로 찾는다(§2-3). 대표 번호를 남기면 지금 코드·시험이 그대로다 |
| 첫 채움은 §2-1 의 재구성 결과로 한다 | DB 와 한 줄도 어긋나지 않음을 확인했다. 적재 SQL 이 다음부터 같은 기록을 스스로 남긴다 |
| 새로 합치는 것은 **같은 건물 + 이름 유사도 0.8 이상**(관광공사 ↔ 상가정보)과 **같은 건물 + 이름 같음**(상가정보끼리)만 | 표본에서 거의 전부 같은 가게였다(§2-2). 애매한 쌍은 합치지 않는다 — 놓치면 핀이 둘일 뿐이지만, 잘못 합치면 한 가게가 지도에서 사라지고 남의 정보가 붙어도 티가 안 난다 |
| §4-1 의 이름 포함에 최소 길이(짧은 쪽 3 글자)를 둔다 | 갱신 규칙(poi-i18n-image.md §8-2)과 같게. 이름이 전혀 다른 짝으로 빼는 일을 막는다 |
| **영업 여부는 정해진 출처 하나가 판단한다.** 상가정보 번호가 있는 POI 는 상가정보, 관광공사에만 있는 POI 는 관광공사 | 관광공사가 줄을 빼는 이유는 알 수 없다(`showflag` 는 사유를 주지 않는다. 지역 코드 이관으로 목록에서 빠진 다른 팀 사례도 있다). 상가정보는 인허가 기록으로 판마다 다시 만들어진다 |
| 판단하지 않는 출처가 빠지면 그 번호에 「이번 판에 없음」 만 남긴다 | 폐업이 아니다. 판단하는 출처가 빼면 POI 를 폐업 표시하되, 다른 출처 번호는 붙은 채 남아 다음 적재에서 그 줄이 같은 POI 를 찾는다 — 새 POI 로 되살아나지 않는다 |
| **POI 는 지우지 않는다.** 폐업은 `closed_at` 만. `--prune` 을 막는다 | §2-4 — 리뷰·코스·번역·사진이 같이 사라진다. 폐업 표시는 되돌릴 수 있다 |
| 판마다 「두 출처의 말이 다른 POI」 목록을 찍는다 | 상가정보가 실수로 가게를 뺀 경우를 사람이 본다 |

## 4. 스키마 (V27)

```sql
CREATE TABLE poi_source (
    source_id   TEXT PRIMARY KEY,              -- 'MA…' · 'tour-…' · 'busstop-…' — 출처가 준 번호
    poi_id      BIGINT NOT NULL REFERENCES poi (id),   -- CASCADE 없음: POI 는 지우지 않는다
    source      TEXT NOT NULL,                 -- 'store' · 'tour' · 'other' (번호 앞부분)
    how         TEXT NOT NULL,                 -- 'own'(그 POI 의 줄) · 'same_name_1m' · 'shadowed_100m' · 'same_building'
    last_seen   TEXT,                          -- 마지막으로 입력에 있던 판(예 '2026-06'). 판단하지 않는 출처가 빠진 것을 이것으로 안다
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON poi_source (poi_id);
```

`poi.source_id` 는 그 POI 의 대표 번호로 `poi_source` 에도 한 줄(`how = 'own'`) 있다. 관광공사 상세를 붙일 때는
`poi_source` 에서 `tour-<contentid>` 로 POI 를 찾는다.

## 5. 적재·갱신 순서 (seed/poi.sql · poi_update.sql)

들어온 줄마다 위에서부터 걸리면 멈춘다.

1. **번호로 찾기** — `poi_source` 에 그 번호가 있으면 그 POI 를 갱신하고 `last_seen` 을 새 판으로.
2. **같은 출처끼리 잇기** — 지금의 `--update` 규칙(30 m · 이름, 서로 최선). 이으면 새 번호를 `poi_source` 에 더한다.
3. **다른 출처와 합치기** — 같은 건물 + 유사도 0.8(관광공사 ↔ 상가정보), 같은 건물 + 이름 같음(상가정보끼리), 그리고 지금의 1 m
   · 100 m 규칙. 맞으면 새 POI 를 만들지 않고 번호만 더한다.
4. **새 POI.**

입력이 끝나면 영업 여부를 정한다. 판단하는 출처의 번호가 이번 입력에 없으면 폐업 표시, 다시 나타나면 지운다. 이번 입력에 없는
출처(예: 상가정보 파일만 넣음)는 건드리지 않는다 — 지금 규칙 그대로.

## 6. 관광공사 상세 붙이기

수집 결과(`raw/tourapi/<언어>/detail.jsonl`)를 `poi_source` 로 POI 에 잇는다. MZ2AZ-376 이 부탁한 것:

- 대표 이미지(`firstimage`)와 상세 사진(`detailImage2`)을 `poi_image` 로 — `source = 'tour_api'`, `credit` 에 출처와 저작권 유형
  (`cpyrhtDivCd` Type1 · Type3), 원 contentid.
- 응답 사진 항목에 출처 표기 값 — **계약 먼저**(`Photo` 에 credit·license 류).
- 사진 주소 — **관광공사 주소를 https 로 바꿔 그대로 싣는다**(2026-10-09 결정). 대표 이미지 41,992 중 18,060 이 `http://`
  인데, 표본 16 장을 `https://` 로 바꿔 모두 열렸다(iOS 는 https 만 받는다).
- **우리 S3 로 옮기는 것은 나중**. 관광공사 서버가 느리거나 사진이 사라지는 일이 실제로 생기면, 또는 상세 사진 수집이 끝나 한꺼번에
  옮길 때. 표본 30 장 평균 387 KB(최대 1.4 MB) → 대표 이미지 약 16 GB, 상세 사진까지 약 100 GB(어림). 그때 정할 것:
  - **버킷을 새로 만들지.** 지금 리뷰 사진 버킷(`scenetrip-user-media-…`, 서명된 주소로 내보냄)에 폴더만 나눠 넣으면 인프라가 그대로다.
    새로 만들 이유는 성격이 다른 자료라는 것 — 사용자 사진은 탈퇴·삭제 규칙과 권한을 좁게 두는 개인 자료이고, 관광공사 사진은 공개
    라이선스 자료라 공개 읽기·CDN·다른 보관 규칙이 맞을 수 있다. 비용도 따로 보인다.
  - 관광공사 약관이 복사본을 우리 저장소에 두고 배포하는 것을 허용하는지. Type3 은 변경 금지라 크기를 줄이거나 자르지 않고 원본 그대로.
    CDN 은 원본을 바꾸지 않으므로 같은 조건이다.
- **썸네일은 관광공사 것을 쓴다.** 목록의 `firstimage2`(대표 이미지가 있는 41,992 곳 모두에 있다)와 상세의 `smallimageurl` 은
  관광공사가 만든 작은 사진이다 — 표본 6 장에서 원본 940 px · 48~591 KB 에 대해 300 px · 11~76 KB(약 8 분의 1). 목록·지도 카드는
  썸네일, 상세는 원본. 우리가 직접 줄이는 것은 Type1(7,906 장, 변경 허용)만 문제없고, Type3(34,086 장)은 크기 조정이 「변경」 인지
  확인하지 못했다.
- 분기 갱신 때 사진은 POI 에 붙어 있으므로 1 번(번호로 찾기)으로 따라간다.

영문 상세는 관광공사 영문 번호가 국문과 달라 **짝을 다시 지은 뒤** 붙인다 — 영문 이름 끝 괄호의 한국어 이름이 우리 이름과
같은 것만(지금 좌표로 이은 12,711 짝 중 6,738 이 다른 가게였다 — 백화점·아울렛 안).

### 6-1. 결정과 실측 (2026-10-15, 권호)

**보여 줄 칸** — 사진 · 개요 · 이용시간 · 쉬는 날 · 홈페이지 · 주차 · 대표 메뉴(음식점) · 입장료. 국문 상세 21,997 곳에서 값이
찬 비율(관광지 / 음식점 / 쇼핑 / 문화시설): 개요 99 / 98 / 99 / 99 %, 이용시간 95 / 98 / 99 / 97 %, 쉬는 날 95 / 97 / 59 / 97 %,
주차 89 / 92 / 99 / 20 %, 대표 메뉴(음식점) 97 %, 입장료(문화시설) 86 %, 홈페이지(관광지·문화시설) 69 · 92 %. 숙박 부대시설·
유모차·신용카드·문의처는 뺀다. 칸 이름이 종류마다 달라(`usetime`·`opentimefood`·`usetimeculture` …) 적재 때 하나로 모은다.

**계약 1.21.0** — `PoiDetail.info`(`PoiInfo`: 칸마다 `{text, lang}`, 칸마다 요청 언어 → en → ko 폴백(응답 언어 폴백과 같은 순서), 모두 없으면 null, 상세가
없으면 `info` 가 null), `Photo.thumbnailUrl`·`license`(`kogl_type1`·`kogl_type3`, 문구는 앱이 언어에 맞춰).

**표 V37** — `poi_detail`(POI · 언어마다 한 줄, ko 도 여기, 관광공사 번호·수정 시각) · `poi_image` 에 `thumbnail_url`·`license`·
`tour_content_id`. 사진은 언어 공통 — 국문·영문 사진을 한 목록으로 합친다. 적재는 다시 돌려도 된다((poi_id, lang) 덮어쓰기,
같은 주소 사진은 한 번).

**바로 붙는 곳부터** — 국문 목록 49,772 중 **37,985 가 `tour-<번호>` POI** 라 출처 번호 표 없이 붙는다(받은 21,997 중 17,285).
나머지는 §2-1 의 합쳐진 줄이다.

**영문 짝** — 영문 제목은 거의 다 「영어 이름 (한국어 이름)」(15,233 / 15,287). 괄호 속 한국어 이름이 **300 m 안 우리 POI 이름과
같으면**(기호·공백 무시) 짝. 겹친 괄호를 고려해 마지막 괄호를 꺼내고 이름 끝 대괄호(`[면세점(TAX REFUND SHOP)]`)를 무시하면
**13,477 / 15,287 (88 %)** — `tour-` 13,197 · 상가정보 280. 같은 POI 에 둘 이상 붙는 24 곳은 가장 가까운 것 하나. 짝 없는 것:
| 원인 | 곳 |
| --- | --- |
| 우리 POI 에 없음 — 영문에만 있는 병원·의원(의료관광)·축제 | 786 |
| 같은 이름이 300 m~3 km — 백화점·아울렛 안 체인 매장 좌표 차이. **붙이지 않는다**(같은 이름 체인이 여러 곳) | 531 |
| 150 m 안 비슷한 이름 — 「…의원」 꼬리 등 | 355 |
| 국문이 상가정보 가게에 합쳐짐(§2-1) | 81 |

**합쳐진 줄(§2-1 의 11,664)에 상세를 붙이는 기준** — 틀린 짝에 붙이면 다른 가게의 개요·사진이 보인다(지도에서 빠진 것보다
나쁘다). 관광공사 이름 ↔ 남은 상가정보 이름: 같음 8,508 · 유사도 0.8 이상 1,009 → **붙인다**. 0.6~0.8 1,530 · 0.6 미만 617 →
대부분 같은 가게(「내뜨락 한정식」→「내뜨락」, 「비움커피(BIUM COFFEE)」→「비움커피」)지만 다른 가게가 섞여(「하누성 횡성본점」→
「하누」) **같은 건물(도로명 + 건물번호)일 때만** 붙인다. 번호는 모두 `poi_source` 에 남긴다.

**잘못 합쳐진 가게는 그대로 둔다** — 피해는 관광공사에만 있던 가게 일부가 지도에 없는 것뿐이고(틀린 정보는 아니다), 떼어 내려면
91 만 곳 재적재와 리뷰·코스 보존이 필요하다. 다음 분기 갱신 때 §4-1 규칙(포함 비교 최소 길이·같은 건물)을 고치며 본다 — MZ2AZ-465.

### 6-2. 갱신 원칙 (2026-10-15, 권호)

**출처 카드와 우리 POI 를 나눈다.** 출처 자료 한 줄(상가정보 · 관광공사 국문 · 영문)은 출처 번호 그대로 보관하고 합치거나
고치지 않는다(`poi_source`). 우리 POI 는 카드 여러 장을 묶은 폴더다 — 리뷰·코스·사진·상세는 POI 에 붙는다.

1. 같은 번호가 또 오면 그 카드를 덮어쓴다 — 번호로만 찾는다(판단 없음).
2. 있던 번호가 사라지면 그 카드에 「빠짐」 과 시각을 남긴다(판단 없음). POI 를 닫을지는 아래 표.
3. 처음 보는 번호만 어느 POI 에 묶을지 판단한다 — **한 번만** 하고 기록한다. 같은 건물 + 이름 유사도 0.8 이상은 자동으로
   묶고, 아무것도 비슷하지 않으면 새 POI, 그 사이는 새 POI 로 두고 「판정 필요」 로 출력해 사람이 판정 파일에 same/not 을
   적는다(촬영지↔편의시설의 `seed/place_poi_links.tsv` 와 같은 방식). 잘못 합치기가 놓치기보다 나쁘다.

| 사라진 것 | 상세·사진 | POI |
| --- | --- | --- |
| 관광공사만(상가정보는 남음) | **남긴다** | 영업 그대로 |
| 상가정보만(음식·숙박, 관광공사는 남음) | 남긴다 | 폐업 — 음식·숙박의 영업 여부는 상가정보 기준 |
| 둘 다 | 남긴다 | 폐업 |
| 관광공사에만 있는 **음식점·숙박** | 남긴다 | 폐업 — 자주 문을 닫는다 |
| 관광공사에만 있는 관광지·문화시설 등 | 남긴다 | 그대로 — 잘 없어지지 않고, 소개만 내렸을 가능성이 크다 |

- 관광공사가 내리는 기준은 모른다. 목록은 2026-09-06 49,772 → 10-09 49,633 으로 한 달에 약 140 곳 줄었다. 다음 분기 갱신 때
  빠진 곳 표본으로 종류별 이유(폐업 · 소개 정리)를 보고 위 표를 맞춘다.
- 내린 뒤에도 공공누리 사진을 계속 써도 되는지는 확인하지 못했다(§9).
- **폐업 POI** 는 지우지 않는다(리뷰·코스가 함께 지워진다, ADR 0022) — `closed_at` 으로 지도·목록·검색·상세에서 숨기고, 이미
  담은 코스·장바구니에만 「폐업했어요」(계약 1.20.0 `closed`)로 남는다.
- 가게 이름이 바뀌어 번호도 바뀌면 옛 POI 는 폐업, 새 번호는 새 POI 가 되기 쉽다 — 꼭 이어야 하면 판정 파일로 잇는다.

**수집의 빈틈** — 지금 `just poi-tourapi` 는 2026-09-06 목록만 돌고 한 번 받은 번호는 다시 부르지 않는다. 분기 갱신 때:
목록을 새로 받는다 → 수정 시각이 `poi_detail.tour_modified` 보다 새 번호와 새 번호만 상세를 다시 받는다 → 목록에서 빠진 번호에
「빠짐」 → 적재.

**PRD 반영** — 로컬에서 갱신을 돌려 결과 수(묶임 · 새 POI · 폐업 · 판정 필요)를 보고 판정 파일을 채운다 → SQL·판정 파일을 PR 로
→ 원격 데이터 적재(MZ2AZ-414 — 자료·SQL·판정 파일을 이미지에 넣어 같은 순서로)로 PRD 에 같은 결과. PRD 에서 다시 판단하지 않는다.

## 7. 배포 판(`poi-data-<판>`)에 칸 더하기

**관광공사 상세는 따로 판을 낸다(2026-10-16)** — `just poi-detail-publish <국문> <영문> <판>` 이 `just poi-tour-detail` 의 두 파일을
묶어 공개 Release `poi-detail-<판>` 으로 올리고, `MODULE.bazel` 의 `poi_detail_*` 세 줄이 받아 적재 이미지(`/data/poi-detail`)에
넣는다. 원격 적재(`remote-load.sh`)는 같은 곳 연결 다음 「③-2 관광공사 상세」 에서 로컬과 같은 `poi_detail_load.sql` 을 국문 → 영문
순서로 돌린다 — 노트북의 수집 파일은 원격 DB 에 닿지 못해서다. 첫 판 `2026-10-16`(국문 24,996 · 영문 15,287 곳, 수집 중). 수집이
이어지면 새 판을 내고 세 줄만 바꾼다 — 적재는 다시 돌려도 같다. 수집 완료 판 `2026-10-29`(국문 49,772 곳 — 사진 있음 42,314 · 영문 15,287 곳, 영문 파일은 10-16 판과 같다). 로컬 `just data-load-local` 실측: 상세 단계 18 초.

`just poi-pack` 은 `src` 를 빼서 합치기에 필요한 칸이 없다. 세 칸을 정식 칸으로 싣는다 — 건물 열쇠(도로명 + 건물번호),
지점명, 원 번호. 서버·다른 사람도 같은 판정을 한다.
