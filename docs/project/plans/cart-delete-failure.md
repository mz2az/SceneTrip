# 장바구니 삭제 실패 처리 (MZ2AZ-260 / MZ2AZ-262)

2026-10-11 백로그 원문을 다시 읽는 중 iOS `CartStore.remove`의 오류 처리를 확인했다.
262는 260의 하위 작업이므로 브랜치는 스토리 키를 사용한다.

## 문제와 바뀌는 동작

기존 코드는 DELETE 오류를 무시한 뒤 `placeIds`에서 장소를 지우고 성공 토스트를 냈다.
반면 화면의 행은 `items`를 읽어, DELETE 성공 뒤 GET이 실패하면 행과 저장 아이콘이 달랐다.

- DELETE가 실패하면 행·저장 아이콘·작품 출처를 그대로 유지하고 실패를 알린다.
- DELETE가 성공하면 해당 장소를 `items`와 `placeIds`에서 함께 제거한다.
  뒤따른 목록 조회 실패도 이 성공한 삭제를 되돌리지 않는다.
- 조회·삭제만 작은 클라이언트 인터페이스로 감싸 실제 Store의 비동기 경로를 시험한다.
  운영 구현은 생성된 `CartAPI`를 호출하고 HTTP 요청을 직접 만들지 않는다.
- 기존 인증·재시도 규칙은 바꾸지 않는다. 응답 유실 뒤 재시도한 DELETE의 404를
  204로 처리하는 것은 `RetryingSession`의 기존 규칙이며, 최초 404를 일괄 성공 처리하지 않는다.

## 시험과 범위

실제 `CartStore.refresh`로 가짜 서버 목록을 채운 뒤 `remove`를 호출한다.
503·연결 실패·최초 404의 목록 보존, 성공 뒤 GET 실패의 두 상태 일치,
성공한 서버 재조회, 장소별 선택 삭제를 검증한다. 기존 인증·재시도 시험도 함께 확인한다.
새 시험 파일은 `BUILD.bazel`에 명시하고 `just check`를 통과시킨다.

이 변경은 262의 전체 iOS·Android 장바구니 여섯 동작을 실제 환경에서 재검증했다는 뜻이 아니다.
Docker·API·사진 저장소를 켜지 않고 기존 사용자 데이터도 바꾸지 않는다.
테스트 러너가 사용하는 임시 iOS 시험 기기는 앱 화면 조작용 기기와 별개다.
닉네임 363의 과거 README 문구는 이 수정에 섞지 않고 원 티켓의 정정 증거로 추적한다.
