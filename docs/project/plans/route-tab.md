## 1. 무엇을 만드는가

장바구니에 담은 촬영지 핀들을 **실제 도로를 따라가는 경로**로 이어 준다. 지금
장바구니는 담기까지만 되어 있고([MZ2AZ-170](https://mz2az.atlassian.net/browse/MZ2AZ-170)),
담은 장소들 사이를 어떻게 이동하는지는 앱이 전혀 답하지 못한다. 이 계획은 그 빈칸을
채운다.

두 지점을 직선으로 잇는 것으로는 안 된다. 외국인 관광객이 실제로 걸어갈 길과 탈
대중교통을 보여줘야 하므로, 경로는 도로망 위에서 계산된 선이어야 한다.

만들 것을 셋으로 나누면 이렇다.

| 구성 | 내용 |
| --- | --- |
| 도보 경로 | 장소 A에서 장소 B까지 걸어가는 길의 좌표열, 거리, 소요 시간 |
| 대중교통 경로 | 정류장까지 도보 + 버스·지하철 노선 + 하차 후 도보의 조합 |
| 방문 순서 | 담은 장소 여러 개를 어떤 순서로 도는 것이 가장 짧은지 |

## 3. 먼저 해야 하는 스파이크 세 개

**이 절이 이 문서에서 가장 중요하다.** 아래 세 가지가 확인되기 전에는 스키마도
API 명세도 확정할 수 없다. 특히 스파이크 1의 결과에 따라 4절의 선택지가 통째로
바뀐다.

### 3-1. [Spike] 한국 OSM 도보 데이터 품질 검증 (1~2일)

**질문**: OpenStreetMap(자원봉사자들이 만드는 무료 지도 데이터)의 한국 인도·횡단보도
데이터가 우리 촬영지를 이어 줄 만큼 촘촘한가.

**방법**:

1. Geofabrik에서 `south-korea-latest.osm.pbf`(한국 지역 OSM 추출본)를 내려받는다.
2. OSRM(오픈소스 경로 탐색 엔진)을 `foot` 프로파일로 컨테이너 하나에 띄운다.
3. `place` 테이블의 실제 촬영지 10~20곳을 페어로 묶어 경로를 요청한다.
4. 네이버 지도 앱의 도보 경로와 눈으로 비교한다.

**핵심 확인 지점은 서울이 아니라 지방이다.** 서울·부산 도심은 OSM 인도 데이터가
촘촘하지만, 속초·통영·강릉처럼 촬영지가 몰려 있는 지방 소도시는 급격히 성겨진다.
우리 데이터셋의 지역 분포에 맞춰 표본을 뽑아야 결과가 의미를 가진다.

**결과에 따른 분기**:

| 결과 | 다음 행동 |
| --- | --- |
| 품질이 쓸 만하다 | OSM + OSRM 셀프호스팅으로 확정. 4절 A안 |
| 서울만 되고 지방이 비어 있다 | TMAP 보행자 경로안내 API를 국내용으로 병용. 4절 B안 |
| 전반적으로 부족하다 | TMAP 단독. 다만 해외 확장을 포기하는 결정이므로 팀 합의가 필요하다 |

### 3-2. [Spike] 대중교통 API 확인 (0.5일)

ODsay(`lab.odsay.com`)에서 키를 발급받아 촬영지 두 쌍의 대중교통 경로를 실제로
호출해 본다. 확인할 것은 세 가지다 — 응답에 도보 구간 좌표가 함께 오는지, 무료
등급의 하루 호출 한도(공개 정책상 1,000건)가 우리 트래픽에 맞는지, 그리고 **결과를
저장해도 되는지**.

마지막 항목이 3-3과 이어진다. 상용 API는 결과 저장을 막는 경우가 흔하다.

### 3-3. [Spike] 좌표 리매핑 비용 실측 (0.5일)

현재 `place` 20건을 표본으로 뽑아, 각 장소의 좌표가 OSM 기준으로는 어디에
찍히는지 확인하고 **어긋난 거리를 미터로 잰다.** 이 숫자 하나가 "전량 다시 찍어야
하는가, 일부만 손보면 되는가"를 결정한다. 감으로 정하면 안 된다.

## 4. 지도 API 선택 — 결정이 필요한 지점

### 4-1. 네이버를 쓸 수 없는 이유 두 가지

멘토는 "네이버 Directions 5 API를 먼저 써 보고 정책이 걸리면 다른 방법"이라고
조언했다. 확인해 보니 두 가지 이유로 이 경로는 막혀 있다.

**첫째, Directions 5/15는 자동차 전용이다.** 네이버 클라우드 플랫폼 개발자
포럼 답변에 따르면 보행자 경로는 아직 열려 있지 않다. 우리에게 필요한 것은 도보인데
그것이 없다.

**둘째, 그리고 더 결정적으로, 이용약관이 결과 저장을 금지한다.** 네이버 클라우드
플랫폼 AI·Naver API 서비스 이용약관은 Maps API의 결과 데이터를 별도로 저장하거나
데이터베이스화하는 것을 금지한다. 리턴받은 즉시 1회 사용만 허용된다.

두 번째가 왜 치명적이냐 하면, 멘토가 제안한 전략의 핵심이 **"촬영지 좌표는 고정이니
경로를 미리 계산해서 DB에 캐싱해 두자"** 이기 때문이다. 네이버 API로 그렇게 하면
전략 자체가 약관 위반이 된다. 우회할 방법이 없다.

거기에 레거시 지도 API는 무료 제공량이 종료되고 신규 신청도 차단됐다(2025-06 공지).
현재 상태는 콘솔에서 직접 확인해야 한다.

> **결론**: 셀프호스팅은 비용을 아끼는 대안이 아니라, 사전 계산·캐싱이라는 우리
> 아키텍처의 전제를 성립시키는 유일한 선택지다. 직접 호스팅한 OSM 데이터에는 저장
> 금지 조항이 없다. 출처 표기(ODbL) 의무만 진다.

### 4-2. 선택지

| | A안 — OSM 계열로 전환 | B안 — 국내는 TMAP, 지도는 네이버 유지 |
| --- | --- | --- |
| 도보 경로 | OSRM 셀프호스팅 | TMAP 보행자 경로안내 API |
| 경로 저장·캐싱 | 제약 없음 | 약관 확인 필요 |
| 베이스맵 | MapLibre 또는 Mapbox | 네이버 지도 SDK 유지 |
| 해외 확장 | 가능 | 불가 |
| 다국어 지명 | OSM이 자동 제공 | 네이버는 불완전 |
| 국내 도보 데이터 | **스파이크 1이 답한다** | 우수 |
| iOS 변경량 | 큼 — `Package.swift:19` 의 네이버 SDK 교체 | 없음 |
| 좌표 리매핑 | 필요 — `place.geom` 전량 | 불필요 |

외국인 관광객이 대상이라는 전제에서는 A안이 맞다. 다만 A안은 iOS 지도 SDK 교체와
좌표 리매핑이라는 두 개의 실제 비용을 부른다. 스파이크 1과 3의 숫자가 나온 뒤
팀이 결정한다.

### 4-3. 왜 GraphHopper가 아니라 OSRM인가

멘토가 시연한 것은 GraphHopper였지만, 우리에게는 **거리 행렬**이 필요하다. 장바구니에
담은 장소 k개의 방문 순서를 정하려면 k×k 크기의 "각 쌍 사이 소요 시간" 표가 있어야
한다. GraphHopper의 오픈소스판은 이 행렬 기능(Matrix API)이 상용 제품에만 있고,
OSRM은 `/table` 엔드포인트로 무료 제공한다.

OSRM 하나로 `/route`(경로 좌표열)와 `/table`(행렬)이 모두 나온다. 장소가 10개
이하이면 순서 최적화는 완전탐색으로 충분하다.

Valhalla는 도보와 대중교통을 한 번에 푸는 멀티모달 엔진이지만, 그러려면 GTFS라는
대중교통 시간표 표준 데이터가 필요하다. 한국은 전국 단위 GTFS가 없어 실효성이 낮다.
대중교통은 ODsay로 분리하는 편이 낫다.

## 5. 좌표를 어떻게 맞추는가

### 5-1. 오차의 진짜 원인

멘토는 지도 서비스마다 좌표가 어긋나는 이유로 측지계(지구 모양을 근사하는 기준) 차이를
길게 설명했다. 결론 — 좌표를 수식으로 변환해 옮기지 마라 — 은 옳지만, 이유를 정확히
알아야 대응이 맞는다.

동경측지계와 세계측지계가 약 365m 차이 났던 것은 **2010년에 전환이 끝난 역사**다.
오늘날 네이버·카카오·구글·OSM의 공개 API는 모두 WGS84(GPS가 쓰는 세계 표준 좌표계,
PostGIS 코드로 4326)로 위경도를 주고받는다. 좌표계가 서로 다르지 않다.

지금 남아 있는 차이는 세 가지다.

1. **각 사업자가 그린 도로·건물 형상이 다르다.** 네이버가 그린 도로선과 OSM이 그린
   도로선이 몇 미터 어긋나 있다.
2. **POI 대표점의 정의가 다르다.** 같은 백화점을 네이버는 정문에, 카카오는 건물
   중심에, OSM은 부지 중심에 찍는다. 수십 미터 차이를 만드는 주된 원인이 이것이다.
3. 항공사진과 베이스맵의 정합 오차.

그래서 "OSRM이 뽑은 경로선을 네이버 지도에 얹으면 길에서 벗어나 보인다"는 관찰은
사실이고, 원인은 1번이다. **경로 엔진과 베이스맵의 데이터 소스를 통일한다** 는 규칙은
그대로 유효하다.

### 5-2. 도로명주소를 매개로 다시 찍는다 — 절반의 해법

좌표를 다른 지도 기준으로 옮길 때는 좌표를 변환하지 말고, 주소를 매개로 목표 지도에서
다시 지오코딩한다. 좌표 → 주소 → (다른 지도) → 좌표 순이다.

**우리 도메인에서는 이것만으로 부족하다.** 촬영지의 상당수가 해변, 방파제, 계단, 다리,
골목, 성곽이다. 주소가 없거나, 주소 대표점이 실제 촬영 스팟에서 수백 미터 떨어져
있다. `〈파친코〉의 그 계단`을 주소로 지오코딩하면 엉뚱한 건물에 찍힌다.

그래서 두 단계로 간다.

1. **주소가 있는 장소** — 재지오코딩으로 좌표 초안을 자동 생성한다.
2. **모든 장소** — 기준 지도 위에 띄운 자체 편집기에서 사람이 최종 확정한다.

멘토가 "지도 편집기를 따로 만들어라"고 한 것이 2번이고, 생략할 수 없다.

### 5-3. 스키마가 리매핑을 견디게 만든다

지금 `place` 테이블은 좌표를 한 벌만 들고 있고, 그것이 어느 지도 기준인지 기록하지
않는다(`V2__schema.sql:38-45`). 게다가 `naver_place_url` 이 dedupe 1차 키다
(`V2__schema.sql:53`) — 중복 판정이 네이버에 묶여 있다.

기준 지도를 바꾸면 좌표 컬럼 전체를 다시 찍어야 하고, 그 작업을 어디까지 했는지
추적할 방법이 없다. **데이터가 적은 지금 컬럼을 더하는 것이 압도적으로 싸다.**

| 컬럼 | 이유 |
| --- | --- |
| `geom_source` | 이 좌표를 어느 지도에서 찍었는가 (`naver` / `osm`) |
| `verified_at`, `verified_by` | 사람이 검수했는가. 미검수 데이터를 걸러 내는 유일한 방법 |

## 6. 저장과 전달

### 6-1. GeoJSON으로 주고받는다

경로 엔진의 응답을 가공하지 않고 PostGIS의 `LineString` 타입에 그대로 넣고,
꺼낼 때 `ST_AsGeoJSON()` 으로 뽑는다. 그러면 iOS가 파싱 없이 지도 라이브러리에
그대로 넣어 폴리라인으로 그린다. 중간에 변환 코드를 만들지 않는 것이 목적이다.

함정 세 가지를 미리 적어 둔다.

1. **GeoJSON(RFC 7946)은 `[경도, 위도]` 순서다.** 한국 API는 대부분 `lat, lng`
   순으로 준다. 뒤집으면 좌표가 아프리카 앞바다로 간다. 실무에서 가장 흔한 버그다.
2. **도보 경로는 점이 수천 개다.** 그대로 내보내면 응답이 수백 KB가 된다.
   `ST_SimplifyPreserveTopology` 로 줄이거나 인코딩된 폴리라인을 쓴다. OSRM과
   GraphHopper는 기본이 인코딩된 폴리라인이므로, 좌표열을 원하면 옵션을 꺼야 한다.
3. **`FeatureCollection` 으로 감싸고 구간마다 `properties` 를 실어야 한다**
   (`mode`: walk/transit, `distance`, `duration`). 단일 `LineString` 하나로 던지면
   프론트가 도보 구간과 버스 구간의 색을 다르게 칠할 수 없다.

### 6-2. 스키마 초안

```sql
CREATE TABLE route_segment (
    origin_place_id BIGINT NOT NULL REFERENCES place (id) ON DELETE CASCADE,
    dest_place_id   BIGINT NOT NULL REFERENCES place (id) ON DELETE CASCADE,
    mode            TEXT   NOT NULL,   -- walk | transit
    profile_version TEXT   NOT NULL,   -- 엔진·OSM 데이터 판. 갱신 시 캐시 무효화 기준
    geom            GEOMETRY(LineString, 4326) NOT NULL,
    distance_m      INT    NOT NULL,
    duration_s      INT    NOT NULL,
    computed_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (origin_place_id, dest_place_id, mode, profile_version)
);
```

`profile_version` 이 핵심이다. OSM 데이터를 갱신하거나 라우팅 프로파일을 고치면
기존 캐시가 전부 낡은 값이 되는데, 이 컬럼이 없으면 어느 행이 낡았는지 구분할 수
없다.

타입이 `GEOGRAPHY` 가 아니라 `GEOMETRY` 인 이유는 `V6__place_geometry_index.sql`
의 주석과 같다 — 경로선은 화면에 그리는 평면 도형이고, "몇 미터 안"을 묻는 대상이
아니다.

### 6-3. 조합 폭발 문제의 답

장소 N개의 모든 쌍은 N²이므로 전부 미리 계산하는 것은 비현실적이라는 우려가
멘토링 뒤 팀 내부에서 나왔고, 결론 없이 끝났다. 답은 이렇다.

**전부 사전 계산하지 않는다. 요청이 올 때 계산하고, 계산 결과를 저장한다.**
장바구니 기반이라 한 번에 필요한 경로는 몇 개뿐이고, 촬영지 좌표가 고정이라 같은
쌍이 반복해서 요청된다. 즉 캐시 적중률이 매우 높다. 인기 있는 쌍 상위 몇 개만
배치로 미리 채워 두면 체감 지연도 사라진다.

사전 계산은 최적화이지 전제가 아니다.

대중교통 구간은 시간대에 따라 답이 달라지므로 이 캐시에서 제외하거나 짧은 유효기간만
준다.

## 7. 지금 하지 않을 것

멘토가 설명한 H3 육각형 격자 클러스터링과 바운드 박스 양자화 캐싱은 훌륭한 기법이지만,
**핀이 수만 개일 때의 문제**다. 지금은 인기순 상위 노출과 더보기로 충분하고, 팀도
같은 판단이었다.

`V4__drop_unused_postgis_extensions.sql` 이 안 쓰는 확장을 정리한 이력이 있으니,
H3 확장도 실제로 필요해진 시점에 넣는다.

## 8. 구현 순서

스파이크가 끝난 뒤의 순서다. [CLAUDE.md §3](../../../CLAUDE.md) 의 계약 우선 원칙을
따른다.

| 순서 | 작업 | 산출물 |
| --- | --- | --- |
| 1 | 기준 지도 결정 (4-2절) | 이 문서에 결정과 이유를 덧붙인다 |
| 2 | API 명세 | `contracts/openapi/scene-api-v1.yaml` 에 `POST /routes` 추가 후 `just gen` |
| 3 | 스키마 | `V7__route_segment.sql`, `place` 에 `geom_source` 등 추가 |
| 4 | 라우팅 엔진 배포 | `platform/` 에 OSRM 매니페스트. `just` 레시피도 함께 |
| 5 | 백엔드 | `services/scene-api/.../route/` 신설 — 온디맨드 계산 + 캐시 |
| 6 | 좌표 검수 편집기 | 운영자용. 5-2절 2단계 |
| 7 | iOS | 폴리라인 렌더링. `geojson.io` 로 중간 검증 |

새 서비스로 분리할지는 열어 둔다. 멘토는 경로 탐색의 부하가 장소 조회를 막지 않도록
분리하라고 조언했다. 다만 모놀리식과 마이크로서비스의 최종 구조가 아직 결정되지
않았으므로(2026-08-08 멘토링 미결 항목), 그 결정에 맞춘다.
