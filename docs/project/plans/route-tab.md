# 루트(코스) 탭 구현 계획 (MZ2AZ-107)

- **에픽**: [MZ2AZ-107](https://mz2az.atlassian.net/browse/MZ2AZ-107) — "코스"
- **작성일**: 2026-08-09
- **상태**: 계획 — 아직 코드가 없다. 3절의 스파이크가 끝나야 4절 이후를 확정할 수 있다.
- **근거**: 2026-08-08 김민수 멘토님 지도 기술 멘토링 + 그 뒤의 사실 확인

## 1. 무엇을 만드는가

장바구니에 담은 촬영지 핀들을 **실제 도로를 따라가는 경로**로 이어 준다. 지금
장바구니는 담기까지만 되어 있고([MZ2AZ-170](https://mz2az.atlassian.net/browse/MZ2AZ-170)),
담은 장소들 사이를 어떻게 이동하는지는 앱이 전혀 답하지 못한다. 이 계획은 그 빈칸을
채운다.

두 지점을 직선으로 잇는 것으로는 안 된다. 외국인 관광객이 실제로 걸어갈 길과 탈
대중교통을 보여줘야 하므로, 경로는 도로망 위에서 계산된 선이어야 한다.

만들 것을 셋으로 나누면 이렇다.

| 구성 | 내용 |
| --- | --- |
| 도보 경로 | 장소 A에서 장소 B까지 걸어가는 길의 좌표열, 거리, 소요 시간 |
| 대중교통 경로 | 정류장까지 도보 + 버스·지하철 노선 + 하차 후 도보의 조합 |
| 방문 순서 | 담은 장소 여러 개를 어떤 순서로 도는 것이 가장 짧은지 |

## 2. 이 계획의 범위 밖

| 항목 | 이유 |
| --- | --- |
| AI 코스 추천, 일정 생성 | 에픽 MZ2AZ-107 안이지만 별도 티켓. 경로 계산이 먼저 있어야 그 위에 얹는다 |

| 자동차·택시 경로 | 멘토 조언대로 택시는 경로를 찾지 않고 직선 거리로 요금만 추정하면 된다 |

## 3. 먼저 해야 하는 스파이크 세 개

**이 절이 이 문서에서 가장 중요하다.** 아래 세 가지가 확인되기 전에는 스키마도
API 명세도 확정할 수 없다. 특히 스파이크 1의 결과에 따라 4절의 선택지가 통째로
바뀐다.

### 3-1. [Spike] 한국 OSM 도보 데이터 품질 검증 (1~2일)

**질문**: OpenStreetMap(자원봉사자들이 만드는 무료 지도 데이터)의 한국 인도·횡단보도
데이터가 우리 촬영지를 이어 줄 만큼 촘촘한가.

**방법**:

1. Geofabrik에서 `south-korea-latest.osm.pbf`(한국 지역 OSM 추출본)를 내려받는다.
2. OSRM(오픈소스 경로 탐색 엔진)을 `foot` 프로파일로 컨테이너 하나에 띄운다.
3. `place` 테이블의 실제 촬영지 10~20곳을 페어로 묶어 경로를 요청한다.
4. 네이버 지도 앱의 도보 경로와 눈으로 비교한다.

**핵심 확인 지점은 서울이 아니라 지방이다.** 서울·부산 도심은 OSM 인도 데이터가
촘촘하지만, 속초·통영·강릉처럼 촬영지가 몰려 있는 지방 소도시는 급격히 성겨진다.
우리 데이터셋의 지역 분포에 맞춰 표본을 뽑아야 결과가 의미를 가진다.

**결과에 따른 분기**:

| 결과 | 다음 행동 |
| --- | --- |
| 품질이 쓸 만하다 | OSM + OSRM 셀프호스팅으로 확정. 4절 A안 |
| 서울만 되고 지방이 비어 있다 | TMAP 보행자 경로안내 API를 국내용으로 병용. 4절 B안 |
| 전반적으로 부족하다 | TMAP 단독. 다만 해외 확장을 포기하는 결정이므로 팀 합의가 필요하다 |

### 3-2. [Spike] 대중교통 API 확인 (0.5일)

ODsay(`lab.odsay.com`)에서 키를 발급받아 촬영지 두 쌍의 대중교통 경로를 실제로
호출해 본다. 확인할 것은 세 가지다 — 응답에 도보 구간 좌표가 함께 오는지, 무료
등급의 하루 호출 한도(공개 정책상 1,000건)가 우리 트래픽에 맞는지, 그리고 **결과를
저장해도 되는지**.

마지막 항목이 3-3과 이어진다. 상용 API는 결과 저장을 막는 경우가 흔하다.

### 3-3. [Spike] 좌표 리매핑 비용 실측 (0.5일)

현재 `place` 20건을 표본으로 뽑아, 각 장소의 좌표가 OSM 기준으로는 어디에
찍히는지 확인하고 **어긋난 거리를 미터로 잰다.** 이 숫자 하나가 "전량 다시 찍어야
하는가, 일부만 손보면 되는가"를 결정한다. 감으로 정하면 안 된다.

## 4. 지도 API 선택 — 결정이 필요한 지점

### 4-1. 네이버를 쓸 수 없는 이유 두 가지

멘토는 "네이버 Directions 5 API를 먼저 써 보고 정책이 걸리면 다른 방법"이라고
조언했다. 확인해 보니 두 가지 이유로 이 경로는 막혀 있다.

**첫째, Directions 5/15는 자동차 전용이다.** 네이버 클라우드 플랫폼 개발자
포럼 답변에 따르면 보행자 경로는 아직 열려 있지 않다. 우리에게 필요한 것은 도보인데
그것이 없다.

**둘째, 그리고 더 결정적으로, 이용약관이 결과 저장을 금지한다.** 네이버 클라우드
플랫폼 AI·Naver API 서비스 이용약관은 Maps API의 결과 데이터를 별도로 저장하거나
데이터베이스화하는 것을 금지한다. 리턴받은 즉시 1회 사용만 허용된다.

두 번째가 왜 치명적이냐 하면, 멘토가 제안한 전략의 핵심이 **"촬영지 좌표는 고정이니
경로를 미리 계산해서 DB에 캐싱해 두자"** 이기 때문이다. 네이버 API로 그렇게 하면
전략 자체가 약관 위반이 된다. 우회할 방법이 없다.

거기에 레거시 지도 API는 무료 제공량이 종료되고 신규 신청도 차단됐다(2025-06 공지).
현재 상태는 콘솔에서 직접 확인해야 한다.

> **결론**: 셀프호스팅은 비용을 아끼는 대안이 아니라, 사전 계산·캐싱이라는 우리
> 아키텍처의 전제를 성립시키는 유일한 선택지다. 직접 호스팅한 OSM 데이터에는 저장
> 금지 조항이 없다. 출처 표기(ODbL) 의무만 진다.

### 4-2. 선택지

| | A안 — OSM 계열로 전환 | B안 — 국내는 TMAP, 지도는 네이버 유지 |
| --- | --- | --- |
| 도보 경로 | OSRM 셀프호스팅 | TMAP 보행자 경로안내 API |
| 경로 저장·캐싱 | 제약 없음 | 약관 확인 필요 |
| 베이스맵 | MapLibre 또는 Mapbox | 네이버 지도 SDK 유지 |
| 해외 확장 | 가능 | 불가 |
| 다국어 지명 | OSM이 자동 제공 | 네이버는 불완전 |
| 국내 도보 데이터 | **스파이크 1이 답한다** | 우수 |
| iOS 변경량 | 큼 — `Package.swift:19` 의 네이버 SDK 교체 | 없음 |
| 좌표 리매핑 | 필요 — `place.geom` 전량 | 불필요 |

외국인 관광객이 대상이라는 전제에서는 A안이 맞다. 다만 A안은 iOS 지도 SDK 교체와
좌표 리매핑이라는 두 개의 실제 비용을 부른다. 스파이크 1과 3의 숫자가 나온 뒤
팀이 결정한다.

### 4-3. 왜 GraphHopper가 아니라 OSRM인가

멘토가 시연한 것은 GraphHopper였지만, 우리에게는 **거리 행렬**이 필요하다. 장바구니에
담은 장소 k개의 방문 순서를 정하려면 k×k 크기의 "각 쌍 사이 소요 시간" 표가 있어야
한다. GraphHopper의 오픈소스판은 이 행렬 기능(Matrix API)이 상용 제품에만 있고,
OSRM은 `/table` 엔드포인트로 무료 제공한다.

OSRM 하나로 `/route`(경로 좌표열)와 `/table`(행렬)이 모두 나온다. 장소가 10개
이하이면 순서 최적화는 완전탐색으로 충분하다.

Valhalla는 도보와 대중교통을 한 번에 푸는 멀티모달 엔진이지만, 그러려면 GTFS라는
대중교통 시간표 표준 데이터가 필요하다. 한국은 전국 단위 GTFS가 없어 실효성이 낮다.
대중교통은 ODsay로 분리하는 편이 낫다.

## 5. 좌표를 어떻게 맞추는가

### 5-1. 오차의 진짜 원인

멘토는 지도 서비스마다 좌표가 어긋나는 이유로 측지계(지구 모양을 근사하는 기준) 차이를
길게 설명했다. 결론 — 좌표를 수식으로 변환해 옮기지 마라 — 은 옳지만, 이유를 정확히
알아야 대응이 맞는다.

동경측지계와 세계측지계가 약 365m 차이 났던 것은 **2010년에 전환이 끝난 역사**다.
오늘날 네이버·카카오·구글·OSM의 공개 API는 모두 WGS84(GPS가 쓰는 세계 표준 좌표계,
PostGIS 코드로 4326)로 위경도를 주고받는다. 좌표계가 서로 다르지 않다.

지금 남아 있는 차이는 세 가지다.

1. **각 사업자가 그린 도로·건물 형상이 다르다.** 네이버가 그린 도로선과 OSM이 그린
   도로선이 몇 미터 어긋나 있다.
2. **POI 대표점의 정의가 다르다.** 같은 백화점을 네이버는 정문에, 카카오는 건물
   중심에, OSM은 부지 중심에 찍는다. 수십 미터 차이를 만드는 주된 원인이 이것이다.
3. 항공사진과 베이스맵의 정합 오차.

그래서 "OSRM이 뽑은 경로선을 네이버 지도에 얹으면 길에서 벗어나 보인다"는 관찰은
사실이고, 원인은 1번이다. **경로 엔진과 베이스맵의 데이터 소스를 통일한다** 는 규칙은
그대로 유효하다.

### 5-2. 도로명주소를 매개로 다시 찍는다 — 절반의 해법

좌표를 다른 지도 기준으로 옮길 때는 좌표를 변환하지 말고, 주소를 매개로 목표 지도에서
다시 지오코딩한다. 좌표 → 주소 → (다른 지도) → 좌표 순이다.

**우리 도메인에서는 이것만으로 부족하다.** 촬영지의 상당수가 해변, 방파제, 계단, 다리,
골목, 성곽이다. 주소가 없거나, 주소 대표점이 실제 촬영 스팟에서 수백 미터 떨어져
있다. `〈파친코〉의 그 계단`을 주소로 지오코딩하면 엉뚱한 건물에 찍힌다.

그래서 두 단계로 간다.

1. **주소가 있는 장소** — 재지오코딩으로 좌표 초안을 자동 생성한다.
2. **모든 장소** — 기준 지도 위에 띄운 자체 편집기에서 사람이 최종 확정한다.

멘토가 "지도 편집기를 따로 만들어라"고 한 것이 2번이고, 생략할 수 없다.

### 5-3. 스키마가 리매핑을 견디게 만든다

지금 `place` 테이블은 좌표를 한 벌만 들고 있고, 그것이 어느 지도 기준인지 기록하지
않는다(`V2__schema.sql:38-45`). 게다가 `naver_place_url` 이 dedupe 1차 키다
(`V2__schema.sql:53`) — 중복 판정이 네이버에 묶여 있다.

기준 지도를 바꾸면 좌표 컬럼 전체를 다시 찍어야 하고, 그 작업을 어디까지 했는지
추적할 방법이 없다. **데이터가 적은 지금 컬럼을 더하는 것이 압도적으로 싸다.**

| 컬럼 | 이유 |
| --- | --- |
| `geom_source` | 이 좌표를 어느 지도에서 찍었는가 (`naver` / `osm`) |
| `verified_at`, `verified_by` | 사람이 검수했는가. 미검수 데이터를 걸러 내는 유일한 방법 |

## 6. 저장과 전달

### 6-1. GeoJSON으로 주고받는다

경로 엔진의 응답을 가공하지 않고 PostGIS의 `LineString` 타입에 그대로 넣고,
꺼낼 때 `ST_AsGeoJSON()` 으로 뽑는다. 그러면 iOS가 파싱 없이 지도 라이브러리에
그대로 넣어 폴리라인으로 그린다. 중간에 변환 코드를 만들지 않는 것이 목적이다.

함정 세 가지를 미리 적어 둔다.

1. **GeoJSON(RFC 7946)은 `[경도, 위도]` 순서다.** 한국 API는 대부분 `lat, lng`
   순으로 준다. 뒤집으면 좌표가 아프리카 앞바다로 간다. 실무에서 가장 흔한 버그다.
2. **도보 경로는 점이 수천 개다.** 그대로 내보내면 응답이 수백 KB가 된다.
   `ST_SimplifyPreserveTopology` 로 줄이거나 인코딩된 폴리라인을 쓴다. OSRM과
   GraphHopper는 기본이 인코딩된 폴리라인이므로, 좌표열을 원하면 옵션을 꺼야 한다.
3. **`FeatureCollection` 으로 감싸고 구간마다 `properties` 를 실어야 한다**
   (`mode`: walk/transit, `distance`, `duration`). 단일 `LineString` 하나로 던지면
   프론트가 도보 구간과 버스 구간의 색을 다르게 칠할 수 없다.

### 6-2. 스키마 초안

```sql
CREATE TABLE route_segment (
    origin_place_id BIGINT NOT NULL REFERENCES place (id) ON DELETE CASCADE,
    dest_place_id   BIGINT NOT NULL REFERENCES place (id) ON DELETE CASCADE,
    mode            TEXT   NOT NULL,   -- walk | transit
    profile_version TEXT   NOT NULL,   -- 엔진·OSM 데이터 판. 갱신 시 캐시 무효화 기준
    geom            GEOMETRY(LineString, 4326) NOT NULL,
    distance_m      INT    NOT NULL,
    duration_s      INT    NOT NULL,
    computed_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (origin_place_id, dest_place_id, mode, profile_version)
);
```

`profile_version` 이 핵심이다. OSM 데이터를 갱신하거나 라우팅 프로파일을 고치면
기존 캐시가 전부 낡은 값이 되는데, 이 컬럼이 없으면 어느 행이 낡았는지 구분할 수
없다.

타입이 `GEOGRAPHY` 가 아니라 `GEOMETRY` 인 이유는 `V6__place_geometry_index.sql`
의 주석과 같다 — 경로선은 화면에 그리는 평면 도형이고, "몇 미터 안"을 묻는 대상이
아니다.

### 6-3. 조합 폭발 문제의 답

장소 N개의 모든 쌍은 N²이므로 전부 미리 계산하는 것은 비현실적이라는 우려가
멘토링 뒤 팀 내부에서 나왔고, 결론 없이 끝났다. 답은 이렇다.

**전부 사전 계산하지 않는다. 요청이 올 때 계산하고, 계산 결과를 저장한다.**
장바구니 기반이라 한 번에 필요한 경로는 몇 개뿐이고, 촬영지 좌표가 고정이라 같은
쌍이 반복해서 요청된다. 즉 캐시 적중률이 매우 높다. 인기 있는 쌍 상위 몇 개만
배치로 미리 채워 두면 체감 지연도 사라진다.

사전 계산은 최적화이지 전제가 아니다.

대중교통 구간은 시간대에 따라 답이 달라지므로 이 캐시에서 제외하거나 짧은 유효기간만
준다.

## 7. 지금 하지 않을 것

멘토가 설명한 H3 육각형 격자 클러스터링과 바운드 박스 양자화 캐싱은 훌륭한 기법이지만,
**핀이 수만 개일 때의 문제**다. 지금은 인기순 상위 노출과 더보기로 충분하고, 팀도
같은 판단이었다.

`V4__drop_unused_postgis_extensions.sql` 이 안 쓰는 확장을 정리한 이력이 있으니,
H3 확장도 실제로 필요해진 시점에 넣는다.

### 10-1. 스파이크 1 — OSM 도보 데이터는 지방에서 무너진다

3-1절의 분기 중 **"전반적으로 부족하다"** 가 답이었다. 거리만 보면 OSM 계열도 도심에서
1~2% 안쪽으로 맞지만, 우리 촬영지가 몰려 있는 지방에서 데이터 자체가 없다.

| 지역 | 인도·보행로 | 횡단보도 |
| --- | --- | --- |
| 서울 광화문 | 498 | 105 |
| 통영 중앙동 | 20 | **0** |
| 속초 중앙동 | 3 | **0** |
| 강릉 주문진 | 2 | **0** |

횡단보도가 0이면 엔진은 어디서 건널 수 있는지 모르고 교차로를 그냥 통과하며,
**횡단보도·계단 안내를 응답에 싣지도 못한다.** 외국인에게 "여기서 건너세요"를 말하려면
이 데이터가 있어야 한다.

도심에서도 갈렸다. 같은 경로의 지하 환승 구간을 두 엔진으로 재면 이렇다.

| 도보 구간 | OSRM | TMAP |
| --- | --- | --- |
| 경복궁역까지 | 646 m · 7분 | 622 m · 9분 |
| **을지로3가 환승** | **811 m · 9분** | **153 m · 2분** |
| 잠실역 → 도착지 | 148 m · 1분 | 151 m · 3분 |

OSRM은 지하 환승 통로를 몰라 사용자를 지상으로 올려 한 바퀴 돌린다. 비용을 아끼자고
OSRM을 쓰면 환승할 때마다 650 m를 헛걷게 만든다.

> **결론**: 4-2절의 **A안(OSM + OSRM 셀프호스팅)은 기각한다.** 도보는 TMAP 보행자
> 경로안내다. OSRM은 버리지 않고 **거리 행렬(`/table`) 전용**으로만 남긴다 — 한도가
> 없어 방문 순서 계산에는 여전히 가장 싸다.

### 10-2. 스파이크 2 — ODsay는 되지만 도보 좌표를 주지 않는다

| | TMAP 대중교통 | ODsay |
| --- | --- | --- |
| 무료 한도 | **10건 / 일** | 1,000건 / 일 |
| 노선 좌표 | 응답에 포함 | `loadLane` 을 한 번 더 |
| 도보 구간 좌표 | 포함 | **없음** |

ODsay는 도보 `subPath` 에 거리와 소요시간만 주고 좌표를 주지 않는다. 대신 승·하차
**출입구 좌표**(`startExitX/Y`, `endExitX/Y`)를 주므로, 그 사이를 도보 엔진으로
채우면 선이 이어진다. 큰 역에서는 역 중심과 출구가 100 m 넘게 차이 나므로 출입구
좌표가 있으면 그것을 쓴다.

**뜻밖의 소득이 다국어였다.** ODsay `lang` 파라미터 하나로 영·일·중(간체·번체)·
베트남어가 나오고, 기계 번역이 아니라 실제 안내판과 같은 공식 표기다
(`서울역버스환승센터(5번승강장)` → `Seoul Stn. Bus Transfer Center (Platform 5)`).
반대로 **TMAP은 응답 항목 40개에 영문 필드가 아예 없다** — `Accept-Language`,
`lang`, `resType` 모두 무시된다. 외국인 대상 앱에서 이 차이는 작지 않다.

### 10-3. 스파이크 3 — 측지계는 원인이 아니었고, 진짜 문제는 따로 있었다

5-1절의 판단이 맞았다. 네이버 좌표를 그대로 TMAP·ODsay에 넣어 137곳을 돌렸고,
**도로 위치 차이는 중앙값 5.7 m** 였다. 좌표 리매핑은 필요 없다 — 4-2절 표의
"좌표 리매핑: 필요" 행은 A안 기각과 함께 사라진다.

대신 예상하지 못한 것이 나왔다. **경로의 시작·끝점이 아무 말 없이 옮겨진다.**

| | TMAP | OSRM |
| --- | --- | --- |
| 중앙값 | 11.6 m | 13.2 m |
| 10 m 초과 | **57%** | 57% |
| 최대 | 390 m (청담대교) | 380 m |

**TMAP도 똑같이 옮긴다.** 지도를 고르는 문제가 아니라 우리 데이터의 문제다. 다리
한가운데·산속·방파제처럼 보행 도로망이 닿지 않는 곳에 핀이 있으면 어느 엔진이든
가장 가까운 길로 끌어당긴다. 외국인이 "도착"을 보고 두리번거리는데 촬영지가 수백 m
밖인 상황이 실제로 생긴다.

후보 셋을 열어 둔다 — **접근 지점(access point) 별도 저장** · **경로 끝에서 촬영지까지
남은 거리 표시** · **5-2절 좌표 검수 편집기 우선순위 올리기.** 셋 다 결정 전이다.

### 10-4. 6-3절의 전제가 하나 깨졌다

도보 경로가 한강을 가로지르는 일이 나왔다. 한강버스가 OSM에 `route=ferry` 로 등록돼
있고 OSRM·Valhalla 둘 다 도보 프로파일에서 페리를 기본 허용하기 때문이다. 배는 도보가
아니고 운항 시간표가 있으므로, **"도보는 시간에 무관하니 캐시해도 된다"는 6-3절의
전제가 그대로는 성립하지 않는다.** 도보 프로파일에서 페리를 배제해야 다시 성립한다.

부수적으로 확인된 것 둘 — 촬영지 155곳 중 **5쌍이 같은 좌표**를 쓰고 그중 한 쌍은
이름까지 같은 중복 행이다(dedupe가 놓쳤다). 그리고 6-3절의 온디맨드 계산 + 저장은
실제로 먹는다 — 같은 경로 두 번째 요청이 **3,611 ms → 0 ms** 였다.

### 10-5. 남은 것

- 인도·횡단보도를 사람이 화면에서 눈으로 확인하는 절차. 네이버가 도보 경로 API를
  열어 두지 않아 자동화할 수 없다.
- 속초 구간에서 Valhalla와 OSRM이 97.6% 차이 난 이유. 나머지 구간은 4.5% 안쪽이었다.

### 11-1. 계획 단계에서는 직선거리만 쓴다

**1절의 "두 지점을 직선으로 잇는 것으로는 안 된다"가 계획 단계에 한해 뒤집혔다.**
여행 전에는 거리(km)만 보여 주고 **예상 소요 시간도 표시하지 않는다.** 실제 도로
경로는 코스를 시작한 뒤에만 부른다.

이유는 비용이다. 코스를 짜는 동안 장소를 넣고 빼고 순서를 바꿀 때마다 길찾기 API를
부르면 감당이 안 된다. 회의 원문 — *"사람이 직접 짤 때는 길을 알 수 없으니까 직선거리만
볼 거란 말이죠"*, *"여행 전에는 무조건 직선으로 보여 주는 거 하고, 몇 분 걸릴지도 그냥
안 보이도록 하고. 여행 중에만 이걸 넣기로 하면 어때요?"*

같은 이유로 **길찾기는 유료 기능으로 뺀다.**

### 11-2. 길찾기 API는 T맵 종량제 하나로 통합한다

**10-1·10-2절이 세운 「ODsay + TMAP」 조합이 여기서 뒤집혔다.** 회의에서 실제로 찾아본
숫자가 근거다.

| 항목 | 값 |
| --- | --- |
| T맵 라이트 요금제 | 1일 1만 건 / 월 220만원 (모든 API 합산) |
| T맵 라이트 — 경유지 최적화 | 1일 100건 |
| 온디맨드 종량제 (출발지–도착지 단일) | 회당 11.88원 |
| 유저 1명이 하루 100회 호출 | 약 1,188원 → 월 약 35,640원 |

원문 — *"T맵 종량제로 씁시다. 굳이 오디세이 이런 거 조합해서 쓰지 말고"*, *"종량제로
나가는 대로 청구하게 하고, 어차피 우리 많이 안 쓸 거면 뒷수습할 필요도 없고"*.

> 회당 11.88원은 회의 중 검색으로 확인한 값이고 팩트 체크 전이다. 구독료를 이 숫자로
> 정할 예정이므로 확정 전에 반드시 확인한다.

이 결정이 10-2절의 다국어 소득을 함께 버린다는 점은 아직 회의에서 다뤄지지 않았다.
T맵 단독이면 정류장·노선·환승 안내를 우리가 번역해야 하고, 그 자리는 오역이 곧 길
잃음으로 이어진다.

**다만 잃는 폭은 6개 언어가 아니다.** 대상 언어는
[MZ2AZ-117](https://mz2az.atlassian.net/browse/MZ2AZ-117)이 이미
**한국어 + 영어 + 일본어**로 정해 뒀다 — 중국 본토는 Google Play를 못 써서 제외했고,
대만(번체)만 미결이다. ODsay가 주는 여섯 중 우리가 실제로 쓸 것은 영·일 둘뿐이므로,
T맵 단독으로 갈 때 직접 만들어야 하는 것도 그 둘이다. 12절의 비교에서 이 분량을 잰다.

### 11-3. 여행 중 길찾기는 「현재 위치 → 다음 목적지」 단위다

전체 구간을 미리 계산해 두지 않는다. 사용자가 계획대로만 움직이지 않기 때문이다.
UI도 그에 맞춰 *"현재 위치 기준 여기서 길 찾기"* 로 바꾼다.

### 11-4. 시작점·끝점 — 전제가 바뀌었다

8/10에는 **"여행 전에는 성지끼리만 잇고 시작점·끝점을 두지 않는다"** 로 정했다.
이유는 하나였다 — *"저희가 숙소 정보를 받을 수 없으니까"*.

8/11에 그 전제가 깨졌다. **사용자가 직접 핀을 찍어 장소를 넣을 수 있게 하기로**
확정했고(위경도 + 제목 + 카테고리, 개인 데이터로만 보관), 숙소·공항 POI는
[MZ2AZ-209](https://mz2az.atlassian.net/browse/MZ2AZ-209)에서 T맵 POI로 따로 모은다.
즉 시작점·끝점을 둘 수 있는 재료가 생겼다. 다만 **"시작점·끝점을 둔다"로 다시
결정한 적은 없다** — 팀에 확인이 필요하다.

### 11-5. 동선 최적화는 계획 단계에 넣는다 — 회의가 뺀 것과 다른 물건이다

8/11에 *"이 코스 만들 때는 넣지 말고"* 로 정한 것은 맞다. 다만 뺀 이유가 하나뿐이었다 —
*"동선 최적화 누를 때마다 API 호출이 되는 거 아니에요?"* **길찾기 API를 부른다는 전제
위의 결정이다.**

우리가 넣을 것은 그 전제를 쓰지 않는다. 각 지점의 **위경도만으로 직선거리를 재서**
가까운 것끼리 잇고 보기 좋게 한 줄로 편다. **API 호출이 0회**이므로 회의가 든 이유가
성립하지 않는다. 회의에서도 알고리즘으로 최적화하고 그 사실을 드러내자는 이야기가
남아 있고(*"어디에 쓸지는 다시 논의"*), 회의록 미결 #4가 정확히 이 항목이다.

**왜 필요한가**: 계획 단계는 사용자가 담은 것을 직접 늘어놓는 자리인데, POI가 10개쯤
되면 사람이 순서를 짜는 일 자체가 버겁다. 버튼 하나로 뼈대를 잡아 주고, 그 뒤에 손으로
바꾸게 한다. 8절의 "최적화로 뼈대를 잡고 사람이 다듬는다" 가 그대로 여기에 붙는다.

11-1절과도 어긋나지 않는다. 계획 단계에서 쓰는 것이 직선거리뿐이라는 점은 같고,
이 기능은 그 직선을 **어떤 순서로 이을지** 만 정한다.

구현은 [MZ2AZ-247](https://mz2az.atlassian.net/browse/MZ2AZ-247)이다. 회의록 문구와
겉으로 달라 보이므로, 전제가 다르다는 사실을 다음 모임에서 팀에 알린다 — 착수를
막지는 않는다.

### 11-6. 일정

경로여정 탭이 한 주에서 **2주(8/10 ~ 8/22)** 로 늘었다. 뒤 일정은 밀리지 않는다 —
커뮤니티·로그인은 원래 8/23부터였다. 8월 말 MVP1 완료, 9/18~19 중간 발표.

## 12. 그래서 지금 무엇을 만드는가 — 두 판본을 나란히 만든다

11-2절이 T맵 단독을 확정했지만, **비교 없이 버리지 않는다.** 두 판본을 만들어 같은
코스로 재 본 뒤 확정을 굳힌다.

| | 판본 A — ODsay + T맵 | 판본 B — T맵 단독 |
| --- | --- | --- |
| 대중교통 노선 | ODsay | T맵 대중교통 |
| 도보 | T맵 보행자 경로안내 | 같음 |
| 고도 | Valhalla (`/height`, 무료) | 없음 |
| 다국어 | ODsay `lang` 6개 언어 | 직접 번역해야 함 |
| 무료 한도 | ODsay 1,000건/일 | **10건/일** |
| 상태 | 프로토타입 v2에 구현됨 | 미구현 |

**T맵을 이전에 뺀 이유가 하루 10건 제한이었다.** 그 한도로는 팀이 함께 테스트할 수
없다. 그래서 판본 B의 대중교통 호출은 **정승길 계정으로, 비교 측정할 때만 수동으로**
돌린다. 자동 테스트나 CI에 넣지 않는다.

비교할 항목은 넷이다 — 같은 출발·도착에 대한 **경로 자체의 차이**, **소요시간·요금의
차이**, **환승 안내의 상세도**, 그리고 **다국어**. 마지막 항목은 판본 B에서 우리가 얼마나
많은 문장을 직접 번역해야 하는지를 재는 것이 목적이다.

결과는 이 문서에 절을 더해 기록한다. 어느 쪽이 이기든 11-2절의 확정을 이 문서가
혼자 뒤집지 않는다 — 근거를 들고 팀 회의로 돌아간다.

> 8절의 방문 순서 최적화(거리 행렬 + 완전탐색/최근접 이웃)는 두 판본과 무관하다.
> 길찾기 API를 부르지 않으므로 어느 쪽에도 붙는다.

## 13. 대중교통 경로를 카카오로 바꾼다 (2026-08-12)

**11-2절의 「T맵 종량제 단독」이 뒤집혔다.** 정승길 확인 —
*"아예 바뀐거야. 카카오 api로 경로추천을 받을거야."*

다만 **「길찾기를 카카오로 아예 바꿨다」는 절반만 맞다.** 정확히는 **대중교통 경로가
카카오로 바뀌었고, 도보 보조와 계단은 여전히 T맵**이다. 이유는 13-5절에 있다.

이 절의 숫자는 전부 프로토타입(`~/workspace/SceneTrip_navi`)에서 실제로 돌려 나온
것이다. 추정은 추정이라고 적었다.

### 13-1. 먼저 — 카카오는 두 회사다

이 절을 쓰다 한 번 틀렸다. 다음 사람이 같은 데서 넘어지지 않게 남긴다.

| | 카카오 (개발자 플랫폼) | 카카오모빌리티 |
| --- | --- | --- |
| 호스트 | `dapi.kakao.com` | `developers.kakaomobility.com` |
| 성격 | REST 키로 바로 | 제휴 영업 |
| 대중교통 | **있다** | 없다 |
| 도보 | **있다** | 제휴 파트너 전용 |
| 자동차 | — | 길찾기 · 다중 경유지(30) · 다중 목적지(30) |
| 발급 | **심사 없음** · 당일 | 제품에 따라 신청 |

**우리가 쓰는 것은 `dapi.kakao.com` 쪽이다.** 모빌리티 문서만 보면 "카카오는 자동차만
주고 도보는 제휴 전용" 이라는 결론이 나오는데, 그건 다른 회사 이야기다.

### 13-2. ⚠️ 이 엔드포인트들은 문서에 없다

**가장 먼저 알아야 할 사실이다.**

```
dapi.kakao.com/v2/routing/publictraffic   대중교통  [사용 중]
dapi.kakao.com/v2/routing/walk            도보      [응답 확인, 미배선]
dapi.kakao.com/v2/routing/bicycle         자전거    [200 응답, 안 씀]
```

셋이 전부다 — `v2/routing/pedestrian` 과 `v1/waypoints/directions` 는 404 로 확인했다.

**카카오 공식 문서에 없다.** 카카오맵 웹이 쓰는 것을 REST 키로 부른 것이다. 동작은
하지만 **예고 없이 바뀌거나 막힐 수 있고, 요금표도 쿼터표도 없다.** 프로토타입에서는
문제가 없으나 **서비스로 낼 때는 리스크다.** 13-7절에 남겼다.

### 13-3. 실제로 부르는 것

```
GET https://dapi.kakao.com/v2/routing/publictraffic
    ?start_x&start_y&end_x&end_y&s_name&e_name
    &input_coord=WGS84&output_coord=WGS84&lang=en
Authorization: KakaoAK <REST 키>
```

키는 `developers.kakao.com` 에서 앱을 만들면 나오는 **일반 REST API 키**다. 심사가 없고
당일 발급돼 바로 호출됐다. 지도 SDK 는 **JavaScript 키가 따로**이며, 도메인 등록 자리가
`[앱 설정] → [플랫폼] → Web` 이 아니라 **JavaScript 키의 「JavaScript SDK 도메인」**
이다 — 프로토타입에서 여기로 반나절을 날렸다. 앱은 네이티브 앱 키를 쓴다.

**한 호출에 경로 15개가 온다** [실측 — 강남→잠실이 정확히 15개, 여러 구간에서 15가
상한이었다]. 각 `steps[].properties.type` 이 `WALKING`·`BUS`·`SUBWAY`·`TRAIN`·
`EXPRESSBUS`·`FERRY` 이고 `path.points` 에 좌표가 들어 있다.

### 13-4. 카카오를 고른 값어치 — 다국어와 지하 환승로

**하나. `lang` 파라미터가 먹는다.** 문서에 없어 실험으로 찾았다 [실측 11개 값].

| 값 | 결과 |
| --- | --- |
| `ko` `KO` | 한국어 |
| `en` `EN` `ja` `zh` | **영어** |
| `jp` `en-US` `zh-CN` `xx` `1` | 한국어(기본값으로 떨어짐) |

즉 **실제 번역은 한국어·영어 둘뿐**이고 일본어·중국어는 없다. 그래도 크다 —
**고유명사까지 옮긴다.**

```
ko : 간선 405 (서울광장 > 롯데백화점) · 213m 이동 · 2호선 · 횡단보도 이용
en : Main-line 405 (Seoul Plaza > Lotte Dept. Store) · Go 213m · Line 2 · Take the crosswalk
```

**10-2절의 판단을 여기서 정정한다.** 그때 ODsay를 「6개 언어」로 적었으나, ODsay가
다국어로 주는 것은 도로교통정보 쪽이고 **대중교통 경로 안내는 영어로 주지 못한다**
[프로토타입 실측]. 카카오가 그 자리를 메운다. 외국인 대상 앱에서 이것이 카카오를 고른
이유 중 하나다.

MZ2AZ-117이 정한 한·영·일 중 **일본어는 여전히 우리 몫**이다.

**둘. 턴바이턴 안내문이 랜드마크 기준으로 온다** [실측].

```
"메가 MGC커피 앞에서 파트너쥬얼리까지 오른쪽길로 30m 이동"
"동대문역사문화공원사거리에서 2개의 횡단보도 이용"
"지하보도 이용"
```

도로명은 괄호로 붙는다(`…이동(을지로)`). 처음 온 외국인에게는 도로명보다 눈에 보이는
가게 이름이 낫다.

**셋. 지하 환승로를 안다.** 10-1절에서 OSRM이 사용자를 지상으로 올려 811 m를 돌렸던
을지로3가에서, 카카오는 **「지하보도 이용」이라고 명시하며 260 m** 로 푼다. T맵(232 m)
보다 평균 42 m 길 뿐이다.

**넷. 오르막을 시간에 반영한다.** 남산 오르막 1,182 m를 **38분**으로 본다(평지 속도면
15분). T맵은 같은 구간을 19분으로 본다 — **T맵은 오르막을 시간에 넣지 않는다.**
따라서 **카카오 결과에는 Naismith 보정을 얹지 않는다.** 두 번 세게 된다.

### 13-5. 그래도 T맵을 못 놓는다 — 계단 하나 때문에

**후보의 47%는 도보 구간이 비어서 온다** [실측 — 5개 구간, 후보 75개 중 35개].
버스 전용 경로가 특히 그렇다. 정류장까지 걷는 부분을 주지 않는다.

| | 개수 | 처리 |
| --- | --- | --- |
| 도보 구간을 주는 후보 | 40 / 75 (53%) | **그대로 쓴다** — T맵 안 부른다 |
| 안 주는 후보 | 35 / 75 (47%) | 승·하차점을 차량 구간 첫·끝 좌표로 잡아 양 끝을 만든다 |

빈 것을 도보 0 m로 두면 「안 걸어도 되는 경로」가 되어 점수 1위로 올라간다(실측).
그래서 ① 1차에는 직선 × 1.3으로 **어림**, ② 예선에 오른 후보만 **T맵 도보로 실측**
한다. 구간당 평균 5.5회다.

**그리고 계단.** 카카오는 계단을 구조화해서 주지 않는다 — 안내 문구에 "계단" 이 섞여
나올 뿐이라 문자열에서 긁어야 한다. **T맵 `facilityType 17` 만이 계단을 알려 준다.**
캐리어를 끄는 외국인에게 계단은 경로를 바꿀 정보이므로, **이것 하나 때문에 T맵 도보를
놓지 못한다.**

**요금이 두 모양으로 온다.** 확정 요금은 `{value: 1500}`, 버스 전용처럼 거리 비례라
확정할 수 없으면 `{min, max}` 다. **`value` 만 읽으면 0원으로 읽혀 그 경로가 1위가
된다** — 실제로 겪었다.

**고도는 아무도 안 준다.** 카카오·T맵·ODsay 셋 다 없어 Valhalla `/height` 를 쓴다.

### 13-6. 그래서 지금 스택

| 몫 | 무엇 | 상태 |
| --- | --- | --- |
| 지도 | 네이버 | 확정 |
| POI | T맵 | 48만 건 수집 완료 |
| **대중교통 경로** | **카카오** | **주력** |
| 도보 보조 · 계단 | T맵 | **계속 쓴다** |
| 고도 | Valhalla `/height` | 무료 |
| 교차 확인 | ODsay | 비교용 유지 |
| T맵 대중교통 | 하루 10회 · **사용자 전용** | 빨간 버튼 뒤 |

12절의 두 판본 비교는 뜻이 바뀐다. **카카오는 셋째 후보가 아니라 이미 채택된 답**이므로,
고르기 위한 비교가 아니라 **카카오가 놓치는 것을 재기 위한** 비교다. T맵 대중교통을
정승길 계정으로 수동으로만 돌린다는 제약은 그대로 유효하다.

### 13-7. 답이 필요한 것

- **비공식 엔드포인트를 서비스에 그대로 쓸 것인가.** 13-2절이 가장 큰 미결이다. 막히면
  대중교통이 통째로 멈춘다 — 대비책이 있어야 한다.
- **쿼터 미확인.** 프로토타입 화면의 「각 1,000건/일」은 **추정이며 근거가 없다**
  (문서화되지 않은 엔드포인트라 공개 쿼터표가 없다). 사실로 쓰지 않는다.
- **요금 단가 미확인.** 11-2절의 회당 11.88원은 T맵 값이라 무효다. 구독료 산정 근거를
  다시 잡아야 한다.
- **일본어.** 카카오가 한국어·영어만 주므로 MZ2AZ-117의 세 언어 중 하나가 빈다.

이 넷은 팀 회의로 가져간다. 이 문서가 혼자 11-2절을 뒤집지 않는다 — 12절 끝의 규칙과
같다.
